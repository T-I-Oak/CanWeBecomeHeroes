# ローカル開発ルールの共通化計画

## 合意した開発単位

- ブランチ: `docs/v0.58-promote-local-rules`
- 予定バージョン: `0.58.0`。設定の更新は初回の実装開始時に行う。
- 基準: CanWeBecomeHeroes `c5421bd` の `01.branch_workflow.md`。
- 共通側の調査基準: GameWorksOAK `9e57b0943e208e53e01c45e49f3fcd52da82fe63`。

## スコープ

このリポジトリの実験適用規定を共通ルールへ昇格させるため、共通部開発担当向けの引継ぎ資料を作成する。
オーナーが資料を共通部担当へ渡し、共通部担当が共通ルールへの反映とレビュー依頼の作成を行う。
ゲーム担当は依頼された差分を期待内容と照合し、指摘・修正・再レビューを繰り返す。
共通ルールの確定・正式反映後、このリポジトリの重複規定を参照に置き換え、ゲーム固有の規定だけを残す。

共通化に際して、オーナー指定の次の修正を含める。
- 開始指示は「フェーズを開始してください」とし、ブランチと保存済みの引継ぎ書から判定したフェーズを開始する。
- オーナー検証の各項目に一意のIDを必ず付与し、提示・判断・フィードバック・対応記録・再提示・バックログで同じIDを使用する。
- オーナー検証へ項目を追加するときは、ID・確認内容・追加理由をチャットで明示する。非同期の反映も対象とし、オーナーの保留判断と通知の両方を必要とする。

## 対象外

- ゲーム担当によるGameWorksOAKの編集・checkout・merge・push。
- ゲーム機能・要求仕様・共通ライブラリのコード変更。
- 他ゲームのローカルルールや作業ブランチの変更。
- 引継ぎ資料の作成だけで、共通ルールの正式適用を完了したと扱うこと。

## 成果物

- 本計画書。
- `phase_docs_v0.58-promote-local-rules_common_request.md`: 共通部担当向け依頼とレビュー基準。
- 実装報告: 共通側のレビュー対象コミット、指摘と対応、正式反映の根拠、ローカル整理、検証結果。
- 通常のレビュー報告と、承認後の `phase_handover.md`。

引継ぎ資料を含む `phase_` 成果物はGitで追跡し、この開発ブランチのマージ前に削除する。
フェーズの状態は `phase_handover.md` だけで管理する。

## 実施方針

1. 計画作業で引継ぎ資料を用意し、計画終了承認後に計画書とともに保存する。
2. オーナーが共通部担当へ引き継ぐ。ゲーム担当から別チャットへの送信は行わない。
3. 共通部担当のレビュー依頼を受け、基準コミットから対象コミットまでの差分を確認する。
4. 引継ぎ資料のID単位で適合・指摘を記録する。修正があれば新しい対象コミットで再確認する。
5. この照合は共通化作業に含まれる外部成果物の確認であり、ゲーム側の通常のレビューフェーズを代替しない。
6. 共通側の確定前にはローカル規定を除去しない。依頼待ち・修正待ちを実装完了と扱わない。
7. 正式反映された共通文書へ参照を置き換え、実験適用の説明とバックログの正式適用判定項目を整理する。
8. 実装報告・終了草案を提示し、承認後に通常のレビュー・マージへ進む。

## 完了条件

- 昇格対象の全規定が共通側に反映され、既存の共通文書との矛盾が解消されている。
- 開始指示の表現、オーナー検証IDの必須化、追加時のチャット明示要件が反映されている。
- 共通部担当のレビュー依頼を照合し、未解決指摘がない。正式反映したコミットを記録している。
- ゲーム側は確定した共通規定を参照し、二重管理と無効なリンクがない。
- ゲーム固有の画面名・担当範囲は必要な形で維持されている。
- 実装フェーズの全テスト・本番ビルド結果を記録している。

## 検証方針

- 対象検証: 引継ぎ資料と原文の照合、規定IDと反映先の対応、相対リンク、旧規定・矛盾の検索、差分の目視確認。
- 共通側のテスト・本番ビルドは共通部担当に実行・記録を依頼し、レビュー時に結果を確認する。
- ゲーム側は実装終了草案の提示前に `npm.cmd test` と `npm.cmd run build` を実行する。文書・設定だけの変更でも省略しない。
- ゲーム側のバージョン設定の一致も確認する。画面挙動を変更しないため、新しい画面操作のオーナー検証項目は現時点で予定しない。
- 計画段階ではゲーム設定・既存ルールを変更しない。テストとビルドは実装段階で行う。
