# 文書の目的に沿った内容整理の計画

## 合意した開発内容

- ブランチ: `docs/v0.67-document-purpose`
- 予定バージョン: `0.67.0`。計画段階では更新せず、初回の実装開始時にpackage.jsonとpackage-lock.jsonを更新する。
- バックログ先頭の「ドキュメントに目的にそぐわない内容が記載されている」への対応。

## スコープ

プロジェクト内のMarkdown文書を点検し、仕様・生成手順・テスト手順・作業記録の配置と重複を整理する。

- `docs/`、`tests/`、アセット付属READMEなど、プロジェクトが管理する文書を対象とする。依存パッケージ、Git管理領域、ビルド出力は対象に含めない。
- `tests/README.md`の段階画像生成手順を`docs/specifications/24.image_conversion.md`へ集約する。テストREADMEには関連テストの実行方法と検証対象を残す。
- 画像選択・読み込み・キャッシュの動作仕様は`docs/specifications/02.runtime_systems.md`を正本とし、生成仕様とテスト手順から適切に参照する。
- その他の文書も目的との不一致、重複した正本、通常文書に残る過去の作業記録を点検する。必要な情報は目的に合う既存文書へ移し、必要なら意味の区切りで文書を分ける。
- 移動・統合後のリンクと見出し参照を更新し、対応結果に応じてバックログを更新する。

## 対象外

- ゲームの挙動・要求仕様の変更、ソースの改修、画像の再生成。
- 性能改善、ドラッグ操作改善、既知項目の保存など、他のバックログ項目。
- GameWorksOAK共通リポジトリの変更。
- 文書の目的整理と無関係な表現の全面改稿。

## 完了条件

- 点検した文書と判断を実装報告に記録し、各文書の内容がその目的に沿っている。
- 生成手順・動作仕様・検証手順の正本が明確であり、必要な情報を欠落させず、重複を参照へ置き換えている。
- 移動・統合に伴うローカルリンクと見出し参照が有効である。
- 全テストと本番ビルドを実行し、結果を実装報告へ記録している。失敗時は共通規定に従い調査・対応する。
- 必要なオーナー検証が生じた場合は、一意ID・理由・手順・期待結果・確認バージョンを提示し、判断と対応を記録している。

## 実装方針

1. 共通文書ガイド、構成、準拠チェックリストとプロジェクト固有の規定を確認する。
2. 管理対象のMarkdown文書を一覧化し、各文書の目的と内容を照合する。ソース・設定は文書の正確性を確かめるために参照する。
3. 情報の正本と移動先を決め、必要な情報を移してから参照元を整理する。過去の比較・作業履歴は通常文書から除き、現在の意味・意図を保持する。
4. 実装報告へ点検範囲・修正内容・対象外の発見事項を記録する。スコープ外の新規指摘はバックログへ記録し、チャットで通知する。
5. 文書のみの変更にも適用されるバージョン更新・検証・フェーズ終了承認の規定に従う。

## 検証方針

- 対象確認: 移動前後の内容照合、相対リンク・見出しアンカー・記載コマンド・テストパスの照合、`git diff --check`。
- 実行手順に変更がない場合、文書整理だけを目的とした新規テストは作成しない。
- 全テスト: `npm.cmd test`。
- 本番ビルド: `npm.cmd run build`。
- ブラウザー検証は変更内容と共通の完了条件を照合して必要性を判断し、実行する場合は`tests/README.md`のWindows実行方針に従う。
- 各確認・コマンドの結果と限界を`phase_docs_v0.67-document-purpose_implementation.md`へ記録する。
