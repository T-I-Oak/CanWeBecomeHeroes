## R-MOBILE-01の再確認

前回は24MiBを超える固定描画集合で、使用中の段階画像が毎フレーム破棄・再取得される問題を確認した。
通常プレイでその容量超過が発生することを確認した指摘ではない。
オーナーと合意した前回・今回の独立アンカー方式への変更を確認した。

- 使用順は独立した境界ノードを持つ双方向リストで管理する。
- 前回・今回の要求画像は保護し、今回使用済みなら並べ直さない。
- 前回アンカーより古い読み込み完了画像だけを破棄する。
- 容量不足A・Bでは新規取得と描画を省略し、元画像へ戻さない。
- 読み込み中も描画省略を維持し、失敗・適切な段階なしの既存フォールバックとは区別する。
- 同じRAF時刻では境界を重複更新せず、ゲーム・タイトル・開始劇・パーティー選択の各ループから更新する。
- 容量不足の静止Canvasは次フレームで再試行し、読み込み完了・失敗でも再描画する。
- 画面外の画像要求をガードする追加変更は行っていない。

`ImageLevelCache.test.js` の固定25種類・複数フレームで、24枚保持・追加取得なし・超過分省略を確認した。
前回保護解除、ズーム切り替え、同時刻の重複更新、未使用画像の破棄、古い未完了画像の保持、静止Canvasの再試行も確認した。
これらによりR-MOBILE-01を解消と判断する。容量超過分の継続的な省略自体は合意済みの動作である。

## 画像コンバーター

- `assets/image-sizes.json` の113定義、制作元、配信用PNG、687枚の段階画像、マニフェストの対応を照合した。
- 制作元113枚を前回コミット`1208f49`の配信用画像と直接比較し、全件バイト一致を確認した。
- 変換前のパス・寸法・ハッシュ検査、拡大拒否、制作元から直接の段階生成、未変更出力の書き込み省略を確認した。
- 通常ビルドはコンバーターを実行せず、制作元とサイズ定義は公開成果物へ含めない。
- 敵画像正規化の出力先を制作元へ変更し、配信用サイズを重複定義しない構成を確認した。
- 仕様のDPR3・最大zoom1.5、情報UI・選択・演出との共用を含むサイズ根拠を照合した。
- 実装時の再生成801ファイル一致記録を確認。レビューでは生成物を変更する再生成は行っていない。
- 制作元と配信用画像の比較PNGを目視確認し、提示されたweight・看板・小型敵の図柄に目立つ破綻は認めなかった。

生成済みマニフェストから通常想定66種類を再集計し、上位2段階19.453125MiB、全縮小段階20.74462890625MiBで仕様と一致した。
これはオーナー指定の同時種類数による見積もりで、全状態の上限や実測メモリ量ではない。
配信用画像・演出・DOM画像・ブラウザー内部の追加保持は24MiB予算と別である。
