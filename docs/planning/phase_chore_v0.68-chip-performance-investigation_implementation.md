# チップ負荷の調査と性能修正

## 対象

- 起点は全体レビューで挙がった性能問題の可能性であり、オーナーが実ゲームで遅さを感じて報告したものではない。

- バージョン0.68.1。提案に加え必要な修正まで対象とする。
- 修正前の測定と制約は phase_chore_v0.68-chip-performance-investigation_baseline.md を参照する。
- 描画品質、既存のメモリ予算、ゲーム挙動を維持する。他の性能や品質との引き換えが必要な変更は、利点と不利益を示してオーナーの判断を仰ぐ。

## 採用する修正

- ChipBoardの接触候補について、軸方向だけで接触しない組を距離計算より先に除外する。
- 走査用のslice・filterと、組キー生成用の配列・ソートを除く。
- 地上分離の逐次処理順、高度・拾得・転送の除外、重なり中の上下順を維持する。
- 密集した混合状態70チップを15回更新し、従来の逐次分離処理との全座標一致を検証する。

## 撤去した試作

- 合成Canvasキャッシュ、描画器への有効化、描画完了判定の追加、および専用テスト・画素比較スクリプトを撤去した。
- 既存24MiBの画像段階キャッシュは、通常画面の66種類について全段階20.74462890625MiBという容量計算に基づく。
- 試作の別枠16MiBには組み合わせ数・拡大時の容量根拠がなく、メモリ使用量を増やしていた。採用しない。
- 撤去前の試作を測った chips-fixed-* および chips-implementation-* の既存結果は、現在の修正の効果を示す根拠に使わない。
- ChipRenderer、ScaledImage、TrialSessionはHEADの実装へ復元し、追加の画像キャッシュは残さない。

## 0.68.2の構成

- `ChipContactPairs`は各チップの位置・半径・高度・上昇状態・拾得／転送フラグの変化を確認する。変化したチップ対他チップと前回の重なり組を重複なく組み合わせ、配列順に処理する。
- 地上分離前に状態を保存するため、分離で押されたチップは次の呼出しで変化として検出される。残った重なりも毎回確認する。
- 追加・削除・入替え・順序変更では全組を確認する。変化数が2%を超える場合は候補生成とソートを避けるため全組走査に戻す。
- 追跡器は描画順用と地上分離用の2個。各追跡器はN個の状態と最大4N個の重なり組を保持する。密集して上限を超えた場合は組番号を破棄し、全組走査に戻す。画像の保持量は増やさない。候補集合は呼出し内で生成・破棄する。
- 0.0001座標単位以下の地上重なりは解消済みとする。ほぼ接している配置の微小な押し戻しを終え、静止状態を追跡できるようにする。外観や通常の押し出し量を変更する精度ではないが、厳密な全座標一致とは異なる仕様として明記した。
- 通常テストが過去コミットのGit取得に依存しないよう、計測用旧ソースの読取を注入できる構成にした。実際の旧処理比較だけがコミット7960292の履歴を必要とする。

## 追加検証の方針と予備測定

- TDD初回の`node --test tests/implementation/chips/ChipContactPairs.test.js`はモジュール未実装で失敗を確認した。
- 重なりのない静止300枚の候補数は44,850→0組、1枚の位置変更では299組、5枚の変更では1,485組となることをテストで確認する。重なり中の組は静止していても継続して判定する。状態変化の確認には別途O(N)の走査が残る。
- 次の更新で新接触を検出し分離が続くこと、着地と拾得／転送状態の解除、密集時の保持上限、追加・削除・入替え・半径変更を検証する。
- 描画順は移動・着地衝撃・上昇・外部の座標や状態の変更を含め500更新で全組走査と照合する。地上分離は独立して、密集状態の逐次分離と次更新での伝播・収束を検証する。
- 予備測定では、微小な位置変化の継続と候補追跡の管理コストにより遅くなる条件を検出した。少数変化の閾値と地上の終了精度を調整し、主要測定と別ファイルへ保存した。予備測定の短い区間を主要比較の改善率として使わない。
- `tmp_performance/chips-active-preflight*.json`は各6秒×1反復の予備測定。Node単体の`tmp_performance/chips-active-node.json`は描画提出を含まない補足実験で、実ブラウザー全体の改善根拠とはしない。
- 途中構成の主要測定`tmp_performance/chips-active-primary.json`は6条件×3反復を完走したが、密集移動で関数呼出し・追跡の管理コストが増える傾向を検出した。その構成を最終結果として採用せず、候補行だけを生成して本体のループで処理する方式へ変更した。
- 最終構成では、全組走査用のインデックス配列を各追跡器にN個保持し、全組走査／候補行のどちらでも同じ分離式と描画順判定を直接実行する。組ごとのコールバック呼出しを避ける。途中構成と最終構成のデータは混ぜて集計しない。
- 対象テストは`node --test tests/implementation/chips/ChipBoard.test.js tests/implementation/chips/ChipBoardPerformance.test.js tests/implementation/chips/ChipContactPairs.test.js tests/implementation/scripts/ChipPerformance.test.js tests/implementation/scripts/PerformanceBuild.test.js`。最終構成で36件成功、失敗0、終了コード0。
