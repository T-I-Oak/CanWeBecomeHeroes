# 正式な試験終了画面

## 開発スコープ

- 対象ブランチ: `feature/v0.44-result-screen`
- 予定バージョン: `0.44.0`。初回の実装開始時に設定を更新する。
- 合格・不合格の正式な終了画面を設計・実装し、実ゲームの終了処理へ接続する。
- PC・スマートフォン向けモックアップでデザインを確認してから本番へ反映する。
- 結果、成績、終了メンバー、アチーブメントの判定・所見を表示する。
- 表示件数上限、候補選定、同点処理、カテゴリ順・カテゴリ内順序を決める。
- 合格時に各Heroへ与える二つ名の名称・選定条件・表示方法を決め、選定と表示を実装する。
- 終了画面からタイトルへ戻る遷移を整備する。
- 開発内容への合意とブランチ作成の順序、共通命名規約の適用を明確にしたワークフロー文書を今回の保存対象に含める。

## 対象外

- 記録の収集・保存とHero解放処理の変更。解放タイミングの要求と現行実装との差は別途扱う。
- アチーブメント取得トースト、レコード画面、ランキング閲覧、解放状況・通算統計の閲覧画面。
- チャレンジモードのゲーム進行・終了処理、ログ履歴、共有機能。
- 保存失敗の利用者向け表示・再試行操作。本番画面への接続で既存の失敗時の進行を妨げない。
- GameWorksOAK側の変更。

## 現状と設計の前提

- `TrialStatisticsSession`と`RunRecordsRepository`が終了情報の作成・保存を担当する。
- `TrialSession`は終了情報を`createTrialRunResult`へ渡し、`TrialRunResultModal.show()`の完了後に試験セッションを終了する。
- 仮合格画面は終了メンバーと発行情報、仮不合格画面は通知文を表示する。
- 終了情報は変更不能な値として渡され、アチーブメント全候補の累積評価と今回ランのG値を参照できる。
- 表示は通信簿のテーブル形式とし、カテゴリ・評価項目・判定・所見を示す。達成条件は終了画面に表示しない。
- 判定・所見は終了後の累積評価を使う。累積整数グレードの更新項目を優先し、残りは今回ランのG値で選定する。採用後の表示順はカテゴリ順とし、選定順と分離する。
- 二つ名は既存の今回ランのHero別情報から選定する。例示の名称・条件は未確定であり、推測して確定扱いしない。

## 実装方針

1. 成績欄、通信簿、メンバーと二つ名、合否ごとの演出、タイトルへ戻る操作をモックアップで提示する。表示上限、選定規則、二つ名の名称・条件、モバイル表示を含め、オーナーと合意してから本番へ反映する。
2. 候補選定と二つ名判定はDOM生成から分離し、既存の終了情報を入力とする。収集情報が不足する案は今回の対象外と照合し、代替案を提案する。収集・保存の変更を無断で追加しない。
3. アチーブメントの共通CSS・DOM生成を用意し、終了画面で利用する。後続のトースト・レコード画面と共有できる表示モードとエントリ一覧の境界を設けるが、それらの画面は実装しない。カテゴリの連続行からrowspanを計算する。
4. `TrialRunResultModal`を正式表示へ置き換え、合格・不合格とも既存の終了情報を使用する。終了通知・タイトル復帰で再集計や再保存を発生させない。
5. 日本語・英語の表示リソース、関連する要求・仕様、UIスタイル規約、バックログを実装結果に合わせて更新する。v0期間の公開更新履歴は空配列を維持する。

## 完了条件

- 合意したデザインと表示規則が仕様へ記録されている。
- 実ゲームの合格・不合格で正式終了画面が表示され、成績・終了メンバー・アチーブメントが終了情報と一致する。
- 合格時の各Heroの二つ名が合意した条件で決まり、表示される。
- タイトルへ戻り、次の試験を開始できる。結果の二重処理や既存記録・解放状況の変更がない。
- PC・スマートフォンの縦横表示で内容と操作に到達でき、必要なオーナー検証の判断・対応・明示的な保留が記録されている。
- 対象テスト、全テスト、本番ビルドの実行結果を実装報告へ記録し、失敗時は原因と対応を明記する。

## テスト方針

- 候補選定: 更新項目優先、上限超過、同点、未達成E、重複除外、カテゴリ順と選定順の分離を検証する。
- 二つ名: 合意した条件の境界、候補競合、該当なし、Hero別情報と終了メンバー順序を検証する。複雑な判定は実装前に仕様テストを作成する。
- 表示・接続: 合否別表示、成績と所見、動的カテゴリ行結合、日英表示、タイトル復帰、終了記録の不変性と二重処理防止を検証する。
- ブラウザ確認: PC、スマートフォン縦・横でモックアップと本番画面を確認する。
- 全体検証: `npm.cmd test`と`npm.cmd run build`を実装終了草案の提示前に実行する。
- 必要なオーナー検証は確認可能な実装ができた時点で、バージョン・理由・手順・期待結果を1件ずつ提示する。未回答を保留扱いしない。

## 保存対象と注意事項

- 計画フェーズ終了時は本計画書、承認済み引継ぎ書、`docs/planning/01.branch_workflow.md`を保存・コミットする。
- `_agent/scripts/init_hook.cjs`の案内更新はGit管理対象外のローカル変更であり、今回のコミットに強制追加しない。正式な規定の正本はワークフロー文書とする。
- ワークフロー改善時の全498テスト・本番ビルドは成功済みだが、後続実装の検証結果として流用しない。
- 計画フェーズでは本番コードやバージョン設定を変更しない。引継ぎ書は終了草案の承認後に保存する。
