# 作業計画

## 目的

バックログと要件・実装の対応を再確認し、依存関係とオーナー承認を守って未完了作業を進める。実装済みの結果画面は検証待ちへ正しく移し、固有スキルは共通の戦闘基盤を先に整えてから、承認済みのものだけを追加する。

## 現在地

- 通常試験は合格証明書／不合格通知まで実装済みであり、オーナー検証待ちである。
- 中ボス・ボスのEnemy、固有タグ、対応する固有スキルの割当は要件で確定している。
- 実装済みの固有スキルは活力・宝石・範囲の3種類である。
- 未実装の固有スキルは、挙動の要件はあるが、スキル名称、アセット、情報ウィンドウ文言の承認が必要である。
- 軽業・信用・幸運・羽の固有スキル、シェア内容、アチーブメント内容、チャレンジモードの成績項目は未確定である。

## 作業順

### 1. 台帳と現状の再確認

1. `backlog.md` と `docs/requirements/` を突き合わせ、完了済み項目を `オーナー検証` へ移す。
2. `docs/specifications/` と `src/` を突き合わせ、固有スキル、結果画面、永続化、モーダルの責務境界を確認する。
3. `npm test` と build を実行し、計画開始時点の基準を記録する。

チェックポイント:

- 要件で確定しているEnemy名・割当・戦闘規則を、未確定事項として扱っていない。
- バックログに完了済み作業や重複した作業が残っていない。
- 実装の責務分割が仕様書と矛盾していない。

### 2. 固有スキル共通基盤の設計確認

1. 既存の行動開始、ダメージ解決、ダメージ受領、行動終了、撃破のフックを一覧化する。
2. 通常保有スキルと、加護による一時保有スキルが同じフック解決経路を使うことを確認する。
3. 戦闘中だけに存在する状態（諸刃の剣、手下など）を、Entityや永続データに混在させず、専用の戦闘状態として管理する設計を定める。
4. 直接攻撃、属性付与・反射・継続効果など、ダメージの原因を区別する文脈を定める。

チェックポイント:

- スキル追加ごとに個別のフックや例外処理を増やさず、同じ意味のフックを共有できる。
- 一時状態は戦闘終了・Entity離脱時に対称に破棄され、永続化されない。
- 加護は各候補を独立に7%で抽選し、保有後の通常フックでは100%参加し、各スキル固有の確率はその後に解決する。

### 3. 固有スキルを承認単位で実装する

候補ごとに、以下を1単位として順次進める。承認前にアセット生成、文言のデータ登録、戦闘ロジック実装は行わない。

1. 対応EnemyとEx1／Ex2の効果を要件から再確認する。
2. スキル名称、アセットの役割・意匠、情報ウィンドウ文言を提案し、オーナー承認を得る。
3. 先に実装テストで効果、状態の付与・解除、加護の代理保有時を定義する。
4. 共通基盤またはスキル効果を実装し、Enemyカタログ、情報ウィンドウ、ログ、アセットを接続する。
5. 要件・既存スキル・表示を再確認し、テストとbuildを通す。
6. バックログをオーナー検証へ移す。

実装順は、共通の一時状態と会心文脈を最初に検証できる武勇（諸刃の剣）、次に炎・水、鉄、魔導、雷、布、加護とする。軽業・信用・幸運・羽は仕様決定後に別途計画する。

チェックポイント:

- 各固有スキルの名称、アセット、情報ウィンドウ文言は実装前に承認済みである。
- 対応Enemyの名称・組合せを推測して変更していない。
- 複雑な状態遷移はTDDで検証し、既存の活力・宝石・範囲の挙動を回帰確認する。

### 4. 戦闘の視認性と数値調整

1. 物理防御エフェクトを属性付与から視覚・アニメーションの両面で分離する。
2. 固有スキルを含めた後、タグ相性シミュレーションと実戦の両方で、アクションゲージ、ダメージ、HP、貢献、報酬、編成を調整する。

チェックポイント:

- エフェクトが水付与と誤認されない。
- シミュレーションの対象範囲と実戦の対象範囲が一致している、または差分が仕様書に明記されている。

### 5. ゲームループと表示機能

1. 通常試験の結果画面をオーナー検証へ移し、フィードバックがあれば同一Minorの継続修正として扱う。
2. 情報ウィンドウのサイズ切替、モバイル操作・カメラ、各エリアのビューを、共通UI仕様とモバイル規則に照らして改善する。
3. チャレンジモードは、成績に何を表示するかが決まってから専用の結果画面を設計する。合格／不合格を流用しない。
4. シェア内容、アチーブメント、ログ履歴、タイトル、説明書、チュートリアルは、それぞれ表示対象・保存対象・完了条件を決めてから着手する。

チェックポイント:

- モーダル、情報ウィンドウ、固定UIは共通の外観・レスポンシブ方針に従い、UX上の例外だけを個別化する。
- 小さいviewportでも全操作が画面内で可能であり、UI全体の`transform: scale()`に依存しない。

### 6. 記録・公開・受入確認

1. 解放状況、統計、ラン結果、クリアー記録のデータモデルと表示目的を定める。途中セーブは設けない。
2. `project_info.json`、公開手順、主要フローの受入テストを整備する。
3. オーナー検証項目を実機・公開先の確認結果で整理し、OK済み項目を削除する。

チェックポイント:

- 永続データ変更はデータバージョン規則に従う。v0系ではマイグレーションを追加しない。
- 公開前に共通ライブラリの`master`状態、テスト、build、未追跡の`dev_`／`tmp_`を確認する。
- `dev_` 文書を作成した作業は、その文書を削除することをバックログの完了条件へ明記する。永続的に参照する計画・仕様・設定資料には`dev_`を付けない。

## 直近の着手点

1. 第1章の台帳整理として、通常試験の結果画面を`オーナー検証`に記載する。
2. 第2章の現状確認として、既存の戦闘フックと固有スキルの責務を読み取り、諸刃の剣に必要な共通基盤だけを設計する。
3. 武勇Exの名称・アセット・情報ウィンドウ文言、および会心倍率が攻撃者・被攻撃者の双方に付く場合の扱いを提案し、承認を待つ。
