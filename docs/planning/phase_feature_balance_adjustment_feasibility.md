# Exスキルを含むシミュレーションの実現可能性調査

## 結論

戦闘開始状態を設定し、実ゲームの戦闘・移動・実体管理・装備回収・帰還を動かす範囲では、A（シミュレーション側の追加のみ、アプリ修正不要）で進められる根拠を確認した。

画面ドライバーや実行環境のstubをシミュレーション側に置くことと、アプリにシミュレーション機能を追加することは異なる。本調査ではアプリのソースを変更していない。既存クラスの読み込みと公開メソッドによる操作で検証した。

## 比較対象

| 区分 | 内容 | 調査結果 |
| --- | --- | --- |
| A | シミュレーションの機能追加のみ、アプリ修正不要 | 戦闘と周辺の既存オブジェクトを利用する方式で実行確認済み |
| B | シミュレーション側の追加と、アプリのごく狭い修正 | 現在の検証範囲では必要箇所なし |
| C | シミュレーションとアプリの両方を大きく修正 | 必要性を示す問題は見つからなかった。採用しない |
| D | 主にアプリを大きく修正 | 必要性を示す問題は見つからなかった。シミュレーション機能をアプリへ入れる方式は採用しない |

## 既存コードの確認

- `BattleSystem` は `controller`、`returnSystem`、乱数関数、ダメージ通知を外側から受け取れる。画面エフェクトは省略できる。
- `HeroItemInteractionController`、`ItemPickupController`、`HeroSlotManager`、`FacilityReturnSystem`、`ChipBoard` はNode上で読み込み・実行できる。
- `EnemyFactory.createFromDefinition()` は中ボス・ボスを生成でき、`Enemy` が敵定義のExスキルを保持する。
- 召喚、幻影頭、吹き飛ばし、属性反射、状態異常などの処理は既存の戦闘クラスにある。
- 従来の `BattleSimulationRunner` は敵を通常敵として作成し、実体管理と帰還を簡略化し、`ChipBoard` やアイテム回収の時間更新を行っていない。Exスキルを評価するにはシミュレーション側で利用範囲を広げる必要がある。
- `GameApp.js` の試験初期化にはDOM操作が混在しているが、利用するゲームクラスそのものを取り出すためのソース変更は不要だった。

## 実行した検証

検証用ファイル: リポジトリ直下の `tmp_ex_feasibility.mjs`。

```powershell
node tmp_ex_feasibility.mjs
```

結果: 終了コード0。詳細は `tmp_ex_feasibility_results.json`。

ドライバーは以下を既存クラスで構成した。

1. 実ゲームのワールドサイズで盤面、Heroスロット、実体管理、アイテム回収、帰還、戦闘を生成する。
2. Heroを戦闘スロットへ配置し、敵定義から中ボス・ボスを生成する。
3. 盤面 → 実体管理・回収 → 戦闘の順序で、1/60秒・1tickずつ進める。
4. 外側からダメージイベントとスキル処理の呼び出しを観測する。

以下を確認した。

- 14種類 × 2レベルの28条件を各1,800tick実行し、例外なく終了する。
- 各敵のスキルIDとレベルが、指定した敵定義と一致する。
- 戦闘中に各スキルの処理へ到達する。死亡時召喚は別途強制撃破で確認する。加護のランダムスキルは付与された別スキルの処理への到達を確認する。
- 活力の死亡時召喚は両レベルで2体を実体管理へ追加し、盤面更新で着地する。
- 範囲の幻影頭は追加後に攻撃し、ダメージイベントを発生させる。
- 鉄の吹き飛ばしは両レベルで移動後に元の位置へ帰還する。
- 羽の倉庫移動は、既存の回収処理で両手の装備を回収し、戦闘スロットへ復帰する。検証条件では277tickで復帰した。
- 同一seedの水ボス戦を2回動かし、ダメージイベント列が一致する。

HP・スタミナ10などの検証条件は経路確認用であり、バランスの調整案ではない。実ゲームの設定・数値を変更していない。

## アプリ側の必要修正と、シミュレーション側の残作業

今回確認した方式では、アプリ側の必要修正は0ファイル・0行。既存のゲームオブジェクトを利用するドライバーはシミュレーション側に置ける。共通基盤への分離、ゲーム側への設定・集計機能の追加、画面用インターフェースの新設は現時点で不要。

シミュレーション側には、状態設定、既存オブジェクトの組み立て・更新、召喚を含む勝敗判定、結果集計、入力条件の拡張が必要。検証用ドライバーをそのまま正式版にするのではなく、従来の入力・集計との互換性を整理する。

画面を含む `startGame()` 全体をDOM/canvasのstubで起動する方式は、実行検証していない。画面入力、画像、保存、ダイアログ、フレーム更新などの環境対応が別途必要。ただし、今回の戦闘評価を行うためにその入口を使う必要はなかった。

## 検証の限界

- 全スキルの効果量・確率の正しさを個別に網羅した検証ではない。スキル処理への到達と、特に依存範囲が広い移動・召喚の経路を確認した。
- 実ブラウザで動くゲームとの同一状態・同一seedによる結果照合、大量試行の性能測定は未実施。
- 試験全体のステージ進行、手動の再出撃、施設利用などを含むシミュレーションは未検証。戦闘単位でどこまで含めるかは正式実装時に明示する。
- 描画のみ省略できるが、召喚追加などを行うアニメーション完了コールバックや移動時間は既存処理どおり進める必要がある。
- 正式実装時は `GameApp.js` の更新順序との対応を確認する。現行クラスを利用しても、ドライバーの更新順序が異なれば結果が変わり得る。

本調査は実装フェーズ内の調査であり、フェーズ終了や引継ぎの更新は行っていない。
