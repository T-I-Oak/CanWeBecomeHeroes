# 準備エリアの導入説明開始タイミング修正

## 合意内容

- ブランチ: `fix/v0.65-tutorial-after-hero-landing`
- 予定バージョン: `0.65.0`。計画時点の設定は `0.64.4` のままとし、実装開始時に更新する。
- バックログ先頭の「準備エリアの説明チュートリアルの開始タイミング修正」を対象とする。

## 開発スコープ

初期Hero全員の落下・跳ね返りが完了してから、課題選択後のゲーム画面の導入説明を開始する。固定時間の待機ではなく、チップの実際の着地状態を開始条件に反映する。

既読状態、チュートリアルのリセット、課題選択、手動一時停止など既存の停止理由との関係を維持する。

## 対象外

- 説明文、ページ分割、ハイライト、カメラ演出の変更。
- 落下・跳ね返りの物理挙動やゲームバランスの変更。
- 情報ウィンドウの性能改善、そのほかのバックログ項目。
- GameWorksOAKの共通ライブラリの変更。

## 現状と実装方針

`src/app/TrialSession.js` は課題選択終了時および更新中に `TutorialController.check()` を呼ぶ。`src/app/TutorialController.js` の `getTutorialTimings()` は、通常ゲーム画面で直ちに `game-screen` を提供する。説明開始時にはチュートリアルの停止理由が追加されるため、初期Heroが落下途中でもゲームが停止する。

`src/chips/ChipBoard.js` の落下処理には着地時の跳ね返りがある。初回の地面接触だけでなく、落下・跳ね返りが完了した状態を確認する。実装時に初期Heroの生成と更新順を確認し、初期Heroを対象とする開始可否をゲーム側から提供する。シナリオIDや既読状態の判定は既存の共通TutorialManagerに任せ、ゲーム側へ重複させない。

着地待ちの間は必要な物理更新を進められる構造とする。課題選択の説明や他のチュートリアルの開始条件への影響を確認し、リセット後の再開も維持する。

必要な要求・仕様書を更新し、対応が完了したバックログ項目を整理する。共通ルールは参照専用とする。

## 完了条件

1. 初期Heroのうち1人でも落下・跳ね返り中なら、ゲーム画面の導入説明を開始しない。
2. 初期Hero全員の落下・跳ね返りが完了し、既存のシナリオ開始条件を満たしたら導入説明が開始する。
3. 課題選択の説明、既読による抑止、リセット後の再開が維持される。
4. 手動一時停止や課題選択など、他の停止理由を勝手に解除しない。
5. 対象テスト、全テスト、本番ビルドの結果を実装報告へ記録する。失敗時は共通手順に従って原因と対応を記録する。
6. 必要なオーナー検証を実装中に提示し、判断と対応を記録する。未回答を保留扱いしない。

## テスト・確認方針

- 開始条件のテストを先に追加し、落下中、跳ね返り中、一部だけ着地、全員着地を検証する。
- 既存の `tests/implementation/app/Tutorial.test.js` などを利用し、課題選択、既読、リセット、ほかの停止理由の回帰を確認する。
- ブラウザー検証で実際の初期Heroの生成・物理更新・説明開始の順序を確認する。
- `tests/README.md` の手順に従い、対象テストに加えて全テストと `npm.cmd run build` を実行する。
- オーナー確認は初回導入の見え方を操作可能な単位で提示する。一意の検証ID、操作手順、期待結果、確認バージョンを記載する。タイトルと倉庫左下の表示が設定バージョンと一致することも確認する。
- URLへバージョンパラメーターを付けない。
