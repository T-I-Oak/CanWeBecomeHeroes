# ブランチ作業フロー

## 目的

開発作業とオーナー検証を混ぜず、変更の範囲、確認対象、masterへ取り込む単位を明確にする。

## 開発ブランチの開始から終了まで

1. 着手前に、今回の開発スコープを決める。
2. そのスコープ専用のブランチを作成する。
3. 設計・実装・テスト・必要な文書更新を行う。レビュー指摘またはオーナー検証NGがあれば、この段階へ戻る。
4. 設計・実装・テスト結果をレビューする。未解決指摘がなければ、必要なオーナー検証を完了または保留へ記録する。確認を依頼するときは、チャットに `package.json` のバージョンと、確認してほしい内容を書く。タイトルと倉庫左下の `vX.Y.Z` が、そのバージョンと一致していることを、修正済みのソースを見ている条件にする。オーナー検証の項目にはバージョンを書かない。
   - その場でオーナーへ確認を依頼し、確認が完了したら作業を完了する。
   - 直ちに確認できない結果は、`backlog.md` の「オーナー検証」へ確認内容を記録する。1項目には確認を1件だけ書く。確認は、画面の操作か見た目で合否が判断できるものにする。実装の内部や、見る対象が特定できない文言は書かない。
5. 確認済み、またはオーナー検証へ記録済みの状態でブランチを閉じ、masterへマージする。

## AI によるフェーズ実行

### 実装フェーズのバージョン更新

バージョン設定（`package.json`、`package-lock.json`）は実装フェーズで更新する。以下のルールは、次回の実装フェーズから適用する。現在マージ待ちの0.34.0は変更しない。

- 初回の実装フェーズ開始時は、計画で決めたMinorを使用し、Patchを0にする。
- 2回目以降の実装フェーズ開始時は、Minorを維持してPatchを1上げる。レビュー指摘やオーナー検証NGによる実装への差し戻しも含む。
- 実装フェーズの終了が承認されず、実装を変更する場合も、変更に着手するときにPatchを1上げる。同じ実装フェーズ内でも適用する。
- 同じ修正版を作る途中の個々の指摘やコミットごとにはPatchを上げない。再提示した終了草案が再び承認されず、さらに実装を変更する場合は、もう1上げる。
- レビューやマージへの移行だけではバージョンを更新しない。確認を依頼するときは、更新済みの設定・画面表示と一致するバージョンをチャットに記載する。

### 担当範囲

- このプロジェクトを担当するAIの責務は、CanWeBecomeHeroesの開発である。
- GameWorksOAKは、開発ルールと共通ライブラリの参照専用とし、変更しない。
- 共通基盤に修正が必要なら、問題と必要な変更をオーナーへ報告し、別担当による対応を求める。

### フェーズ開始の指示

AI の担当は固定しない。オーナーは、正式指示「次のフェーズを開始してください」または短縮指示「フェーズ開始」により、新しいフェーズの開始を依頼する。「フェーズ開始」は現在のフェーズの継続ではなく、保存済みの状態から次に指定されたフェーズを開始する指示である。

オーナーは、同じ AI へ連続するフェーズを依頼してもよいし、フェーズごとに別の AI へ依頼してもよい。原則として、各フェーズは新しいセッションで開始する。AI は、依頼されたフェーズに定められた責務を越えて作業してはならない。

### フェーズの共通ステップ

マージ以外の各フェーズは、必ず次の4ステップを順に行う。

1. **フェーズ確認**: 現在ブランチと `dev_handover.md` の有無・「次に開始するフェーズ」を確認し、表に従って今回のフェーズを一意に判定する。状態を特定できない場合は、推測せずオーナーへ判断を依頼する。
2. **フェーズ宣言**: 判定したフェーズ名をチャットで宣言する。宣言前に主作業を始めない。
3. **実施**: そのフェーズの主作業と成果物作成を行う。この時点では `dev_handover.md` を更新しない。
4. **承認**: 次フェーズへ向けた `dev_handover.md` の草案をチャットへ表示して停止する。草案を表示した時点ではフェーズは完了しておらず、保存済みの引継ぎ書も更新しない。草案表示後のオーナーの `ok` は、その草案の承認を表す。承認されたときだけ、表示した草案と同じ内容を `dev_handover.md` へ書き込む。その後に「フェーズが完了しました」と記載し、保存した引継ぎ書の内容をそのまま示す。

マージ・フェーズは承認ステップを持たない。マージ後に、操作後に確認したmasterへのマージ結果と `dev_handover.md` を削除した事実だけを報告する。削除済みまたは過去の成果物を現在の状態として報告してはならない。

### ブランチ内の一時成果物

開発ブランチでは、`docs/planning/` に次の `dev_` ファイルを置く。`<branch>` はブランチ名をファイル名として安全な表記へ置換した識別子とする。

- `dev_<branch>_plan.md`: 開発スコープ、対象外、完了条件、実装・テスト方針。
- `dev_<branch>_implementation.md`: 計画に対する実装結果、変更箇所、対象テスト・全テスト・本番ビルドの結果、失敗時の調査結果、オーナー検証候補。
- `dev_<branch>_review.md`: 現時点のレビュー結果。未解決指摘の有無を明確に記載する。
- `dev_handover.md`: 次に開始するフェーズと、次担当へ伝えるべき注意事項を記録する唯一の引継ぎ書。

これらは開発期間中だけ維持する `dev_` 成果物であり、マージ前に削除する。フェーズを表す記述は `dev_handover.md` だけに置き、計画書・実装報告・レビュー報告へ状態フィールドを重複して持たせない。

### `dev_handover.md` の記載と更新

`dev_handover.md` には、少なくとも次の3項目を置く。

- 次に開始するフェーズ
- 直前のフェーズで完了したこと
- 次担当への注意事項（なければ「なし」）

計画フェーズは、開発ブランチと計画書を作成し、承認された後に `dev_handover.md` へ次フェーズ「実装」を記録する。以後、各非マージフェーズは承認された草案だけを `dev_handover.md` に更新する。マージ・フェーズは、すべての `dev_` 成果物とともに `dev_handover.md` を削除する。

### フェーズの判定と成果物

| ブランチと引継ぎ書の状態 | 実行するフェーズ | 実施してよいこと | 出力して停止するもの |
| --- | --- | --- | --- |
| `master` 上で `dev_handover.md` がない | 計画 | 開発スコープを決め、開発ブランチと計画書を作成する。 | 引継ぎ書の草案 |
| 開発ブランチ上で `dev_handover.md` があり、「実装」と記載されている | 実装 | 計画の範囲内で設計・実装、対象テスト・全テスト・本番ビルド、必要な仕様書・バックログ更新を行う。レビュー指摘またはオーナー検証NGの修正もこのフェーズで行う。 | `dev_<branch>_implementation.md` と引継ぎ書の草案 |
| 開発ブランチ上で `dev_handover.md` があり、「レビュー」と記載されている | レビュー | 計画、設計、仕様、共通ルール、ブランチ差分、テスト結果を照合する。修正後の再確認もこのフェーズで行う。ソースは変更しない。レビューで問題がなければオーナー検証を扱う。 | `dev_<branch>_review.md` と引継ぎ書の草案 |
| 開発ブランチ上で `dev_handover.md` があり、「マージ」と記載されている | マージ | 必要な確認が完了していることを確認し、`dev_` 成果物を削除してコミット・masterへのマージを行う。 | masterへのマージ結果 |

`master` 上に `dev_handover.md` がある、開発ブランチ上に `dev_handover.md` がない、引継ぎ書のフェーズが上表にない、またはブランチ自体を特定できない場合は異常状態である。AIはフェーズを推測して開始せず、オーナーへ判断を依頼する。

### 完了時に記載する次フェーズ

| 完了したフェーズ | `dev_handover.md` に記載する次フェーズ |
| --- | --- |
| 計画 | 実装 |
| 実装 | レビュー |
| レビュー | 未解決指摘またはオーナー検証NGがあれば実装。全項目がOKまたは「いまは検証しない」ならマージ。 |
| マージ | `dev_handover.md` を削除するため、次フェーズは記載しない。 |

レビュー報告に未解決指摘がないことは、レビューを実施した AI だけが記録できる。実装フェーズの AI は、レビュー指摘またはオーナー検証NGへの対応内容を実装報告へ追記する。

フェーズ判定に `git status` の未コミット差分の有無を使ってはならない。計画書自体も差分になるためである。`git diff master...HEAD` はレビュー対象の確認に使うが、着手するフェーズは `dev_handover.md` の記載だけで判定する。

### 実装フェーズの完了条件

実装中は、変更した機能に対応する対象テストを随時実行する。対象テストの成功だけで実装フェーズを完了してはならない。

フェーズの承認草案を表示する前に、テストスイート全体と本番ビルドを実行する。ソース、アセット、文書、設定だけの変更であっても省略しない。実装報告には、対象テスト、全テスト、本番ビルドのそれぞれについて、実行したコマンドと結果を記録する。

全テストまたは本番ビルドが失敗した場合、実装担当は承認草案を表示する前に原因を調査する。今回の計画範囲または今回の変更が原因なら修正して再実行する。既存の失敗または明らかなスコープ外の失敗なら、失敗内容、調査結果、今回修正しない理由を実装報告へ記録する。テストが要求仕様と矛盾すると判断した場合は、テストを都合よく変更せず、オーナーへ確認を求める。

レビュー担当は、実装報告に記載された検証結果とブランチ差分を照合する。レビューのためにテストを再実行してもよいが、実装の完了根拠を記録する責務は実装担当にある。

### レビュー中のオーナー検証項目の扱い

レビューで未解決指摘がないと確認した後、画面操作または見た目でオーナーに確認してもらう必要がある項目を検討する。項目が0件なら、承認草案の次フェーズは「マージ」とする。画面操作や見た目の確認は原則としてレビュー時に行うが、実装フェーズの承認草案確認時などにオーナーから指摘があった場合は、形式的なレビューへの移行を待たずに、そのまま実装フェーズ内で修正対応を行ってよい。

項目が1件以上ある場合は、各項目を依頼する。オーナーが各項目について返す結果は次の3つだけとする。

- **いまは検証しない**: その項目だけをbacklogの「オーナー検証」へ記録する。1項目には確認を1件だけ書く。
- **OK**: その項目の検証を完了する。backlogに記録済みの項目なら削除する。
- **NG**: その項目を差し戻しとして扱う。

依頼済みの全項目について結果を反映した時点で、NGが1件でもあれば、承認草案の次フェーズを「実装」とする。NGがなく、各項目がOKまたは「いまは検証しない」なら、承認草案の次フェーズを「マージ」とする。

オーナー検証の回答を待つ間も、保存済みの引継ぎ書は「レビュー」のままとする。次担当への注意事項に、依頼済み項目と未回答項目を記載する。独立した「オーナー検証」フェーズは設けない。

## オーナー検証中の指摘

オーナー検証中や実ゲーム確認中に受けた指摘は、現在の開発スコープと照合する。

- 現在の作業範囲内であれば、そのブランチで修正する。
- 現在の作業範囲外であれば、`backlog.md` の未完了項目として依存関係と優先順に合う位置へ追加する。
- オーナーが修正を指示したブロッキングバグだけは、現在のスコープ外でもその修正を行う。バックログへ送って止めない。バグの報告やバックログへの追加だけでは修正しない。

スコープ外の新規作業を「オーナー検証」へ記録してはならない。「オーナー検証」は、開発ブランチで実装済みの結果について、オーナーが確認するための項目だけを置く。

開発中に、別のオーナー検証が進むことがある。各項目の「いまは検証しない」、OK、NGは、その開発と非同期に届く。backlogへの反映は、届いた時点で行う。

- 「いまは検証しない」の項目は、「オーナー検証」へ追加する。実装はしない。
- OK の項目は、「オーナー検証」から外す。実装はしない。
- NGは、「要望・バグ指摘」へ戻し、依存関係と優先順に合う位置へ置く。
- 差し戻しの実装は、現在の開発スコープと照合する。範囲内ならそのブランチで修正する。範囲外なら、修正の指示があるまで実装しない。ブロッキングバグは、修正を指示されたときだけ直ちに修正する。
- 差し戻しの着手は、その項目をマージした Minor の継続開発である。Minor は上げない。Patchの更新は「実装フェーズのバージョン更新」に従い、差し戻し対応の実装フェーズ開始時に行う。コミットのたびにPatchは上げない。

## 定期見直し

新規開発で Minor の下1桁が 0 または 5 になるとき、その版は文書とソースの見直しだけにする。機能の実装と同じブランチへ混ぜない。同じ Minor の Patch では始めない。`0.23` の次の見直しは `0.25.0` である。見る範囲と直した点の報告は、`GameWorksOAK/docs/common/03.workflow_guide.md` の定期見直しに従う。
