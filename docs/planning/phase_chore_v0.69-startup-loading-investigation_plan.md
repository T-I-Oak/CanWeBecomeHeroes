# 起動時の読み込み負荷調査計画

## 合意した開発内容

- ブランチ: `chore/v0.69-startup-loading-investigation`
- 予定バージョン: `0.69.0`。初回の実装フェーズ開始時にpackage.jsonとpackage-lock.jsonを更新する。計画時点の設定は`0.68.2`を維持する。
- バックログ先頭の「起動時JavaScriptのサイズと読み込み負荷を調査する」を対象とする。
- 本番ビルドの現状を測定し、調査用ビルドで候補を比較する。オーナーの本番実装指示に基づき、画像マニフェストの静的チャンク分割を本番設定へ適用し、通常ビルドの警告解消までを今回の範囲とする。再実装の予定バージョンは`0.69.1`、ブランチは維持する。
- オーナーの補足に従い、判断の主目的はチャンクサイズ警告への対応とする。開始時間の短縮を必須とせず、性能測定は補足資料として扱う。画像マニフェストの静的チャンク分割も比較し、警告を解消する最小限の案を優先する。

## 現状と調査対象

`src/main.js`からGameAppを読み込み、GameAppはTrialSessionを静的にimportする。TitleMenuもRecordScreenを静的にimportし、タイトル生成時にインスタンスを構築する。ScaledImageは画像マニフェストを静的にimportする。GameTextRepositoryは起動時に各文言リソースの読み込み完了を待つ。

これらはコードを確認した時点の構造であり、個別モジュールが最終チャンクへ与える寄与や実行時間は未測定である。既存distのサイズだけを基準値とせず、現行ソースからビルドし直して確認する。

## スコープ

1. 現行の本番ビルドについて、起動時の依存関係、生成チャンク、初回取得リソースと読み込み順序を確認する。
2. TrialSessionをゲーム開始時、RecordScreenを初回表示時に読み込む候補を優先して調査用ビルドに実装し、個別および併用の効果を比較する。共有依存が起動側に残る量も確認する。
3. タイトル操作可能後の先読みを比較し、起動時の競合、即時操作時の待ち時間、先読み完了後の待ち時間と通信量を確認する。
4. 画像マニフェストの表現縮小を調査用ビルドで比較する。画像段階選択・キャッシュの既存仕様を維持する前提で、通信量と解析・実行負荷を評価する。
5. 再現可能な測定手順・必要な計測補助とテストを整備し、実装報告へ比較結果、推奨案、採用判断の条件と限界を記録する。
6. `vite.config.js`のmanualChunksで`src/chips/image-levels.json`だけを静的分割する。通常ビルドの警告0件と既存の画面・画像描画・言語切替を確認する。実装報告・バックログ・必要な構成文書へ適用結果を反映する。

## 対象外

- 本番への遅延読み込み・先読み・マニフェスト内容変更、ゲームルール・画面仕様の変更。
- モバイルドラッグ、レコードの既知項目、タグスキル上限など他のバックログ項目。
- 共通GameWorksOAKリポジトリの変更。
- チャンク警告上限の引き上げだけによる対処。
- ローカル測定を公開環境やモバイル実機の性能保証として扱うこと。

## 測定方針

- Vite開発サーバーではなく、現行と各候補を同じ条件で生成した本番相当ビルドを配信する。調査用変換・計測フックは通常ビルドへ含めない。
- 通常ビルドを基準に、遅延読み込みの各候補、併用、先読み有無、マニフェスト縮小の寄与を区別する。候補を組み合わせる前に単独の効果を確認する。
- ブラウザー・バージョン、画面サイズ、CPU制限、通信条件、圧縮配信の有無、保存データ、キャッシュ条件、反復数を記録する。冷えたキャッシュと再訪を区別し、同じ初期状態で原則3回以上反復する。
- 生成JavaScriptの非圧縮サイズ・gzip参考サイズと、ブラウザーで実際に観測した初回通信量を区別する。タイトル操作可能までと、その後の先読み・画面遷移による追加取得を別集計し、単なる取得時期の移動を総量削減としない。
- ナビゲーション開始からタイトルが操作を受け付けるまでを測る。DOM表示だけでなく実際の操作受付を確認する。ゲーム開始・レコード表示は操作から対象画面が利用可能になるまでを測り、演出など固定の待ちと読み込み待ちを区別する。
- JavaScriptの解析・実行はブラウザーのトレース等で確認する。総経過時間やページ全体のCPU指標をそのまま解析時間としない。計測負荷の影響と取得できない指標は明示する。
- 初回表示直後の操作と先読み完了後の操作を分ける。初回と再表示、通常試験と挑戦モード、タイトルへの復帰時に構成が成立することも確認する。
- 各反復の結果とばらつきを示し、共有モジュールの残留・重複や依存関係による削減限界を報告する。測定中に別のテスト・ビルドを並行実行しない。
- 採取JSON・トレース・比較用ビルドはリポジトリ内の`tmp_`配下へ置く。生データや過去の測定表を恒久資料に追加せず、今回の結果はフェーズ実装報告へ記載する。

## 実装・テスト方針

調査専用のビルド変換・計測補助はscriptsの責務として配置し、既存のチップ描画性能調査と目的を区別する。複雑な集計や状態管理は先にテストで契約を定義する。比較用の変換が適用されなかった場合や必要な画面へ到達しなかった場合を成功として集計しない。

- 対象テスト: 追加・変更した計測補助のテスト、TrialSession・レコード・画像マニフェストに関わる既存テストを変更内容に応じて選定し、コマンドと結果を記録する。
- 全テスト: `npm.cmd test`。
- 本番ビルド: `npm.cmd run build`。通常出力へ調査用フック・比較用実装が混入しないことを確認する。
- ブラウザー検証: `npm.cmd run test:browser`と候補ごとの到達・遷移確認。Windowsの権限、終了コードとサーバー終了確認は[テスト手順](../../tests/README.md#ブラウザー検証と公開前の実行順)に従う。
- 調査専用候補でもタイトル、試験開始、レコード初回表示・再表示、言語切替と画像描画が成立することを確認する。
- 必要なオーナー判断は一意ID・確認バージョン・理由・手順・期待結果とともに提示し、判断・対応を実装報告へ記録する。未回答を保留扱いしない。

## 完了条件

1. 現行と候補について、初回通信量、JavaScript解析・実行時間、タイトル操作可能までの時間、ゲーム開始とレコード初回表示の待ち時間を同じ条件で比較している。
2. 共有依存、先読みの競合と通信量、画像マニフェスト縮小の効果を確認し、推奨案と採用時の注意事項を示している。効果が乏しい候補も結果と理由を記録する。
3. 測定条件・再実行手順・各反復のばらつき・測定の限界が記録され、推測と測定結果が区別されている。
4. 対象テスト・全テスト・本番ビルド・ブラウザー検証のコマンドと結果を実装報告へ記録している。失敗は原因と今回の対応範囲を調査している。
5. 本番設定へ画像マニフェストの静的分割を適用し、警告上限を変えず通常ビルドでチャンクサイズ警告0件を確認している。主要画面・画像描画・言語切替が維持され、調査用コードの通常ビルドへの混入がない。必要な仕様・手順・バックログを結果に応じて更新している。
