# モバイル性能の原因調査・情報採取計画

## 目的と合意内容

モバイルでは動作が非常に重く、ゲームとして操作できないとの報告を受けた。
実機では開発者ツールを使用できず、確認にはpushと公開が必要である。
原因調査と比較実験はまずPC上で進める。PCでは説明できない実機の極端な遅さを絞るため、
オーナーの追加合意により、開発者ツール不要の計測画面を一度公開して実機採取する。
採取後は同じブランチで方針を合意し、恒久修正とPC検証まで行う。実機での試行錯誤を繰り返さない。
Canvasのネイティブ解像度とcamera zoomを維持し、情報ウィンドウを開く前の通常画面を対象とする。

- ブランチ: `investigate/v0.61-mobile-performance`
- バージョン: 初回 `0.61.0`、計測実装 `0.61.1`、採取結果に基づく改善 `0.61.2`、画像欠落修正 `0.61.3`、実機確認後の計測撤去 `0.61.4`。
- 今回の成果: 測定結果、原因の根拠、改善計画、合意後の修正。
- 恒久的な修正範囲は調査結果を提示して合意する。

## スコープ

1. 描画、シミュレーション、DOM更新、入力、画像読み込み・保持の実装を調査する。
2. ローカルの本番ビルドで基準計測を行う。
3. 負荷条件と処理群を個別に変える比較実験を行う。
4. 根拠のある原因候補、改善案、優先順位、再検証方法をまとめる。
5. 調査用スクリプトやローカル計測手段を必要な範囲で整える。
6. 通常URLで表示する実機計測画面、条件比較、結果JSONの保存を実装する。測定は「測定開始」から行う。
7. PC検証後、通常URLへ測定版を一度公開する。未一般公開のため別URLを作らないとの追加指示に従う。
8. 採取結果を受けて追加合意した画像の事前生成と段階選択を実装する。測定画面・JSON保存は維持する。
   元画像を残し、表示先の物理画素数に足りる画像を選ぶ。実機での一括縮小生成を製品の描画経路へ入れない。
9. 実機での速度・画質・画像欠落の確認後、オーナーの指示により公開アプリの測定画面・JSON保存・比較実験と計測フックを撤去する。
   画像の事前生成・段階選択と静止プレビューの再描画は維持する。

## 対象外

- 未合意の恒久的な最適化、画質・ゲーム仕様の変更。
- 結果の自動送信、Canvas解像度削減、camera zoom変更、情報ウィンドウの最適化。
- 調査のための繰り返しの実機確認・公開。
- GameWorksOAKの変更。共通側に問題があれば根拠と必要な対応を報告する。
- PCの結果だけを根拠としたモバイル実機の改善保証。

## 調査・実装方針

### 1. 実装調査

- 初期読み込みの遅さ、継続的な低フレームレート、時間経過後の悪化、操作時の停止を分ける。
- 各ループの呼出頻度、チップ数による計算量、繰り返しの画像処理、DOM更新を追う。
- 一時停止中の処理、タイトル演出の停止・破棄、試験再開始時のリソース解放も確認する。
- 疑わしい構造の列挙で終わらず、次の計測で検証する項目と対応づける。

### 2. PCでの基準計測

- ビルドしたゲームをローカルで配信し、実ブラウザーで測る。
- コミット、ゲーム版、共通ライブラリの版、ブラウザー、OS、CPU/GPU、画面寸法、画素密度を記録する。
- 背景タブにせず、画像読み込み後の定常状態と初回読み込みを分ける。
- タイトル、課題選択、準備、戦闘、一時停止、情報ウィンドウ、ドラッグ・ズームを対象にする。
- 通常のフローで得られる状態を基準とし、乱数・編成・操作・チップ数を可能な範囲で固定する。
- 条件ごとに5秒のウォームアップ後、30秒の計測を3回行うことを基本とする。
- 再現が難しい場合や計測条件を変える場合は、理由と実際の条件を記録する。

### 3. 指標と比較実験

- フレーム間隔の中央値・p95・p99、33.3ms/50ms超の割合を記録する。
- 入力、更新、描画順計算、背景・パネル、チップ、演出、DOM更新の処理時間を段階的に分ける。
- 1フレームの更新回数、チップ・Hero・Enemy数、速度倍率、Canvasの内部寸法を併記する。
- 計測ログはメモリー上で件数を制限して集計し、毎フレームのconsole出力を避ける。
- 計測なし・ありの差を確認し、計測負荷が大きければ粒度や採取頻度を調整する。
- 小画面と高画素密度、標準速度と高倍率、少数と多数のチップを比較する。
- CPU負荷制限は補助条件とし、倍率を記録する。モバイルCPU/GPUの再現とは扱わない。
- 基準状態を維持したまま、描画解像度や個別の描画・更新処理を一つずつ変える。
- 更新省略などで状態が変わる実験は、短時間の同一状態比較として扱い、通常プレイ性能と区別する。
- JSの描画呼出時間だけでGPU・ラスタライズ負荷を断定しない。フレーム間隔と条件変更の結果も照合する。
- 時間経過・再開始で悪化する場合は、オブジェクト数、イベント・DOM・画像の保持を追加調査する。

### 4. 分析と改善計画

- 各候補を「実測で支持」「実測で支持されない」「PCでは未確定」に分ける。
- 数値、条件、再実行手順を残し、比較実験による改善量と通常動作時の負荷割合を示す。
- 優先順位は寄与の大きさ、変更リスク、画質・操作・ゲーム進行への影響で決める。
- 原因を特定できなくても、実施済みの切り分けと残る不確実性、次の具体的な調査を示す。
- 改善後も同じ条件で比較できるよう基準結果と手順を保存する。
- 恒久修正後はPCで性能比較・回帰確認を済ませ、通常のマージ・push・公開後に実機で最終確認する。
- 追加合意した一度の実機採取で通常画面の描画条件を比較し、原因候補を絞る。

## テスト・検証方針

- 計測や集計のコードを追跡対象として追加する場合は、その責務に応じたテストを追加する。
- 調査用の処理省略や条件変更を通常のゲーム動作へ混入させない。
- 自動テストに不安定な実時間の性能閾値を直接持ち込まず、同じ環境・条件での比較を使う。
- 対象テストを実行し、ブラウザーに関わる追跡対象を変更した場合は関連するブラウザー検証も行う。
- 実装終了草案の前に `npm.cmd test` と `npm.cmd run build` を実行する。文書・調査のみでも省略しない。
- コマンド、結果、失敗の調査内容と対応理由を実装報告へ記録する。

## 完了条件

- 調査対象と測定条件が明記され、第三者がPCで追試できる。
- 基準値と条件別の比較結果があり、仮説と実測事実が区別されている。
- 原因候補ごとの根拠、優先順位つき改善案、改善後の検証手順がある。
- PCで断定できない点が明記され、実機検証の繰り返しを前提にしていない。
- 恒久的な修正範囲を決めるための資料が揃っている。
- 追加合意した画像描画の改善と画像欠落への修正が実装され、実機での速度・画質・画像欠落についてオーナー確認が得られている。
- 最終成果物から実機用の性能測定機能を撤去し、改善を維持している。
- 全テスト・本番ビルドの結果が記録されている。
