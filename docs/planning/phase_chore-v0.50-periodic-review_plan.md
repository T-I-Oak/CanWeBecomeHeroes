# v0.50 定期見直し計画

## 開発範囲

- ブランチ: `chore/v0.50-periodic-review`
- 予定バージョン: `0.50.0`。初回の実装開始時に `package.json` と `package-lock.json` を更新する。
- Minor末尾が0になる新規開発として、文書・ソースの定期見直しを行う。
- 共通ルールと `01.branch_workflow.md` を照合し、このリポジトリの実験適用規定を優先する。
- 文書と実装の整合性、存在しない仕様・参照先、章構成を点検する。
- 未使用コード、重複、ファイルサイズ、責務分割を点検する。
- 仕様とテスト対象、ソースとテストの責務・配置の対応を点検する。
- バックログの依存関係・優先順と、オーナー検証が画面操作・見た目で1件ずつ判定できることを確認する。
- 確認した文書の不整合を修正し、必要なコード整理はゲームの挙動を維持する範囲で行う。

## 対象外

- 新規機能の追加、ゲーム仕様やバランスの変更。
- 課題選択表示、チャレンジモード、共有・公開整備など、バックログの新規機能の実装。
- 開発ルールの共通ルールへの正式採用の判断。
- GameWorksOAK側の変更。共通側は参照専用とする。
- オーナーが保留した実機検証を、担当者の判断だけで確認済みにすること。

## 実装方針

1. 共通の文書・構成・コーディング・CSS・モバイル・共通ライブラリ規定と、ゲーム固有の規定を読み、点検項目を整理する。共通側の未コミット変更を正式適用済みの規定として扱わない。
2. `docs/`、`src/`、`tests/`、`scripts/`、設定・公開データについて、参照・責務・仕様との対応を点検する。文書は100～300行を目安に読みやすさを確認し、ソースは1ファイル500行の規定に照らして確認する。
3. 未使用候補は動的参照、HTML・CSS、データ経由の参照とテスト・開発用入口を確認してから削除を判断する。分割は責務に基づき、行数だけを理由に機械的に行わない。
4. 文書は現行の意味と構造に合わせる。ゲームの挙動を変える必要がある問題は、本計画で修正せずバックログへ記録する。
5. ソースを整理した場合は関連テストの配置と責務も整え、挙動維持を確認する。新たなテストは必要な回帰検証に限定する。
6. バックログの新規要望と実装済みのオーナー検証を照合する。既存の判断を保持し、判断が不明な項目を独断で完了・却下しない。
7. 点検範囲、発見事項、修正内容、対象外として記録した問題を実装報告に残す。

## 検証方針

- 変更した責務に対応する `tests/spec/` と `tests/implementation/` の対象テストを実行し、コマンドと結果を記録する。対象テストがない文書修正などは、その理由と参照確認の結果を記録する。
- 文書内のローカル参照先と、修正した構成・責務の説明を実ファイルと照合する。
- ソースやテストを分割・移動した場合は、import先と関連する開発用入口も確認する。
- 実装終了草案の提示前に `npm.cmd test` と `npm.cmd run build` を実行する。文書・設定のみの変更でも省略しない。
- 失敗時は原因を調査し、今回の変更が原因なら修正して再実行する。既存または範囲外の問題は根拠と未修正の理由を記録する。
- 画面操作・見た目でオーナーの判断が必要になった場合は、実装中にバージョン、理由、手順、期待結果を項目ごとに提示し、判断を得て記録する。必要項目がなければ、その理由を記録する。

## 完了条件

- 開発ルール、文書、ソース、テスト、バックログの点検範囲と結果が記録されている。
- 確認した文書の不整合と、挙動を維持するコード整理が完了している。
- 新規機能やゲーム仕様変更が混在しておらず、範囲外の問題はバックログに記録されている。
- 対象テスト・全テスト・本番ビルドのコマンドと結果が実装報告に記録され、失敗があれば調査結果と扱いが明確になっている。
- 必要なオーナー検証の判断と対応が記録され、未回答や未対応のフィードバックがない。保留はオーナーが明示した項目だけである。
- スコープ、予定バージョン、ブランチ名の変更が必要な場合は、反映前にオーナーの再合意を得ている。
