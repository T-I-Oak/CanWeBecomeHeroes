# 共通部開発担当への依頼: フェーズ開発ルールの正式化

## 目的と担当

CanWeBecomeHeroesで実験適用している開発ルールを、GameWorksOAKの共通ルールに正式採用する。
共通部担当は共通文書を更新し、ゲーム担当へ変更内容のレビュー依頼を作成する。
資料の受け渡しはオーナーが行う。ゲーム担当は共通側を編集しない。
レビュー指摘があれば共通部担当が修正し、再レビューを依頼する。
共通ルールの確定・正式反映後に、ゲーム担当がローカルの重複規定を整理する。

## 昇格する規定と受入基準

### R01: フェーズ判定と責務

- 正式指示「フェーズを開始してください」と短縮指示「フェーズ開始」は、現在ブランチと保存済みの引継ぎ書から判定したフェーズを開始する指示とする。
- 原文の「次のフェーズを開始してください」「次フェーズを開始する指示」という表現は、この定義へ修正して共通化する。引継ぎ書の「次に開始するフェーズ」は開始対象そのものを示す。
- `master` で引継ぎ書なしは計画。開発ブランチで引継ぎ書ありは、記載された実装・レビュー・マージを実行する。
- `master` に引継ぎ書がある、開発ブランチにない、未知のフェーズ、ブランチ不明は異常。推測せずオーナーへ判断を依頼する。
- 未コミット差分の有無でフェーズを判定しない。担当AIを固定せず、原則は新しいセッションで開始する。
- 各フェーズの責務を越えない。レビューはソースを変更せず、修正が必要なら実装へ戻す。

### R02: 承認と引継ぎ書

- 非マージフェーズは、確認→フェーズ宣言と停止→開始合意後の実施→引継ぎ書草案提示と停止の順序を守る。
- 計画では、スコープ・対象外・完了条件・予定バージョン・ブランチ名を提案し、明示合意後に合意した名前でブランチを作成する。
- 開始合意・開発内容への合意・終了草案承認は別。質問や調査指示を合意と扱わない。スコープ・バージョン・ブランチ名の変更には再合意を得る。
- 草案表示後の `ok` はその草案の承認。承認前に引継ぎ書を更新せず、承認された草案と同じ内容だけを保存する。
- 保存・終了コミットと確認後に完了を報告し、コミットIDと保存した引継ぎ書の全文を示す。
- 引継ぎ書の必須項目は「次に開始するフェーズ」「直前のフェーズで完了したこと」「次担当への注意事項」。状態を他の成果物へ重複記載しない。
- 次フェーズは計画→実装→レビュー。レビューで未解決指摘・要修正フィードバックがあれば実装、なければ判断・対応・明示保留の記録を確認してマージ。
- マージは追加の承認ステップなし。完了時はマージ・pushの確認結果と引継ぎ書の削除を報告する。

### R03: バージョンとブランチ

- 初回の実装開始時に、計画で決めたMinor・Patch 0を設定する。新規開発はMinorを上げ、同一タスクのフィードバック対応はMinorを維持する。
- 再実装・レビュー差し戻し・オーナーフィードバック対応で実装を再開する場合はPatchを1上げる。
- 実装終了草案が承認されず、変更に着手する場合もPatchを1上げる。同じ修正版の個々の指摘・コミットごとには上げない。
- 再提示した草案が再び差し戻された場合は、次の修正着手時にもう1上げる。
- 計画・レビュー・マージへの移行だけでは更新しない。文書・設定だけの実装もこの規定の対象。
- 確認依頼に記載するバージョンは設定・画面と一致させる。ブランチ名は `[prefix]/v[Major].[Minor]-[description]`、Patchは含めない。
- Majorの明示指示要件や利用者向け更新履歴の運用は維持する。

### R04: 成果物、コミット、削除

- `docs/planning/phase_<branch>_plan.md`・`_implementation.md`・`_review.md` と `phase_handover.md` を使用する。ブランチ識別子はファイル名に安全な表記へ置換する。
- 実装報告には計画への実装結果、変更箇所、対象・全テスト・ビルド、失敗調査、提示したオーナー検証・判断・対応・保留理由を記録する。
- レビュー報告には未解決指摘の有無を明記する。未解決指摘なしを記録できるのはレビュー実施担当だけ。
- `phase_` はignoreせずGit追跡する。`dev_`・`tmp_` のignore運用は維持する。既存の開発成果物は `dev_` から移行し、引継ぎ書の旧名を残さない。
- 非マージフェーズの終了草案承認後に、変更一式・成果物・承認済み引継ぎ書をコミットする。1ファイルごとの個別コミットを必須としない。
- 対象を明示して通常の `git add` を使用し、無関係な差分・一時検証ファイル・`dev_`・`tmp_` を含めず、ignore対象を強制追加しない。
- コミット前にステージ差分、後に `git log -1` と `git status --short --branch` を確認する。失敗や追跡対象の残差分があれば完了としない。変更なしは空コミットを作らずHEADを報告する。
- 計画・実装・レビューの終了コミットはローカルに記録する。過去の終了コミットを推測して分割・履歴改変しない。
- マージ前に全フォルダーの `dev_`・`tmp_`・`phase_` のファイルとフォルダーを、追跡・未追跡・ignore対象を含め削除する。
- 削除前に一覧・絶対パス・リポジトリ内であることを確認し、他リポジトリと `.git` は対象外。削除後に再走査し、追跡済み削除をコミットしてからマージする。

### R05: オーナー検証とバックログ

- 必要な検証は実装中、確認可能な時点で1件ずつ提示する。各項目に一意のIDを必ず付与し、理由・操作・期待結果・確認バージョンとともに示す。判断・フィードバック・対応記録・再提示・バックログでも同じ項目は同じIDを使用し、フィードバックの対象を明確にする。レビューまで提示を待たない。
- 「項目却下」は対象から除外。「項目確認済み」は完了。どちらもバックログに同じ項目があれば削除する。
- 「項目でフィードバックあり」は内容を判断し、範囲内の修正を実装中に行って再提示する。発言だけで一律に不合格としない。
- 「現時点で確認しない」とオーナーが判断した項目だけを「オーナー検証」へ残す。レビューでの確認指定もこの保留に含める。
- 「オーナー検証」へ項目を追加するときは、追加した項目のID・確認内容・追加理由をチャットで明示する。別開発の判断を非同期に反映する場合も同じとし、ファイルの更新だけで済ませない。この通知はオーナーによる保留判断を代替しない。
- 未回答を保留と扱わない。判断・対応前に終了草案を出さず、独立のオーナー検証フェーズを作らない。回答待ちでも保存済み引継ぎ書を進めない。
- レビュー担当は却下・確認済みを再依頼せず、レビューでの確認指定に従う。新規検証項目も理由を示して同じ4判断を受け、要修正なら実装へ戻す。
- 新規要望・スコープ外指摘は依存関係と優先順に「要望・バグ指摘」へ記載し、オーナー検証に混ぜない。同欄を新規開発の全体作業計画の唯一の台帳とする。
- スコープ外のブロッキングバグはオーナーが修正を指示した場合だけ直ちに対応する。報告・バックログ追加だけを修正指示としない。
- 別開発の検証判断も非同期に記録へ反映する。スコープ外の差し戻し実装は指示を待つ。同一タスクの差し戻しは元のMinorを維持する。

### R06: 実装検証

- 対象テストを随時行い、終了草案前には全テストと本番ビルドを実行する。文書・設定のみでも省略しない。
- 対象テスト・全テスト・ビルドのコマンドと結果をそれぞれ実装報告に残す。
- 失敗は草案前に調査し、今回の範囲・変更が原因なら修正・再実行する。既存または明らかな範囲外の失敗は調査と今回直さない理由を記録する。
- 要求仕様とテストの矛盾はオーナーへ確認し、都合よくテストを変更しない。レビューは報告と差分を照合する。

### R07: マージ・pushと共通ライブラリ

- マージの開始指示には `master` へのマージと `git push origin master` を含め、pushの追加承認を求めない。
- ゲームのマージ着手前とpush直前に、次のコマンドで共通側を確認する。

```powershell
git -C ../GameWorksOAK status --short --branch
git -C ../GameWorksOAK branch --show-current
git -C ../GameWorksOAK rev-parse HEAD
git -C ../GameWorksOAK ls-remote origin refs/heads/master
git -C ../GameWorksOAK diff --name-only HEAD -- src/lib
git -C ../GameWorksOAK ls-files --others --exclude-standard -- src/lib
```

- 共通側のHEADがmaster、HEADとremote masterのIDが一致し、参照する `src/lib` に未コミット・未追跡変更がないことを合格条件とする。
- remote追跡表示だけでは判定しない。コマンド・リモート照会の失敗は未確認とする。
- 合格ならゲーム担当の確認だけで完了し、共通部担当・オーナーの別途承認を求めない。不合格・失敗時だけ状態と必要対応を報告して解消を待つ。
- 共通側の文書変更も報告するが、文書変更だけをライブラリ未公開と扱わない。ゲーム担当が共通側をcheckout・編集・merge・pushして解消しない。
- 解消によって検証時のライブラリが変わった場合はゲーム側の全テスト・本番ビルドを再実行する。
- push後は当該リポジトリの `git rev-parse master` と `git ls-remote origin refs/heads/master` のID一致を確認する。
- push失敗ではローカルのマージを保持して調査し、force pushしない。反映未確認なら完了とせず、解消不能ならマージ済み・push未完了と原因を報告する。

### R08: 定期見直し

- 新規開発でMinor末尾が0になる10回ごとに、その版を文書・ソースの見直し専用にする。同じMinorのPatchでは開始しない。
- 機能実装・新規仕様変更を同じ見直しブランチへ混ぜない。
- 開発ルール、存在しない仕様・章・参照、テストと仕様・配置、未使用コード・文書整合・ファイルサイズ、バックログの粒度・依存関係・優先順を点検する。
- 文書分割・コーディングは既存共通ガイドに従い、点検範囲・修正・全テスト・ビルド結果を実装報告とチャットへ記録する。
- 見直し範囲外の不具合は要望・バグ指摘へ記録する。

## ゲーム固有の表現の扱い

- 「タイトルと倉庫左下」のバージョン表示位置はこのゲームの具体例。共通では各プロジェクトの確認画面に一般化し、ゲーム側に具体的な場所を残す。
- 「ゲームの画面操作・見た目」は各プロジェクトの利用者が操作・確認できる単位に一般化する。
- CanWeBecomeHeroes固有の検証IDやゲーム機能の仕様は共通へ移さない。
- 共通部とゲーム担当の責務は区別する。共通部担当自身のリポジトリ更新に、ゲーム担当向けの共通側参照専用規定を誤適用しない。
- これら以外に原文の意味を変更する必要があれば、変更点と理由をレビュー依頼に明示する。

## レビュー依頼に含める情報

1. 共通側のブランチ名、基準コミット、レビュー対象コミット、変更ファイル一覧と差分の確認方法。
2. R01〜R08それぞれの反映先ファイル・節と、原文から一般化した箇所。オーナー指定の開始指示の表現修正、オーナー検証IDの必須化、追加時のチャット明示要件も含める。
3. 旧規定との競合をどう解消したか。特にコミット単位のPatch、dev_計画書、1ファイル個別コミット、実装済み項目の一律検証待ち移動、共通部担当の公開確認必須を確認する。
4. 共通側の全テスト・本番ビルドの実行コマンドと結果、文書参照・追跡設定の確認結果。
5. 未解決事項と、ゲーム担当に判断を求める点。再依頼では前回指摘への対応と新しい対象コミット。
6. レビュー後の正式反映時は、masterのコミットIDとremote反映確認結果をオーナー経由で伝える。

ゲーム担当はIDごとの適合・指摘を返す。指摘のある版を確定済みと扱わず、修正後の差分を再確認する。
レビュー適合と共通側の正式反映が確認できるまでは、ゲーム側のローカル規定を削除しない。
共通側の作業が終わっても、ゲーム側には別途、通常の実装終了・レビュー・マージの手順が残る。
