## 判断の目的

オーナーから、気になっているのは開始時間ではなくビルドの警告であるとの補足を受けた。
警告の原因と最小限の対応を主な判断対象とし、実行中の性能比較は補足資料として扱う。
起動を速くすることや、遅延読み込み・先読みを採用することを今回の目的とはしない。
警告上限は変更せず、画像マニフェストを静的な別チャンクへ分ける候補を追加した。
この候補では起動時の静的読み込みを維持し、入口の非同期起動方法や画面ライフサイクルを変更しない。

## 警告についての結論

Vite 7.3.6の通常ビルドで、単一のJavaScriptチャンク514.50kBが既定の500kBを超える警告を再現した。
gzip後の137.63kBではなく、minify後・gzip前のチャンクサイズが判定対象である。
ビルドエラーやゲームの動作不良を示す警告ではない。

警告への最小限の対応として、`build.rollupOptions.output.manualChunks`で
`src/chips/image-levels.json`だけを`image-levels`静的チャンクへ分ける案を推奨する。
調査用ビルドでは入口447429byteとマニフェスト67326byteになり、標準の500kB設定で警告0件を確認した。
通常の静的importを維持でき、遅延読み込み・先読み・入口の非同期起動方法の変更は不要である。
起動時の総JS量を減らす案ではなく、意味のあるデータ境界で1チャンクを分ける対応となる。
マニフェストの内容・生成処理・画像選択・キャッシュは既存のものを使用する。

現在の調査用ビルドは計測フックを含む。通常ビルドと同一のViteログ設定で、
通常構成1件・計測付き対照1件・静的分割0件の警告を記録した。
初期の性能比較ビルドはログと圧縮サイズ表示を抑制していたため、その無警告出力を解消の根拠には使用していない。
警告解消の確認では標準のinfoログと圧縮サイズ表示を有効にし、実際の警告文を保存した。

初回調査では本番適用を対象外としたが、レビューでのオーナー指示を受け、先頭のRV-STARTUP-01対応で本番へ適用した。
依存の増加でいずれかのチャンクが500kBを超えれば再び警告されるため、警告上限を上げる必要はない。

## 比較条件

通常設定による`normal`、計測フック付きの`baseline`、非同期起動方法だけを変更する`bootstrap`を対照とする。
`trial`・`records`はそれぞれの単独遅延読み込み、`both`は併用。
`prefetch`は併用にタイトル操作可能後の先読みを加える。
`compact`はマニフェストの表現縮小だけ、`combined`は遅延読み込み・先読み・表現縮小の併用。
`static`は画像マニフェストの静的なチャンク分割だけを加える。
先読み条件は即時入力と先読み完了後の入力を別に測定する。

入口`src/main.js`の`await startGame()`は、通常のゲームループが終了するまで解決しない。
共有エクスポートが入口チャンクへ残るビルドでは、動的チャンクが入口の評価完了を待ち、初回画面が開かなくなる。
予備測定でこの到達失敗を再現したため、遅延読み込み候補だけ、起動Promiseをトップレベルで待たない調査用変換を適用した。
例外はmicrotaskで再送出し、失敗を隠さない。`bootstrap`でこの変更単独の影響を区別する。
本番への採用時も入口の非同期境界と循環依存の解消が必要であり、import文の置換だけでは成立しない。

マニフェスト候補は画像パス・元寸法・段階の寸法を行配列へまとめ、共通のパス接頭辞から段階パスを復元する。
制作元ハッシュなど実行時に参照しない情報は配信用の表現へ含めない。
元のJSONは変更せず、元寸法・全段階の順序・寸法・パスを全件照合した。
ScaledImageの段階選択、キャッシュ、失敗時の原画使用は共通の既存処理を使用する。

全比較ビルドで同一のモジュールIDをチャンク間に重複配置していないことを確認した。

両方を遅延化しても起動側には100モジュールが残る。
Rollupのminify前`renderedLength`では、画像マニフェスト72573byte、敵文言定義22966byte、

これらはminify後のチャンク内の厳密なbyte寄与ではなく、依存が残る箇所の目安である。
GameTextRepositoryは起動時に15個の文言リソースの読み込みを待つため、JS分割だけではこの待ちを取り除けない。

マニフェスト単独の縮小は非圧縮で50361byte、gzip参考で2713byteの削減となる。
パスの反復はgzipで圧縮されやすく、非圧縮での削減率を圧縮配信へそのまま当てはめられない。
一方、復元コードの実行負荷が加わるため、通信量の減少だけを解析・実行時間の改善と解釈しない。

## 測定条件と指標

ブラウザーはWindows上のheadless Chrome 155.0.8059.86。
1024×768 CSS px・DPR1、CDP CPU4倍制限、CDP latency=40ms、
下り2621440byte/s・上り1310720byte/s、HTTP非圧縮・max-age=3600のローカル配信。
各条件・操作・キャッシュについて3反復する。
日本語・初期2職・通常試験クリア済み・全チュートリアル既読・seed54を毎ナビゲーションで設定する。
ユーザーの通常ブラウザーの保存データは使用しない。

冷えたキャッシュは新しいブラウザーコンテキスト、再訪は同じコンテキスト内の次のナビゲーションとする。
初回と再訪の間にもメンバー・レコード等を実際に表示するため、再訪はそれらのアセットとコードキャッシュも温まった状態となる。
ブラウザープロセス・OSファイルキャッシュまで毎回初期化する条件ではない。
候補の順番は固定であり、時間経過やPCの背景負荷による偏りを完全には排除できない。
測定中に別のビルド・テストは並行実行しない。

タイトル時刻はナビゲーション開始から同期初期化完了まで。
直後のMutationObserverでタイトルのボタンを実際にクリックし、対象画面への到達を確認する。
通常ビルドはDOM生成の観測時刻、計測フック付きはshow内のmarkを使用するため、わずかな境界差がある。
入力待ちはクリックからレコード／メンバー選択のDOMが生成されるまでを測る。
描画フレームの提示完了や全画像のdecode完了を表す指標ではない。
続けて実際のタブや開始・課題選択を操作し、通信エラー・DOM画像の欠損も検査する。
開始劇の固定演出はスキップし、スキップ入力から課題選択の生成までを別に測る。
ユーザーがメンバーや演出を見ている時間を遅延読み込みの待ちへ加算しない。

通信量はNavigation/Resource TimingのtransferSizeを使用し、完了済みリソースだけを境界時刻で集計する。
未完了の画像等はタイトル時点の集計に入らず、その後の画面表示・先読みの取得と区別する。
HTTPヘッダーを含むtransferSizeと、キャッシュにも値が残るencodedBodySizeを混同しない。
リソースのURL・開始時刻・完了時刻・サイズはJSONへ記録し、取得順序と追加通信を確認できる。
約1036kBのロゴは、通常構成ではタイトル境界前、速くタイトルへ到達する候補では境界後に取得が完了する場合がある。
したがってタイトル時点の総通信量の差を、そのまま総ダウンロード量の削減として扱わない。
ナビゲーション→エントリーJS・CSS→文言15件の取得→タイトル初期化という順序を確認した。
遅延化したチャンクは操作時、先読み条件ではタイトル初期化後に取得される。

トレースは`devtools.timeline,v8,blink.user_timing,disabled-by-default-v8.compile`を採取する。
解析・コンパイルと、EvaluateScript/v8.evaluateModule/FunctionCall/RunMicrotasksの実行を別集計する。
待機専用のparseOnBackgroundWaitingは除外し、同じスレッド・カテゴリ内の入れ子区間は和集合で集計する。
カテゴリ間の重なりは残るため両者を加算しない。スレッド間は加算する。
トレースに記録されない処理は含まず、コンパイル関連イベントの経過時間は純粋なCPU時間とは限らない。
ブラウザーへ注入した計測補助の処理も指標に含まれる。
ページ全体のTaskDurationや総経過時間をJavaScript解析時間として使用しない。

採取時点が異なり、フック・ブラウザー内部のコードキャッシュ・背景負荷を完全に分離する対照ではない。
補助コードが完全に無負荷であるとは扱わず、とくに再訪時の小さな差から改善率を主張しない。
静的分割についても、警告解消と動作維持を採用判断の根拠とし、起動性能の改善を必須条件としない。

## 判断・残る課題

初回調査の変更は調査用コード・手順とバージョンだけであり、利用者向けの見た目・ルール・読み込み仕様は変更していない。
実機での速度改善や画質変更のオーナー検証は新規に依頼していない。
オーナーからの「警告が気になる」という補足は計画と推奨案へ反映した。
初回調査でバックログ先頭を「静的分割の本番適用判断」へ更新し、RV-STARTUP-01の本番対応後に削除した。
実機・公開配信での性能保証は今回に含めない。

遅延読み込みは警告を解消できるが、入口の非同期境界の変更と初回入力の待ちが必要である。
先読みは完了後の待ちを抑える一方、直後の入力では待ちが残り、レコードだけ使う場合にもゲーム用JSを取得する。
両遅延化のレコード使用後JS約316kBに対し、先読みありでは約520kBとなった。総量削減として採用しない。
マニフェスト縮小も単独で警告を解消するが、復元コードと生成表現を追加する必要がある。
警告対応だけなら、既存JSONをそのまま静的分割する案のほうが変更範囲を小さくできる。
