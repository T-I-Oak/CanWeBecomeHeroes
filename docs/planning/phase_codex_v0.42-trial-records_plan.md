# 試験ランの記録・統計・クリアー履歴とアチーブメント

## 開発単位

- バックログ「3. ゲームランの記録と結果を設計する」のうち、試験ランとアチーブメントの永続化、タイトルからの閲覧、ラン終了時の獲得表示を扱う。
- ブランチ: `codex/v0.42-trial-records`。
- 現在のバージョンは `0.41.0`。初回実装開始時に `package.json` と `package-lock.json` を `0.42.0` にする。計画段階では更新しない。
- Minor末尾は0ではないため、定期見直しは今回の対象ではない。
- 運用は `01.branch_workflow.md` を優先し、それ以外はGameWorksOAKの共通ルールに従う。共通リポジトリは変更しない。

## 現状と接続先

- `HeroProgressRepository` は解放済み職業と `hasClearedTrial` を共通 `DataManager` のゲーム名前空間へ保存している。
- `TrialRunFlow` はランの終了遷移時に `onRunCompleted` を1回呼ぶ。`TrialSession` はその通知で `TrialRunResultModal` を表示する。
- `TrialRunResult` は終了メンバーと発行日を保持する表示用スナップショットで、永続履歴ではない。
- `TitleMenu` のレコード領域は空表示のみ。チャレンジのコマンドは存在するが、`GameApp` は試験以外の開始を処理していない。
- `BattleSystem.contributionPoints` はギルド消費後の所持値である。累計獲得ptと混同しない。
- `GameLog` はメモリ内のイベント履歴、`FlowLog` は通知表示を担う。今回これらを永続履歴として保存しない。

## 開発スコープ

### 終了記録

- 試験の合格・期限切れ終了時に、結果表示に用いる終了情報と同じ時点のスナップショットを保存する。
- 各記録は記録ID、モード（試験）、開始・終了日時、合格／不合格、到達ステージ番号・種類、開始Heroと終了メンバーのHero／職業ID、ゲーム内経過ticks、累計獲得貢献pt、そのランで初獲得・更新したアチーブメントIDと達成値を持つ。
- 累計獲得ptは敵撃破による獲得を加算する。ギルドで使っても減らない。所持ptを使った代用集計はしない。
- 開始Hero・終了メンバーは後から変更されない値として記録する。名前・翻訳文・アセットや生きたゲーム実体は保存しない。
- 終了通知の重複で同じランを再集計しない。結果画面から戻る前に保存する。
- ページを閉じた途中ランは終了記録に含めない。途中の盤面や再開可能な状態を保存しない。

### 永続化と既存データ

- 共通 `DataManager` の既存ゲーム名前空間を使い、ゲーム側の記録用Repositoryに読込・保存・集計の責務を置く。
- 統計は終了済み試験数、合格数、不合格数、累計獲得pt、最高獲得ptとする。終了履歴は新しい順の直近50件を保持し、通算統計は履歴の削除で減らさない。
- クリアー記録として初回合格日時・直近合格日時・合格回数を保持する。直近50件から古い合格が外れても保持する。
- 記録保存形式の版と履歴保持上限を明示し、形式の初期化・移行をテストする。
- 記録機能導入前の解放状況・初回クリアーフラグ・言語・設定・チュートリアルを維持する。既存のクリアーフラグから過去の日時や回数を作らない。旧データで日時不明の場合はその旨を表示する。
- 保存失敗は環境エラーとして扱い、保存成功と誤表示せず、タイトルに戻れる状態と再試行手段を設ける。再試行でも二重集計しない。

### アチーブメント

- 要求資料の「ゲームランモード」に従い、基本は両モード共通とし、必要な条件だけモードを限定する。今回の判定元は実装済みの試験ランと解放状況である。
- アチーブメントの具体的な種類・名称・獲得条件・達成値・判定時点は、実装フェーズでオーナーと一緒に検討して決める。決めた内容に基づいて判定と必要な記録項目を設計する。この計画書には具体例を記載せず、担当者の案をオーナーの意向や確定仕様として扱わない。
- 確定した条件と値の単位をカタログで一意に定義し、表示文言と判定処理を分離する。獲得済み状態は履歴保持上限で失われない。
- ラン終了時に終了記録・統計・アチーブメントを同じ保存データへ反映する。保存再試行で二重獲得・二重更新を起こさない。
- 既存データからの獲得状態の移行可否は確定した条件に基づいて決める。保存済みデータで確認できない達成・日時・数値を推測しない。移行を新しいランの獲得通知として表示しない。
- タイトルのレコードに確定した全項目の名称・条件・獲得状態を一覧表示し、仕様で定めた達成値も表示する。未獲得の条件も読めるようにする。
- `TrialRunResult.achievements` に当該ランの初獲得・更新結果を渡し、合格・不合格の両結果画面に表示する。保存失敗時は今回達成した内容と保存状態を区別する。
- 名称・条件・獲得／更新・日時不明の文言は日英対応する。今回アチーブメント専用の画像生成は行わず、既存UIと文字で判別できる表示を使う。
- 未実装のチャレンジに依存する条件は、そのモードの開発時に扱う。

### タイトルのレコード

- レコード領域に解放済みHero、通算統計、クリアー記録、アチーブメント一覧、終了履歴を表示する。
- 履歴では終了日時、結果、到達ステージ、経過ゲーム内時間、獲得ptと参加メンバーが読めるようにする。
- 新規データでは未記録状態を表示する。既存クリアーフラグと新しい履歴がない状態も区別する。
- Hero名・結果・ラベルは `GameTextRepository` 経由で解決し、日英切替時も開いている領域を更新する。
- PC・タブレット・スマートフォンの縦横画面で内部スクロールでき、閉じる操作が画面内に収まるようにする。

## 対象外

- チャレンジ（エンドレス）のゲーム進行と終了結果画面。
- 合格／不合格の正式画面への全面的な差し替え。今回の結果画面変更はアチーブメントの獲得・更新と保存状態の表示を対象とする。
- ログ履歴パネルと情報ウィンドウリンク。FlowLogの操作化。
- 途中セーブ・再開、記録共有、外部送信、ランキング、記録削除機能。
- 戦闘バランス、加入劇、公開メタデータ、共通開発ルールの正式適用。
- Hero解放のタイミング変更。要求資料の「遭遇時解放」と現行の「合格時にメンバー解放」は一致していないため、仕様差をバックログに明記し、今回の記録機能に混ぜて変更しない。

## 実装方針

1. アチーブメントの具体的な内容をオーナーと一緒に検討して決める。記録のデータ契約と保存・二重集計防止・履歴保持・累計獲得pt・決めたアチーブメント判定の仕様を先にテストで定義する。
2. ラン単位の開始情報と累計獲得ptを収集し、終了時のアチーブメント判定と保存へ接続する。ゲームルールと保存・表示を分離する。
3. タイトルのレコード表示と結果画面の獲得表示を責務に応じたモジュールへ分離し、既存のModal・CSS・多言語の仕組みを使う。
4. 保存失敗と再試行、旧データ、言語変更、短い画面の表示を検証する。
5. 確定した利用者向け仕様を `docs/requirements/`、実装構造を `docs/specifications/` と `docs/architecture/` に記録する。バックログは完了範囲と後続作業が分かるよう整理する。

## 完了条件と検証

- 合格・不合格の各ランが1回ずつ保存され、再読込後に同じ履歴と統計を表示できる。
- ギルド消費を含むランでも、獲得ptの記録と統計が消費前の累計に一致する。
- 同じ記録IDの再通知・保存再試行で履歴と統計が増えない。
- オーナーと確定した各アチーブメントの達成・未達成・再判定が条件どおりである。更新を持つ仕様では更新・非更新も検証する。
- 各ランの結果画面と永続履歴に同じ獲得・更新内容が表示される。合格・不合格による判定の違いは確定仕様に従う。
- 履歴が50件を超えても獲得状態と仕様で定めた達成値を維持する。旧データの移行は確定条件と確認可能なデータに基づき、日時や数値を捏造しない。
- 51件以上の終了後に履歴は直近50件、通算統計と初回クリアー情報は全終了分を維持する。
- 旧データの解放状況・クリアーフラグ・設定が失われず、未知の過去記録を生成しない。
- 途中離脱を合格・不合格として記録しない。新規データ、日時不明の旧データ、保存失敗を適切に表示する。
- 対象の単体・結合テストを `node --test` で実行し、終了遷移から保存・表示まで確認する。
- 終了草案の提示前に `npm.cmd test` と `npm.cmd run build` を実行し、コマンドと結果を実装報告へ記録する。
- ブラウザでレコード開閉、日英切替、再読込、PC・タブレット・スマートフォン相当の表示を確認する。
- 実装中にオーナー検証を1件ずつ提示する。予定項目は「合格履歴の表示」「不合格履歴の表示」「解放済みHeroの表示」「アチーブメント一覧と条件の表示」「結果画面の初獲得表示」「結果画面の記録更新表示」「言語切替」「スマートフォンでの閲覧と閉じる操作」。具体的な手順・期待結果・更新済みバージョンを提示し、各判断と対応結果を記録する。
- オーナー検証は未回答を保留扱いせず、明示された保留だけをバックログへ記録する。

## 後続の作業

バックログの同段階に、チャレンジ実装とその成績表示・固有アチーブメント、ログ履歴パネル、正式結果画面への差し替えを残す。今回の記録とアチーブメント定義にはモードを持たせるが、未実装モードの成績・終了条件は先取りしない。
