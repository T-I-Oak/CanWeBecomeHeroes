# フロートログ性能改善の計画

## 合意した範囲

- 予定バージョンは0.76.0。ブランチは`perf/v0.76-flow-log-optimization`。
- `PERF-01`は採用未決定。通常ダメージ・ミスのフロート通知を抑えた比較用試作を先に用意し、実ゲームで違和感を確認してオーナーと相談する。今回の計画合意を通知抑制の採用承認と扱わない。
- オーナーの明示判断を得るまで、通知抑制を通常実装へ確定反映しない。履歴は比較時も維持する。会心・撃破等の通知も維持する。
- `PERF-05`はフロート表示時間をJavaScriptで決定し、既存CSS変数へ渡す。getComputedStyleの読戻しとCSS側の時間二重定義を除く。現在の時間・ランダム補正・位置・終了削除を維持する。
- PERF-01を不採用にした場合もPERF-05は独立して進める。別の通知削減案を採る場合は、変更内容を相談し、範囲変更の合意を得る。

## 対象外

PERF-02〜04、HUD・背景、解像度変更、待ち行列の新設、保存形式変更、ゲーム内文言変更、共通リポジトリ変更、既存の保留中オーナー検証6件。

## 実装方針

1. 実装開始時にpackage.jsonとpackage-lock.jsonを0.76.0へ更新する。
2. 通常表示と通知抑制を同じ戦闘条件で比較できる一時検証手段を用意する。切替・計測用の処理は通常ビルドへ含めず、tmp_成果物として管理する。
3. 通常戦闘の疎な通知と多い通知の両方で、攻撃やミスの把握、戦闘の手応え、残る通知の読みやすさをオーナーに確認してもらう。勇者・敵双方を対象にし、確認バージョン、手順、確認理由、期待結果を一意ID付きで提示する。
4. 採用・不採用・修正案の判断と根拠を実装報告へ記録し、判断に従って通常ソースを反映する。未回答を採用や保留と扱わない。
5. FlowLog.jsとflow-log.cssの時間定義を整理する。現行のinfo=6秒、luck=9秒、unluck=7秒、system.warning=10秒、その他=6秒と、0.85〜1.15倍の補正を維持する。未使用のhero/enemy.warningは現行どおり6秒とし、warning一律10秒にはしない。
6. 必要な仕様書・バックログを更新する。通知抑制を不採用にした場合も、オーナー判断を記録し、採用済みと記載しない。

## 検証と完了条件

- CombatActionLog・GameLog・FlowLog・履歴の関連テストを確認し、勇者・敵の通常／ミス／会心／撃破の通知と履歴を検証する。期待値はオーナー判断に従う。
- 実ブラウザーで主体・level・代表乱数値の表示時間、位置、言語更新、animationendによる削除を確認する。getComputedStyleの読戻しがなくなることを確認する。
- PERF-01の体験確認は通常実装への採用判断より先に行う。PERF-05の見た目維持もオーナー検証として提示する。
- 変更前後を同一条件の往復比較で測定し、ログ発行CPUとフレーム間隔を分けて報告する。PERF-01採用時は現行→通知抑制→時間一元化の効果を区別し、不採用時は現行と時間一元化を比較する。測定中は他のテスト・ビルドを並行実行しない。
- 調査元はコミット8615200の性能比較資料・レビュー。既存のCPU削減率を今回の完成実装の実績へ転用せず、Android/Vivaldiの症状解消をPC測定から断定しない。
- `npm.cmd test`、`npm.cmd run build`、`npm.cmd run test:browser`を実行し、対象テストとともにコマンド・結果を実装報告へ記録する。失敗時は共通手順に従って調査する。
- タイトルと倉庫のバージョン表示が設定と一致すること、比較用処理が通常ビルドへ混入しないことを確認する。
- 必要なオーナー検証の判断と対応を記録してから終了草案を提示する。明示的に「現時点で確認しない」とされた検証だけをバックログへ記録する。ただしPERF-01の採用判断が未決定なら、通知抑制を確定反映して終了しない。
