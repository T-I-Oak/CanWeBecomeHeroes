# v0.70 定期見直し計画

## 目的と合意内容

共通ワークフローの「定期見直し」に従い、Minor末尾が0となる版で文書とソースを点検し、現在の仕様と動作を維持したまま保守に必要な整理を行う。

- ブランチ: `chore/v0.70-periodic-review`
- 予定バージョン: `0.70.0`
- 基準バージョン: `0.69.1`
- 計画時にはバージョンを変更しない。初回実装開始時に `package.json` と `package-lock.json` を更新する。
- フェーズ開始と開発内容について、オーナーの明示合意を得ている。

## スコープ

| 点検領域 | 対象と確認内容 |
| --- | --- |
| 開発ルール | プロジェクト固有のブランチ作業フローと共通ルールを照合する。共通側の未コミット変更は正式適用済みとして扱わない。 |
| 文書 | `docs/`、`tests/` の案内、アセットの説明について、存在しない仕様・章・参照先、実装との不整合、重複、文書サイズを確認する。 |
| ソース | `src/`、`scripts/`、起動・ビルド設定について、未使用コード、責務の重複、文書との整合性、ファイルサイズを確認する。 |
| テスト | 要求文書と仕様テスト、ソースと実装テストの対応、分割・移動に伴う配置と責務を照合する。 |
| バックログ | 要望・バグ指摘の依存関係と優先順、オーナー検証の一意IDと1件ずつ判断できる粒度を確認する。 |

点検で根拠を確認できた文書の訂正、未使用コードの除去、責務に沿った分割・配置の整理を行う。行数だけを減らす整形や、整理自体を目的とした抽象化は行わない。

## 対象外

- 新機能、ゲームルール・表示要件・保存仕様の変更。
- モバイルのドラッグ対象を見やすくする改善の設計・実装。
- 成績表の既知項目判定と既知フラグの保存・表示制御。
- タグスキル上限とステータス上限の関係の変更。
- 制限環境そのものに対するブラウザーテスト終了待ちの対策。
- GameWorksOAK側のルール・共通ライブラリの変更。
- 既存の保留されたオーナー検証を、今回の点検だけで確認済みとすること。

範囲外の不具合は、内容と根拠を確認し、バックログの「要望・バグ指摘」へ依存関係・優先順に沿って記録する。追加内容と理由をチャットで通知する。仕様変更やスコープ拡大が必要なら、変更案への合意を得てから進める。

## 実装方針

1. 実装開始時にルールと作業ツリーを確認し、バージョンを `0.70.0` に更新する。
2. Git追跡対象を基に点検対象の一覧を確認する。生成物・外部依存は手書きソースと区別し、必要なら生成元と生成手順を確認する。
3. 文書の参照先、章構成、モジュールの参照元と利用経路、ソース・文書の行数を調べ、各領域の点検結果を実装報告へ記録する。
4. ソースは共通基準の1ファイル500行制限、文書は100〜300行程度の目安を踏まえ、責務に沿った分割の必要性を判断する。分割時は参照・説明・テスト配置を合わせて整える。
5. 未使用と判断する場合は、静的importだけでなく動的読込、HTML、データ、テスト、スクリプトからの利用も確認する。
6. 保存データ、ゲーム計算、画面操作の契約を維持する。変更の必要がない領域も、点検した内容と根拠を報告する。
7. 点検範囲、修正内容、範囲外の発見事項、検証結果を `phase_chore_v0.70-periodic-review_implementation.md` にまとめる。

## テスト・確認方針

- 関連テストは変更対象に応じて `node --test` で実行する。実行コマンドと結果を記録する。
- 複雑な計算・状態管理・イベント連鎖を変更する必要が生じた場合は、仕様とスコープを確認し、共通ルールに従い先にテストで挙動を定義する。
- 全テスト: `npm.cmd test`。
- 本番ビルド: `npm.cmd run build`。
- 主要フロー・本番起動: `npm.cmd run test:browser`。`tests/README.md` の実行順とWindowsでの権限申請手順に従い、テスト本体とサーバー終了の結果を区別する。
- 文書の参照先、モジュールのimport、移動したテストの配置、差分の空白エラーを確認する。
- 初回実装の設定値と、タイトル・倉庫左下のバージョン表示が `v0.70.0` と一致することを確認する。
- 失敗が出た場合は今回の変更との関係を調査する。範囲内の原因は修正・再実行し、既存または範囲外の失敗は内容・根拠・修正しない理由を記録する。
- 自動テスト成功をモバイル実機や見た目の確認済みとは扱わない。新たにオーナー判断が必要となった場合は、確認可能になった時点で一意ID、理由、手順、期待結果、確認バージョンを提示し、判断と対応を記録する。

## 完了条件

- 点検領域すべてについて、確認範囲と結果が実装報告に記録されている。
- 見直し範囲内で必要な整理を行い、仕様・文書・参照・テスト配置が実装と整合している。
- 新機能・新仕様を混在させず、範囲外の発見事項が必要に応じてバックログに記録・通知されている。
- 関連テスト、全テスト、本番ビルド、ブラウザー検証のコマンドと結果、失敗時の調査結果が記録されている。
- 必要なオーナー検証に未回答・未対応の指摘がなく、保留はオーナーの明示判断に基づいている。
- 実装報告と、次フェーズをレビューとする引継ぎ書草案を提示できる。
