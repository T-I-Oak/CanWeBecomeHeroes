# 情報ウィンドウ更新負荷の調査計画

## 合意した開発内容

- ブランチ: `chore/v0.63-information-window-performance`
- 予定バージョン: `0.63.0`。初回の実装着手時にpackage.jsonとpackage-lock.jsonを更新する。計画では更新しない。
- バックログ先頭の「情報ウィンドウ表示中の更新処理が、操作性を損なう負荷につながるかを確認し、対策の要否を判断する」を対象とする。

## 背景と確認対象

既存の[モバイル性能調査](../analysis/01.mobile_performance.md)では、情報更新を省略するとDOM・レイアウト処理と全体負荷が減った。ただし当時の画像・描画条件と現行版は異なるため、過去の数値を現行版の結果として使わない。

現行のInformationWindowManager.refreshDynamicEntriesは、実体情報を開いていてドラッグ・操作中でなければ表示層へ通知する。InformationWindowLayer.renderは全ウィンドウを構築し直してreplaceChildrenする。TrialSessionの分割更新との関係を確認し、呼出頻度と処理の因果を測定する。

## スコープ

- 現行版の情報非表示・実体情報表示・動的更新省略を、同じ画面・乱数・速度・画像条件で比較する。
- 更新回数、情報更新時間、主処理時間、DOM・レイアウト処理、フレーム間隔、ゲーム時間の進みを記録する。
- 反復間のばらつきと計測自体の影響を確認し、対策の要否と推奨案を文書化する。
- 必要な範囲でローカル計測スクリプトとテスト手順を整備し、調査結果に応じバックログを更新する。

## 対象外

- 情報ウィンドウの恒久的な性能修正・表示仕様変更。
- 多数チップの描画・組合せ計算、通常画面の描画改善、画質・解像度の変更。
- モバイル実機の再現保証、実機での追加採取、公開・pushによる速度検証。
- GameWorksOAKの変更。同リポジトリは共通ルールとライブラリの参照専用とする。

恒久修正が必要と判明した場合は、根拠と候補を報告して後続開発を提案する。このブランチで修正へ範囲を広げない。

## 実施方針

1. 既存のmeasure-performance.js、PerformanceBuild.js、集計処理を確認し、既存条件をできる限り再利用する。
2. 短い予備測定で起動、情報表示、更新省略、指標取得、終了処理を確認する。予備結果は主要比較と区別する。
3. 主要比較は390×844 CSS px、DPR 3、固定乱数・チュートリアル完了状態、速度1倍、情報表示時の停止なしを基本とし、標準CPUとCPU制限4倍で情報非表示・表示を比較する。CPU4倍では更新省略条件も比較する。各条件は5秒ウォームアップ後30秒×3反復とする。
4. CPU4倍の同一画面で更新あり→省略→ありを各10秒×3反復で比較し、別時点の状態差だけで原因を断定しない。表示実体、チップ数、ゲーム内状態も記録する。
5. 情報表示条件で詳細計測なしの比較を追加し、計測の影響を確認する。必要な条件追加は調査範囲内で理由を記録する。
6. 各反復の平均、p95/p99フレーム間隔、50ms超率、ゲーム時間の進み、LayoutCount・LayoutDuration等を照合する。処理省略は上限評価として扱い、完成した修正の効果としない。
7. 環境・ブラウザー・ゲームと共通側のコミット・差分・版・測定条件・エラー・限界を調査文書と集計JSONへ保存する。生データと比較ビルドはtmp_配下へ保存し、通常ビルドへフックや処理省略を入れない。

## 判断と成果物

- 再構築・寸法計算と負荷の対応が反復と同一画面比較で確認できるかを判断する。全体のフレーム間隔や進行への影響も併記し、小さな関数の時間だけで対策を決めない。
- 対策が必要なら、表示内容の変更検知、描画単位の更新、分割更新ごとの通知抑制等の候補と、現在値・装備・タグ・ピン・親子・位置・拡縮・スクロール・消滅時閉鎖を維持する条件を整理する。候補の実装効果は未検証と明記する。
- 明確な影響が確認できない場合や環境変動が大きい場合は、その結果と残る不確実性を記録し、結論を強めない。PCのCPU制限を実機の再現と扱わない。
- docs/analysis/へ調査文書と生配列を除いた集計JSONを追加し、必要ならtests/README.mdを更新する。
- backlog.mdの調査候補を、確認結果と後続作業が分かる記述へ更新する。既存のオーナー検証項目には変更を加えない。

## 検証と完了条件

- 対象検証: 計測スクリプトの予備・主要比較と集計の整合性、情報ウィンドウの既存仕様テスト・関連実装テスト。計測補助に複雑なロジックを追加する場合は、共通方針に従い先にテストで仕様を定める。
- 終了草案の前に`npm.cmd test`と`npm.cmd run build`を実行する。必要なブラウザー検証はtests/README.mdに従う。失敗時は原因と今回の範囲との関係を調査し記録する。
- 通常ビルドへ調査用フックや更新省略が混入していないことを確認する。
- 測定手順・結果・限界・対策判断、バックログ更新、対象テスト・全テスト・本番ビルドのコマンドと結果を実装報告へ記載する。
- 利用者向け挙動は変更しないため、新たな見た目・実機操作のオーナー検証は現時点では予定しない。判断が必要な事項が判明したら理由と確認可能な内容を提示し、未回答を保留扱いしない。
- 定量結果と判断が記録され、通常動作を維持し、必須検証の結果と失敗調査が揃ったことを完了条件とする。
