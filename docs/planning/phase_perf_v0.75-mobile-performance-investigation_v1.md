# 改善候補と効果（ゲーム中のみ・V1前の判断資料）

2026-10-29～30の追加合意に基づく計測用試作。バージョン0.75.1。通常ソース・アセットは変更しない。タイトル・開始劇・結果・共有画像の追加計測は行わない。

A1＝現行、B＝小変更の試作、A2＝現行へ戻す。同一ページで各10秒、5秒ウォームアップ、各3反復。PC/Chrome・390×844・DPR3でありAndroid/Vivaldiの改善率ではない。

各セルは反復値の中央値 [最小–最大]。短縮率は各反復で `100 × (1 − B / ((A1 + A2)/2))` とし、その中央値と範囲を示す。負値は悪化。

## オーナー指定の第1候補

通常ダメージ（logDamage）とミス（logMiss）の発行時にnotify:falseを指定する。履歴への保存と履歴ウィンドウの既存フィルターは維持し、会心・撃破・Exスキル・施設・警告等の通知は従来どおり残す。FlowLog側へ表示条件を追加する案ではなく、CombatActionLogの発行オプションを変更する案である。変更規模は小（1メソッド内の発行オプション）。第1候補の実際の発行オプションを計測用ビルドで試作した。人工混合30件/秒では履歴300件を保持して表示300→150件、ログ発行CPU計を42.3～50.7％削減した。実ルール由来の通常ダメージ7＋ミス3の一括では表示10→0件、生成同期時間を84.0～93.3％削減した。画面全体やAndroidの改善率とは区別し、反復値を後述する。第1候補の指定を記録するもので、通常ソースへの採用・実装は未実施。

## 第2候補：雷の描画状態の復元漏れ

雷用のshadow等の描画状態が、後続の使い魔・惑乱・文字・タグへ残る。雷ループの前後にsave/restoreを置いて閉じ込める、小規模なバグ修正候補として記録する。雷自身の画素は試作で一致し、後続演出に付いていた紫色の影が消える。混在人工条件のp95短縮率は64.5～73.4％で、実機や通常戦闘全体の改善率ではない。オーナーとの確認で第2候補として整理し、通常ソースへの実装は未実施。

## 第3候補：使い魔画像の修正と描画時filterの削除

紫色が却下された理由は、惑乱と見た目が似すぎるためだった。真っ黒である必要はなく、現在の白黒・暗さの再現も必須条件ではない。惑乱と見分けられる配色の画像へ修正し、描画時のfilterを不要にする案として記録する。具体的な配色は未決定。画像1点とdrawNightFamiliarのfilter指定が主な変更箇所で、新しい汎用キャッシュは不要。公転・羽ばたき・飛行は維持し、輪郭・透過と惑乱との識別性を確認する。画像差し替え後の効果量は未計測。通常ソース・画像への反映は未実施。

## 第4候補：盾・属性リングの描画軽減

盾・属性リングも修正候補としてオーナーと確認した。まず対象画像の縮小版を既存の画像段階選択へ登録し、表示サイズに合う画像を使う案を中心に整理する。演出の枚数・付与値に伴う大きさ・透明度・揺れは維持し、大きな描画方式の変更を前提にしない。最大ズーム、高DPR、強い属性付与時に必要な解像度が足りることを確認する。縮小画像を既存の画像段階選択へ登録する試作で、人工48枚条件の同期main平均を76.5～79.1％削減した。元画像で必要になる毎回の縮小描画を軽くする。表示の枚数・形状・位置・強さ・揺れは同じ描画処理を使用し、必要解像度を満たす段階がなければ元画像へ戻る。画素は完全一致ではなく、縮小時の再サンプリング差がある。これはPCの引き画面・小さい人工対象での値で、大きい勇者や最大ズーム時の同率改善は保証しない。通常ソース・画像への反映は未実施。

## 第5候補：表示時間をJavaScriptで一元管理する

CSS読取の集約案、その後のCSS側calc案は、時間の設定場所を現行のまま温存していた。最終的な追加案は、種類ごとの基準時間（通常6秒・幸運9秒・不運7秒・警告10秒）とランダム補正をJavaScript側で一元管理し、既存の--flow-duration-adjustedへ決定済みの時間を渡す構成とする。CSSは色・字体・移動等の表示を担当し、種類ごとの流れる時間の定義とそのfallbackをJSと二重管理しない。getComputedStyleによる時間の読戻し、待ち行列・flush・disposeの新設は不要。これに伴う変更はFlowLog内の時間決定と不要な読取関数、およびflow-log.cssの時間定義。JS一元化版を第1候補適用後の状態で試作・比較した。人工混合30件/秒のログ発行CPU計を追加で47.7～55.7％削減した。混合60件一括（表示30件）の生成同期時間は66.0～77.1％削減した。旧集約・CSS側calcの数値は転用していない。過去の集約・CSS側calc試作の結果は検証履歴として区別し、この案の実測値としない。通常ソースへは未反映。

## 重い場面と軽い場面がある症状に対応する主候補

## 対象と試作の内容

### 使い魔の元画像の確認

実際に描画する画像は`public/assets/effects/night-familiar.png`（1254×1254）で、紫色のコウモリの画像だった。黒い画像ではない。
`tmp_inspect_familiar_pixels.mjs`で、原寸Canvas上の無加工描画と`grayscale(1) brightness(0.32)`適用後を比較した。
alphaが128以上の379,639画素のうち、RGBの最大値と最小値の差が5を超える色付き画素は376,437（99.16％）。filterによりRGBが変わった画素は379,302（99.91％）だった。alphaの変更は0画素。
したがって「既に黒く、filterが全く無意味」という仮説はこの画像には当てはまらない。filterを単純削除すると元の紫色が出る。見た目を保つ案は、同等の加工済み画像へ差し替えて描画時filterを除く方法となる。
これは画像内容の点検で、加工済み画像へ差し替えた性能測定ではない。出力`tmp_performance/familiar_pixel_inspection751.json`。
その後、紫色が却下されたのは惑乱と見た目が似すぎるためで、真っ黒である必要はないとオーナーから明確化された。第3候補の要件は「惑乱と見分けられる配色の画像へ修正し、描画時filterを除く」とする。現在の白黒・暗さの再現は必須ではなく、具体的な配色は未決定。新しい汎用キャッシュは導入せず、画像と描画箇所に範囲を限定する。画像の実変更は未実施。

### HUDの同値書込を止める

`TimeSettingsController.updateStatus`の3か所だけを対象とする。statusのtextContent、状態のclassName、一時停止ボタンのtextContentを、現DOM値と異なるときだけ代入する。
文言解決は毎回行うため、言語切替や停止理由・加速状態の変化を過去値のキャッシュで隠さない。DOMに保存されている値と比較し、別コードが書き換えた場合も次の更新で修正できる。
ゲームの停止・速度・保存処理、設定のイベント、CSSやログは変えない。3代入への条件追加とボタン文言の一時変数だけで実装できる。

shadowだけでなくstrokeStyleやlineWidth等も戻るため、「blurを0にした」初回比較と区別する。

- `v1-shadow-lightning`: 雷12本だけ。後続に追加の使い魔等がない対照。
- `v1-shadow-mixed`: 雷・使い魔・惑乱・ダメージ文字・タグ転送が各12対象の人工負荷試験。
