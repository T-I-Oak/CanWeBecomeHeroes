## 開発範囲

`tests/spec/05.information_window.test.js` を追加する。既存の `InformationWindowManager`、`EntityDetailLayout`、`StatusLocalization`、`EntityRegistry` 等の検証を照合し、内部メソッドごとの単体検証を複製せず、次の利用シナリオを組み立てる。

| 受入シナリオ | 操作と期待結果 |
| --- | --- |
| 親子の参照と置換 | 親から子、子から孫を開くと祖先が残る。親の別アイコンから参照すると、ピン止めしていない既存の子とその子孫が新しい子に置き換わる。 |
| 内外のタップと閉じる | 最も深いタップ対象と祖先が残り、他の未固定の枝が閉じる。外側では未固定のウィンドウが閉じる。閉じる操作では固定済みも含め対象と子孫が閉じる。 |
| ピン止めと時間停止 | 停止設定が有効な間、未固定のウィンドウがあれば時間停止する。固定済みだけなら外側操作後も残り、情報ウィンドウによる停止が解除される。手動停止・課題選択・自動停止など他の停止理由は維持される。設定無効時も確認する。 |
| 静的情報と実体情報 | Hero・Enemy・Itemおよび固有スキルの定義参照が対象を識別する。定義情報と実体情報を区別し、実体詳細では対象の現在値・装備・タグ・重量を表示する。固有スキルの効果計算は対象にしない。 |
| 表示中の更新と消滅 | HeroのスタミナとEnemyのHPが表示中に更新される。実体が消滅するとその実体ウィンドウが閉じ、定義情報は残る。 |

Node上では実際のManager・GameClock・EntityRegistry・対象生成・描画処理を必要な範囲で組み合わせる。DOMが必要な検証は既存のテスト補助を確認し、イベントと表示結果を検証できる最小限の環境を用意する。本番コードにテスト専用フックを追加しない。描画内容を確認せずデータの変更だけで「表示更新」を検証済みとしない。

`tests/README.md` に要件05の受入テストと検証範囲を記載する。`docs/planning/backlog.md` は05の対応済み部分を整理し、03の未完了項目を維持する。実装フェーズ開始時に `package.json` と `package-lock.json` を `0.56.0` に更新する。

## 対象外

- 固有スキル要件（03）の効果・確率・戦闘接続の受入テスト整備。
- ゲーム仕様、画面デザイン、本番機能の変更と共通ライブラリの変更。
- 要件05の全表示文言・全対象・全レイアウトの網羅、実機のタップ精度や見た目の判定。
- 既存の保留中オーナー検証項目の再依頼・完了扱い。

要件と実装の矛盾が判明した場合、テストの期待値を実装に合わせて変更しない。根拠を整理してオーナーへ確認し、製品修正やスコープ変更が必要なら合意を得る。

## 完了条件

- 要件05に対応する独立した受入テストが存在し、上記シナリオの操作と観測結果を確認できる。
- 既存テストとの役割の違いと、今回自動化していない範囲が対応表・実装報告から分かる。
- テスト対応表、バックログ、バージョン設定が今回の範囲と一致する。
- 対象テスト、全テスト、本番ビルドのコマンドと結果を実装報告へ記録する。失敗時は原因と今回の変更との関係を調査し、作業フローに従って扱う。
- 新たな画面変更がないため、通常は追加の見た目に関するオーナー検証を必要としない。必要性が判明した場合は理由・操作・期待結果を提示し、オーナーの判断を記録する。

## 実装・検証方針

1. 要件05、既存テスト、入力・表示・時間停止の接続を照合し、シナリオごとの観測点を決める。
2. 公開操作と表示結果を中心に受入テストを作成する。既存の低水準テストは維持し、ソース文字列の一致だけを受入判定にしない。
3. `node --test tests/spec/05.information_window.test.js` を実行し、必要に応じて関連する実装テストも実行する。
4. 対応表・バックログを更新し、`npm.cmd test` と `npm.cmd run build` を実行する。
5. ブラウザー接続を変更・追加した場合は `npm.cmd run test:browser` も実行し、その結果を記録する。
6. `phase_test_v0.56-information-window-acceptance_implementation.md` に検証範囲、結果、未解決事項、必要なオーナー判断を記録する。

計画フェーズではテストの実装とバージョン更新を行わない。
