# 情報ウィンドウの差分描画計画

## 合意した開発内容

- ブランチ: `perf/v0.66-information-window-incremental-render`
- 予定バージョン: `0.66.0`。初回の実装開始時にpackage.jsonとpackage-lock.jsonを更新する。
- 情報ウィンドウの更新負荷を測定し、変更部分だけのDOM更新と、必要時だけの寸法計算を実装・検証する。
- 現在値・装備・タグ、ピン、親子関係、移動、拡縮、スクロール、実体消滅時の閉鎖を維持する。

## 対象外

- 多数チップの描画・組合せ計算、画像・解像度の変更。
- モバイルでHeroをドラッグしている間の対象表示改善。
- ゲームルール、更新頻度、および下記のオーナー指示によるヘッダー固定以外の情報ウィンドウ表示仕様の変更。
- GameWorksOAKの変更。共通側はルールとライブラリの参照専用とする。

## オーナーフィードバックによる追加内容

公開した0.66.0のOV-INFO-INCREMENTAL-01に対し、オーナーから「本文だけの内部スクロールが自然」であり、
ヘッダーを含めた全体スクロールは承認できないとの指示を受けた。
修正版0.66.1ではヘッダーを固定し、本文だけを高さ制約内でスクロールする。
閉じる・ピン・表示サイズの操作ボタンを常時操作可能に保ち、本文の位置は数値更新で維持する。
既存の移動・拡縮・ログ履歴を自動検証し、同じIDの01を公開後に再提示する。
02・03のオーナー確認済み判断は維持し、再確認を依頼しない。

## レビュー指摘R-01による文書整理

オーナー方針により、0.66.3では分析資料全体を廃止する。既存分を含むMarkdownと測定JSONを削除し、参照元を整理する。
現行設計に必要な説明だけを実装と照合してランタイム仕様・画像生成仕様へ統合する。
再利用可能な計測手順と指標の制約はtests/README.mdへ、今回の検証結果とオーナー判断はフェーズ実装報告へ記録する。
過去の調査経緯・比較測定結果・検証の進行状況を永続仕様へ移さない。
完了条件は分析ディレクトリと削除資料への参照が残らず、必要な現行設計を仕様で読めることとする。
オーナー確認済み01～03は再依頼しない。製品の動作は変更しない。

## 当初調査で確認した構造

`InformationWindowManager.refreshDynamicEntries`は、実体情報があり、ドラッグ・操作中でない場合に描画を通知する。
`TrialSession`のフレーム内通知集約は実装済みであり、維持する。
`InformationWindowLayer.render`は通知のたびに全ウィンドウを生成し、ルートの子を置換する。
その後、各ウィンドウの境界取得とタイトルの収まり計算を行う。
`EntityInformationRenderer`は現在値・タグ・装備と静的な説明を一括生成する。
Treeのエントリーは更新時に置換されるため、同じIDでも最新の状態を操作に使用する必要がある。

## 実装方針

1. 既存方式の基準値を取得し、動的更新のDOM生成・寸法計算と、他の描画・計算の負荷を分けて確認する。
2. ウィンドウIDに対応するDOMを保持し、開閉・順序変更を反映する。変化しない静的ウィンドウは再生成しない。
3. 実体情報の表示値を比較し、変化したゲージ・数値・タグ・装備などを更新する。
   構造が変わる部分は必要な領域だけを再構築し、毎回の全内容生成による比較は避ける。
4. 初回表示、構造・寸法に影響する内容、言語、拡縮、表示領域の変化など、再計算が必要な条件を明示する。
   数値だけの更新で不要な位置・タイトル計算を繰り返さない。
5. 保持したDOMのイベント処理が古いエントリー・装備・言語を参照しないようにする。
   Managerの交換、画面破棄、ログ履歴との併用も確認する。
6. 実装済みの構造を仕様書へ反映し、測定条件・結果・残る負荷をフェーズ実装報告へ記録する。

具体的な分割・更新APIは実装時に決める。性能改善と表示の正しさを両立できない場合は、
効果を断定せず原因を調査する。合意した範囲の変更が必要ならオーナーへ再提案する。

## 検証方針

状態管理と更新判定は、先に失敗するテストを追加してから実装する。
既存の要求05、InformationWindow関連、EntityDetailLayout、TrialSession、LogHistoryのテストを照合する。

- 現在値・最大値・タグ・重量・装備の変更と、変更後のリンク先を検証する。
- 不変部分のDOM保持、無変更時の更新抑制、必要時の寸法再計算を検証する。
- 開閉、子の置換、ピン、移動、拡縮、言語変更、実体消滅を検証する。
- 実ブラウザーでスクロール保持、タイトル配置、画面端の配置、複数ウィンドウとログ履歴を確認する。
- 対象テストに加え、`npm.cmd test`と`npm.cmd run build`を実装終了草案の提示前に実行する。
- 主要フローのブラウザー検証はtests/README.mdに従う。Windowsの権限制限・終了待ちを成功と扱わない。

性能比較は既存の`measure-performance.js`と`summarize-performance.js`を基にする。
390×844 CSS px・DPR 3・seed 54・出現完了・速度1倍・情報表示時の停止なし、
敵4体・29チップ・regular/pattern10/level5・Averyの実体情報1枚を基本条件とする。
標準CPUとCPU4倍で、同一ページの旧方式A1→修正方式B→旧方式A2を比較する。
旧方式は今回の変更前の方式であり、既存のフレーム内通知集約を有効にした状態とする。
旧方式の切替は計測専用とし、本番へ復元処理を含めない。

既存の30秒×3反復・ウォームアップ5秒、往復比較の各10秒×3反復を基本とし、
テスト・ビルドと主要測定は並行しない。変更が必要なら理由と実際の条件を記録する。
主処理時間、フレーム間隔・分位点、Layout、ゲーム進行、DOM更新・寸法計算回数を照合する。
情報表示なしの条件も用いて残る負荷を切り分ける。表示内容・チップ数・停止状態とエラーを検証し、
単なる更新省略や状態差による速度向上を改善と扱わない。

## 完了条件

- 同条件の往復比較で更新負荷の低減を確認し、ばらつきと適用範囲を記録する。
- 維持対象の機能と表示の正しさを検証し、全テスト・本番ビルドの結果を記録する。
  失敗がある場合は草案前に調査し、範囲内の原因を修正する。
- 実機の操作性はPCのCPU制限測定から断定せず、確認可能な実装ができた時点で、
  一意ID・理由・操作・期待結果・確認バージョン付きでオーナーへ提示する。
  各項目の判断を記録し、未回答を保留として扱わない。
- 実装報告に変更内容、対象・全テスト、本番ビルド、測定結果とオーナー判断を記録する。
