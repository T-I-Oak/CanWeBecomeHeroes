# モバイル性能調査の実装報告

現在の提案範囲は2026-10-29の追加合意に従い、**ゲームプレイ中だけ**とする。
効果・変更規模・見た目への影響は[改善候補の比較一覧](phase_perf_v0.75-mobile-performance-investigation_v1.md)を優先して参照する。
タイトル・開始劇・結果・共有画像の記録は追加合意前の参考データであり、現在の改善候補から外した。
V1直前という制約に合わせて規模を併記する。見た目の変化や規模を理由に担当が候補を除外せず、修正するかはオーナーが判断する。
その後「常に重いのではなく、重いときと軽いときがある」との症状情報を受領した。
常時のHUD・背景は症状対応の主候補から外し、ログ・使い魔・雷との混在・盾や属性の表示数に伴う負荷を主候補として整理し直した。
過去の常時処理の数値は参考記録として保持する。
その後、解像度低下は表示がぼけるためオーナー判断で不採用となった。比較記録は保持するが、現在の修正候補からは外す。
オーナー指定の第1候補は、通常ダメージ（logDamage）・ミス（logMiss）の発行時にnotify:falseを指定する案。
履歴は維持し、会心・撃破などの通知は残す。FlowLog側の条件追加ではない。第1候補の実際の発行オプションを計測用ビルドで試作した。人工混合30件/秒では履歴300件を保持して表示300→150件、ログ発行CPU計を42.3～50.7％削減した。実ルール由来の通常ダメージ7＋ミス3の一括では表示10→0件、生成同期時間を84.0～93.3％削減した。画面全体やAndroidの改善率とは区別し、反復値を後述する。通常ソースへは未反映。
第2候補は雷の描画状態の復元漏れを止める小規模なバグ修正。雷自身を維持し、後続演出への影設定等の漏れを止める。通常ソースへは未反映。
第3候補は使い魔画像を惑乱と見分けられる配色へ修正し、描画時filterを削除する案。
紫色が却下された理由は惑乱と見た目が似すぎるためで、真っ黒・現在の白黒や暗さの再現は必須ではない。具体的な配色は未決定。画像差し替え後の効果は未計測で、通常ソース・画像へは未反映。
第4候補は盾・属性リングの描画軽減。既存の画像段階選択へ縮小画像を登録し、演出の見た目と動きを維持する案を中心とする。縮小画像を既存の画像段階選択へ登録する試作で、人工48枚条件の同期main平均を76.5～79.1％削減した。元画像で必要になる毎回の縮小描画を軽くする。表示の枚数・形状・位置・強さ・揺れは同じ描画処理を使用し、必要解像度を満たす段階がなければ元画像へ戻る。画素は完全一致ではなく、縮小時の再サンプリング差がある。これはPCの引き画面・小さい人工対象での値で、大きい勇者や最大ズーム時の同率改善は保証しない。通常ソース・画像へは未反映。
第5候補は、基準時間とランダム補正をJavaScript側で一元管理し、決定済み時間をCSSへ渡す構成へ訂正した。CSSからの時間読戻しと時間の二重定義をなくす。
JS一元化版を第1候補適用後の状態で試作・比較した。人工混合30件/秒のログ発行CPU計を追加で47.7～55.7％削減した。混合60件一括（表示30件）の生成同期時間は66.0～77.1％削減した。旧集約・CSS側calcの数値は転用していない。旧集約案とCSS側calc案（36通りの表示確認）は検証履歴として残し、新案の検証済み実績や効果率へ転用しない。通常ソースへは未反映。

Android/Vivaldiで報告された症状の直接原因は、実機未計測のため確定していない。
初回報告は負荷の省略比較から改善案を推測するところで止まっており、次の実装を選ぶ根拠として不足していた。
「次の計画が立てられる」とした説明と終了草案を撤回し、0.75.1で表示仕様を維持するフロートログ集約試作を追加比較した。
通常ソースへの性能改善の反映は行っていない。

初回の切分け（0.75.0、33条件×3反復）と、改善案そのものの検証（0.75.1）は別の測定である。
初回の「CSS読取を省いたときの75～80％」を、集約実装や画面全体の改善率として使わない。
追加比較の全文と反復別数値は[集約試作の実測](phase_perf_v0.75-mobile-performance-investigation_prototype.md)に示す。

## 既存基盤で分かる範囲と補完

`scripts/measure-performance.js`と`scripts/lib/PerformanceBuild.js`は、待機・戦闘・情報表示、
GameApp内の処理区間、メソッド、CDP指標を計測できる。
タイトルのupdate/drawは個別に計時できるが、GameAppのmainとは別ループである。
既存の情報・Chip比較は今回の演出件数比較にそのまま流用しない。

不足しているのは、演出の種類・同時表示数を固定した往復比較と、フロートログの発生数・生成時間・同時表示数である。
既存スクリプトを一時コピーして、計測専用ビルドでCombatEffectSystem・FlowLog・GameLogだけを外部参照可能にした。
通常ソースへ参照を追加していない。

### 固定Canvas演出

- ウォームアップ5秒、採取の待機時間30秒をA1→B→A2の各10秒へ分け、3反復する。
  A1/A2は演出あり、Bは演出描画省略。更新・fixture維持はBでも続ける。
  CDP・状態取得の待ちで実際の区間は延びる。重い条件ほど境界の待ちが長く、実秒はCDPのTimestamp差分を用いる。
- 敵出現完了後にclockを手動停止し、boardの数・敵・速度・tickを同一ページの3区間で固定する。
  実際の戦闘計算と演出コストを混同しないための人工試験であり、自然戦闘ではない。
- 実HeroのChipを複製した12個のオブジェクトを、Canvas座標x=55/180/305、y=180/320/460/600からworldへ変換して配置。
  radius=38 world px、boardには追加しない。各区間でCanvas・cameraは同じ。
  通常Heroのradius=96を再現した配置ではなく、実戦の距離・画面密集度や演出面積へ数値を外挿しない。
- 種類: なし、使い魔1/12体、惑乱1/12対象（sprite 3/36枚）、雷1/12本、ダメージ文字12、
  混在（使い魔・惑乱・雷・文字・タグ転送が各12対象）、盾＋3属性×12対象（48枚）。
  「全エフェクトなし」は追加fixtureがない意味で、通常画面の全演出・表示を消す意味ではない。
  使い魔12体は12source×1体であり、同じボスの周囲に12体を置く配置ではない。ダメージ量は各0.5（表示値50）で固定。
  選定理由は、原寸sprite＋filter、sprite枚数、blur、縁取り文字、透過画像の重複を分離できるため。
  飛行・攻撃・全状態アイコン等の未計測対象は演出一覧に示し、共有する描画経路だけから同じ負荷とは扱わない。
- 短命の配列要素は各drawの直前にelapsed=0へ戻してから1/60秒updateする。
  公転時間は呼出しごとに進める。演出数を維持する人工処理の時間は`fixtureMaintenance`として区別する。
  攻撃・飛行の全寿命や、全world位置・画面密集度を再現する比較ではない。
- fixtureの画像を事前にload/decodeし、その後ウォームアップする。
  読み込み済みかはmetadataと実行時例外で確認し、GPU textureの準備完了を保証したとは扱わない。
- 補助比較: 同じ混在をDPR 1、詳細計測無効、filter省略、shadowBlur=0で比較。
  filter/blurのBでは演出数・種類を保つ。shadowColorは維持し、影のぼかしだけを0にする。
  画質を変える切分けであり、採用済みの改善案ではない。
- 各区間境界でCDPとゲーム状態を逐次取得するため、境界の採取処理と待ちは完全に同期していない。
  区間先頭の2間隔を除外する。特に重い条件は標本数が少なく、短い予備測定を主要結果へ混ぜない。

### フロートログ

- 同じ通常画面でclockを停止し、既存の`GameLog.logLocalized`から実際の`logDamage`形式の日本語ログを生成する。
  HeroとEnemyの画像付き参照を2個持ち、通常のinfo/battleで表示する。内容・サイズ・CSSを通常実装から使用する。
- 毎秒1件（1000msごと1件）、10件（100msごと1件）、30件（100msごと3件）、60件一括を人工条件とする。
  要求頻度と実際の発生数を区間別に記録し、処理遅延で発生数が減った場合を隠さない。
- 30秒×3反復、A1→B→A2の各10秒。区間切替で既存の表示DOM/Mapを空にし、ログ配置の乱数をseed=54へ戻す。
  A1/A2で表示、Bは生成・履歴保存を続けつつFlowLog.showだけ省略する。
- 切分け条件のBでは、表示件数を維持してtext-shadowだけを省く、または`--flow-duration`読取を6000msの固定値へ置き換える。
  後者はこのfixtureがinfoのみであることを前提とし、通常のlevel別時間設定を変更しない。
- 60件一括は各区間のCDP/状態スナップショット後に発生させる。
  6秒前後で自然に消えるため、10秒全体の指標と生成直後のコストを混同しない。
- 混在条件ではCanvasの混在演出を3区間とも有効にし、Bだけフロートログを省く。
  Canvas演出まで一緒に省いてフロートログの効果と扱わない。
- `show`の所要時間・件数・最大同時表示、区間末のDOM数・画像未完了数、CDP Style/Layoutを照合する。
  `show`はタイマーコールバック内で動くため、GameApp内の`main`だけでは生成コストを拾えない。
  タイマーは境界取得中も動くので、show時間の配列と境界スナップショットの件数差は最大数バッチずれる場合がある。
  60件一括では生成全体の時間と次RAFまでの時間も別途取得し、先頭2間隔の除外で初動を隠さない。
  初回比較はinfoのみ。追加試作で会心・失敗・警告のlevel別表示時間とscale、画像付きの混在を比較した。
  全locale・すべての長さ・全画像の組合せを網羅する検証ではない。

コード上の実ゲームの経路では、攻撃のダメージ表示と`CombatActionLog.flush`のフロートログ、
雷伝播と被弾・ダメージ文字、使い魔の飛行とダメージ文字等が重なる。
通常戦闘条件で演出の同時発生件数を個別追跡しておらず、12対象の混在fixture全体が自然戦闘で同時発生することは確認していない。

## 計測結果と改善候補

### Canvas演出で計測した事実

14条件×3反復。以下は区間別p95の反復間の範囲であり、端末での改善率ではない。

| 条件 | A1/A2（演出あり） | B | 解釈 |
| --- | --- | --- | --- |
| 追加演出なし | 約33.4～33.5ms | 同程度 | 描画省略フラグだけでは大きな差を出さない対照 |
| 使い魔1体 | 約66.7～83.4ms | 約33.4ms | 単体でもこのPC環境では遅延する |
| 使い魔12体 | 約416.6～433.3ms | 約33.4ms | 原寸画像＋filterの経路を優先調査する根拠 |
| 惑乱1/12対象 | 約33.4ms | 約33.4ms | 画像枚数だけで使い魔と同等の負荷とはいえない |
| 混在 | 約1533.1～1633.1ms | 約33.4ms | 同期mainは約4～5msでも、区間間隔は大きく異なる |
| 混在、filterだけ省略 | A1/A2は約1516.5～1683.4ms | 約50.1～66.7ms | filterを省くと大きく変わるが、遅延は残る |
| 混在、shadowBlurだけ0 | A1/A2は約1499.7～1599.9ms | 約416.7～516.6ms | 雷以降の描画へblurを継承する経路も切分け対象 |
| 混在、DPR 1 | 約200.0～216.7ms | 約16.7～16.8ms | 描画解像度にも依存する。画質を含む採用判断はしていない |
| 盾＋3属性×12対象 | p95は約33.4ms | 約33.4ms | main平均はA1/A2約23.2～24.8ms、B約4.3～4.5ms。p95だけでは同期処理の余裕の差を見落とす |

使い魔12体のupdate平均は0.1ms未満の時計分解能に埋もれる値が多い。
その一方でmain平均は約4ms、CDP TaskDuration/実秒は演出あり区間でほぼ1秒となる。
同期関数の発行時間を全部足せば後続描画の負荷を説明できる、という解釈はしない。
GPU・raster・driver待ちの内訳そのものは今回直接分解していない。

混在の詳細計測無効条件でも同じ桁の遅延が生じるため、メソッド別タイマーだけが主要因とは考えにくい。
ただし詳細計測無効でもfixture維持・RAF採取・ローカル変換は残る。
重い混在条件のA1/A2は区間あたり約8間隔しかなく、p99とp95は独立した安定推定ではない。
細かなms差を順位に使わず、往復比較の桁の差と3反復での再現性を根拠とする。
全区間を結合するとBのフレーム数が支配し、混在全体のp95が33.5msになる反復もあった。
この値を「混在しても滑らか」と読むことはできない。

### 改善候補の整理

| 優先 | 候補・根拠 | 想定する修正範囲と期待 | 懸念・追加計測 |

### フロートログで計測した事実

毎秒30件の通常ログでは、約180件以上が同時に表示され、約1700個の子孫DOM要素を持つ条件になった。

表示省略Bでは同じログを履歴へ記録しながら、表示MapとDOMは0件となる。
表示ありのp95が50msになる反復はあるが、全反復で同じフレーム間隔の悪化が出たわけではない。

30件/秒でdurationのcomputedStyle読取だけを省いた比較では、
show平均がA1/A2の約0.622～0.755ms/件からBの約0.144～0.165ms/件になった。
区間内のStyle再計算はA1/A2の842～859回に対してBは526～555回であり、

style計算の一部が後続フレームへ移る可能性も考慮し、CDPと区間全体を併読する。

text-shadowだけを省いた30件/秒の比較では、p95・mainに一貫した改善を確認できなかった。
この結果から、影を外せばAndroidで滑らかになると結論づけない。
移動は既にtransformによるCSS animationであり、生成時と表示中の負荷を分けて扱う。

通常30件/秒の1反復後に生成を停止して7.5秒待つと、表示Mapと直下DOMはともに0件となった。
