# モバイル性能調査計画

## 合意内容

モバイルで動きが滑らかでない原因と、性能改善できる箇所を調査する。エフェクト単体の負荷に加え、同種・異種のエフェクトが重なる際の負荷も調べる。改善の修正は別途判断する。

- ブランチ: `perf/v0.75-mobile-performance-investigation`
- 予定バージョン: `0.75.0`。実装フェーズ開始時にpackage.json・package-lock.jsonを更新する。計画時には更新しない。
- 端末・OS・ブラウザー・具体的な発生場面は未指定。未取得の条件を推測で確定しない。

## 開発スコープ

### 2026-10-29の追加合意（以後の判断で優先）

- 対象はゲームプレイ中だけに絞る。タイトル・開始劇・結果画面・共有画像の初回データは参考記録として残し、以後の追加調査・V1前の改善候補から外す。
- V1リリースまで数日のため、描画方式や構造の大幅変更は提案しない。変更範囲が小さく、戻せる案を優先する。
- 通常ソースへの性能改善の採用は引き続き別判断。まず計測専用の小さな試作で、効果・挙動・見た目への影響を確認する。
- 実機のUSBデバッグ・同一Wi-Fiによる検証は利用できない。PCで評価可能な小変更の採否を整理し、実機の改善率を断定しない。
- 初回の幅広い候補一覧よりこの制約を優先し、各候補に変更規模・見た目への影響・効果の確度を付ける。
- 追加の明確化: 修正するかはオーナーが判断する。担当は見た目の変化や規模だけを理由に候補を除外せず、効果を確認できた箇所を比較可能な形でリスト化する。
- 症状の追加情報: 常に重いのではなく重いときと軽いときがある。HUDと背景の常時処理は症状対応の主候補から外し、発生・表示数・重複で変動するログ、使い魔、雷との混在、盾・属性表示を主候補にする。解像度低下は後続のオーナー判断で不採用となり、過去の参考記録だけを残す。
- オーナー指定の第1候補: 通常ダメージ（logDamage）とミス（logMiss）の発行時にnotify:falseを指定する。履歴は維持し、会心・撃破等の通知は残す。FlowLog側で除外する案ではない。効果量を計測用試作で確認し、通常ソースへの実装は別判断とする。
- 第2候補: 雷の描画状態の復元漏れを小規模なバグ修正として整理する。雷ループ前後のsave/restoreで後続演出への影設定等の漏れを止め、雷自身の見た目は維持する。後続演出の紫色の影は消える。通常ソースへの実装は未実施。
- 第3候補: 使い魔の紫色は惑乱と見た目が似すぎるため却下された。真っ黒である必要はなく、現在の白黒・暗さの再現も必須ではない。惑乱と見分けられる配色の画像へ修正し、描画時filterを削除する。具体的な配色は未決定。新しい汎用キャッシュは不要とし、公転・羽ばたき・飛行を維持、輪郭・透過と識別性を確認する。画像差し替え後の効果量は未計測、通常ソース・画像への反映は未実施。

- ゲームの更新・描画、DOM更新とレイアウト、画像処理、メモリ確保・解放の負荷候補を確認する。
- エフェクトを種類と実装経路で整理し、更新と描画、同時表示数、継続時間、描画面積、画像変換などの負荷要因を調べる。戦闘・固有スキル・状態表示に加え、タイトルや結果画面など独立した演出ループも確認する。
- エフェクトなし／単体／同種複数／異種同時の条件を比較する。実ゲームで起こる組合せと人工的な負荷試験を区別する。
- 既存計測基盤を確認し、再現可能な条件で計測する。調査専用の計測追加が必要な場合は一時成果物または計測専用ビルドに限定する。
- 改善候補の根拠、影響する場面、改善案、期待する効果、挙動・画質等への懸念、優先順位、追加計測事項を調査報告へまとめる。

- 第4候補: 盾・属性リングの描画軽減。既存の画像段階選択へ縮小画像を登録する案を中心とし、演出の枚数・付与値に伴う大きさ・透明度・揺れを維持する。最大ズーム・高DPR・強い属性付与時の画質を確認する。描画全省略の削減率を修正後の効果へ転用せず、修正後の効果量を計測専用試作で確認する。通常ソース・画像への反映は未実施。

第5候補は、基準時間とランダム補正をJavaScript側で一元管理し、決定済みの時間をCSSへ渡す構成とする。CSSからの時間読戻しと、時間の二重定義をなくす。旧集約案やCSS側calc案の構成は採らず、待ち行列等の新設は不要。JS一元化版の試作・性能計測と第1候補後の追加効果を今回の調査範囲で確認する。旧試作の数値を転用せず、通常ソースへの反映は別判断とする。

### 2026-10-30の範囲確認

オーナー回答は「調査・計測用試作・報告を仕上げる」。第1候補と最終的な第5候補、その組合せの効果を追加比較し、通常ソースへの反映は含めない。

## 対象外

- Canvasの解像度低下は、表示がぼけるためオーナー判断で不採用。過去の比較値は参考記録に残すが、修正候補には含めない。
- 性能改善の実装、通常ビルドの動作・描画品質・ゲームルール・ゲーム内文言の変更。
- 端末ごとの最適化の採用判断、未計測の改善率の断定。
- 旧保存データの移行・補正、共通リポジトリの変更、公開・配信。
- 既存の保留中オーナー検証6件の再確認。

## 調査・計測方針

1. 既存の`tests/README.md`、`scripts/measure-performance.js`、`scripts/lib/PerformanceBuild.js`と関連処理を照合し、既存計測で分かる範囲と不足を整理する。
2. 更新・描画の呼出経路とエフェクト一覧を確認し、常時処理、発生時処理、対象数によって増える処理を分ける。
3. 待機・戦闘・画面操作などの基準条件を定める。エフェクトは実装上の負荷候補を絞った後、単体と重複時の比較対象を決め、選定理由と未計測対象を記録する。全種類・全組合せを計測したように扱わない。
4. 比較条件では乱数、敵・チップ数、装備・スキル、進行状態、速度、停止状態、Canvas寸法、DPRをそろえる。エフェクト数とゲーム進行を記録し、エフェクトの差と戦闘計算量の差を混同しない。省略比較は計測用に限定し、可能なら同一ページの往復比較を用いる。
5. ウォームアップと複数反復を行い、フレーム間隔の中央値・p95・p99、長いフレームの頻度、更新・描画の時間、ゲーム進行速度、ブラウザーのTaskDuration・LayoutDuration等を取得可能な範囲で比較する。CPUプロファイルは補助調査として分離し、詳細計測自体の負荷も確認する。
6. CPU負荷制限や小画面・高DPRのPC計測は実機の再現とは扱わない。GPU描画完了、GC、メモリ消費など直接測れていないものは推定と明記する。画像寸法からのメモリ概算と実測値も区別する。
7. 実機情報や接続が得られた場合は実機で照合する。取得できない場合はその限界と再現・追加計測の手順を記載する。実機未確認を確認済みとしない。

主要計測とテスト・ビルドを並行実行しない。生データ、プロファイル、調査専用ページ・スクリプトは`tmp_`配下へ置き、報告にはコマンド、条件、集計結果、ばらつき、解釈と限界を残す。通常ソースへの計測フック追加や恒久的なテスト資産の追加を前提にしない。

## 成果物と完了条件

- `phase_perf_v0.75-mobile-performance-investigation_implementation.md`へ調査結果と検証結果を記載する。必要なら同接頭辞の調査資料へ分割して参照する。
- エフェクト一覧と調査対象の対応、単体・重複時の比較結果、その他の負荷候補を示す。
- 改善候補は計測で裏付けた事項／コードからの推測／追加調査が必要な事項を区別し、修正範囲を別途判断できる粒度で整理する。
- 計測条件と再現手順、計測できなかった条件、実機確認の有無を示す。
- 通常ビルドに性能改善や調査用挙動を入れない。
- 必要なオーナー検証を提示する場合は一意ID、理由、手順、期待結果、確認バージョンを示し、判断を記録する。未回答を保留にしない。

## 検証方針

- 調査用の仕組みを変更する場合は、変更範囲に対応する既存の対象テストを実行する。既存の計測結果を新しい測定結果として扱わない。
- 実装フェーズの終了草案提示前に`npm.cmd test`と`npm.cmd run build`を実行し、結果を報告へ記載する。失敗した場合は原因と今回の範囲との関係を調べる。
- ブラウザー検証の実行時は`tests/02.browser_verification.md`の専用実行手順に従う。
- バージョン更新後、確認依頼では設定とタイトル・倉庫の表示の一致を確認する。
- レビューでは合意範囲、調査の再現性、事実と推測の区別、通常ビルドへの変更の有無、検証結果を照合する。
