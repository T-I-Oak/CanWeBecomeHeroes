# v0.60 定期見直し計画

## 開発スコープ

Minorが10の倍数となる新規開発に適用する定期見直しを行う。現在のゲームの挙動を維持し、文書とソースの保守性・整合性を確認する。

- 予定バージョン: `0.60.0`。
- 開発ブランチ: `chore/v0.60-periodic-review`。
- 共通ルールとプロジェクト固有の規定を読み直し、準拠状況を点検する。
- 文書の現存しない仕様、章構成、リンク・参照先、実装との不整合を点検する。
- ソースの未使用コード、重複、文書との整合性、ファイルサイズを点検する。ソースは共通コーディングガイドの1ファイル500行制限、文書は文書ガイドの100～300行程度という目安を確認する。
- テストの対象と文書の挙動、責務、配置を照合する。ソースを分割・移動する場合は対応するテストの責務と配置も見直す。
- バックログの要望・バグ指摘の依存関係・優先順、オーナー検証の項目単位と判断記録を確認する。
- 点検で必要と判断した文書修正、未使用コード整理、挙動を維持する責務分割を実施する。

## 対象外

- 新規機能、ゲームルールや画面・操作の仕様変更。
- 見直し範囲外の不具合修正。発見した場合は根拠とともにバックログの要望・バグ指摘へ記録する。
- GameWorksOAK側の変更。必要な修正は問題と変更内容をオーナーへ報告する。
- 既存の保留済みオーナー検証を、今回の点検だけで確認済みに変更すること。

## 完了条件

- 開発ルール、文書、テスト、ソース、バックログの各点検範囲と結果を実装報告に記録する。
- 見直し範囲内の修正内容、修正不要とした判断、残る問題と扱いを実装報告に記録する。
- 文書は現行の仕様・実装・参照先を示し、分割する場合は参照を更新する。
- ソースの整理・分割によって既存の公開インターフェースとゲームの挙動を維持し、関連テストの責務・配置を整える。
- 対象テスト、全テスト、本番ビルドを実行し、コマンドと結果を記録する。失敗は原因を調査し、今回の変更・範囲に起因するものは修正して再実行する。既存または範囲外の失敗は根拠と今回修正しない理由を記録する。
- オーナー判断が必要な項目が生じた場合は、一意ID・理由・操作手順・期待結果・確認バージョンを提示し、判断と対応を記録する。未回答を保留として扱わない。
- 点検範囲、修正内容、全テスト・本番ビルドの結果をチャットでも報告する。

## 実装方針

1. 初回の実装開始時に`package.json`と`package-lock.json`を`0.60.0`へ更新する。タイトルと倉庫左下のバージョン表示が設定と一致することを確認する。
2. 追跡対象の文書・ソース・テスト・設定を棚卸しし、行数、参照関係、責務を点検する。生成物や依存パッケージをゲームの保守対象ソースに含めない。
3. 未使用と判断するコードは、静的参照に加え、動的参照・データ定義・外部からの利用経路を確認してから整理する。
4. 挙動維持を検証できる単位で修正する。複雑なロジックを扱う必要が生じる場合は共通ルールのTDD方針に従う。
5. 通常の文書は現行の意味を記し、点検履歴と検証結果はフェーズ実装報告へ集約する。v0期間の`public/data/update_history.json`は空配列を維持する。
6. スコープ・予定バージョン・ブランチ名を変更する必要が生じた場合は、変更案を提示して再合意を得る。

## テスト方針

- 検証コマンドと配置は[テストの構成と実行](../../tests/README.md)に従う。
- 変更したモジュールに対応する実装テストと要求仕様テストを随時実行する。単純な文書修正だけのために実装をなぞるテストを追加しない。
- ソースの分割・移動では呼び出し側の接続と既存の挙動を確認する。画面・起動・入力・本番参照経路に関わる変更では`npm.cmd run test:browser`も実行する。
- 終了草案の提示前に`npm.cmd test`と`npm.cmd run build`を実行する。文書・設定だけの変更でも省略しない。
- 必要な手動確認は実装結果に応じて提示し、自動テスト成功を実機・見た目の確認済みとは扱わない。
