# 終了画面の画像シェア計画

## 合意した開発単位

- ブランチ: `feature/v0.53-result-sharing`
- 予定バージョン: 初回 `0.53.0`。オーナーから共有フローの計画誤りを指摘され、修正着手時に `0.53.1` へ更新する。
- 終了画面の表を上、裏を下に縦に並べた1枚の画像をシェアする。
- シェアに添えるテキストと画像構成は、実装開始前のオーナーとの打ち合わせで以下のとおり合意した。

### 実装開始前の合意（2026-10-18）

- ゲームタイトルは `Can We Become Heroes?`。
- 共有文はゲームタイトル、結果の一文、`https://t-i-oak.github.io/CanWeBecomeHeroes/`、`#CanWeBecomeHeroes #GameWorksOAK` を改行で連結する。
- 結果の一文は、合格「勇者認定試験に合格しました！」、不合格「勇者認定試験に挑戦しました！」、実力判定「実力判定試験を終えました！」。
- 画像は上からタイトル画像、終了画面の表、裏の成績表、copyrightの順とする。
- copyrightは `© T.I.OAK 2026 | GameWorks OAK`。既存のAppMetadataを参照する。
- 紙の質感・線・文字色はゲーム画面を再現する。背景・余白・出力サイズは既存画面に合わせて実装で調整する。
- 終了画面のボタン順は「裏返し」「結果をシェアする」「タイトルに戻る」。
- オーナーの「作業を進めてください」により実装へ着手した。

### 共有フローの訂正（2026-10-18）

初回計画の「画像共有API非対応ならPNG保存」は誤りとオーナーから指摘された。他ゲームに合わせて、PCは画像コピー→確認画面→X投稿画面、モバイルは端末共有へ修正する。先のPNG保存に関する検証依頼は取り下げる。

## 開発スコープ

- 終了画面にシェア操作を追加する。
- 勇者認定試験の合格・不合格、実力判定試験の終了について、通知面と成績表を1枚の画像にする。
- 現在どちらの面を表示しているかによらず、同じ終了結果の表裏を生成する。
- PCは画像をクリップボードへコピーし、確認画面を経て本文入りのX投稿画面を開く。画像はユーザーが投稿画面へ貼り付ける。モバイルは端末の画像共有機能を使用する。他ゲームと同じフローに揃える。
- 日本語・英語の終了画面と操作表示に対応する。
- 対象テスト、関連仕様書、バックログを更新する。

## 対象外

- `project_info.json` の紹介文・タグ・コンセプト画像の整備。
- GitHub Pagesの公開基盤変更、主要フロー全体の受入テスト整備。
- 戦闘時間・試験難易度などのゲームバランス調整。
- GameWorksOAKの変更。

## 現在の実装と設計方針

- `src/app/TrialRunResultModal.js` が終了時の確定情報から表裏を表示する。
- 紙面は840×534の論理サイズを持ち、画面表示では利用可能領域に合わせて縮小する。画像生成は端末の画面サイズ・縮小率・現在の表示面に依存させない。
- 表裏の表示内容と画像の内容が一致する構成とし、描画・画像生成・共有操作の責務を分ける。実装方式と画像の出力寸法・形式は実装時に検討する。
- 共有画像には終了画面の操作ボタンを含めない。通知、メンバー、二つ名、成績表が欠けないようにする。
- 画像生成のために表示中の面を操作したり、成績を再集計・再保存したりしない。裏返し・タイトル復帰の既存操作を維持する。
- フォントと画像の読み込み完了、生成処理の多重実行、共有のキャンセル、生成・コピー・共有失敗時の扱いを設計する。
- PCとモバイルを判定し、PCはクリップボード、モバイルは画像共有へ進める。PC表示のiPadはモバイルとして扱う。非対応・権限不足は失敗案内を表示し再試行可能にする。キャンセルを失敗と混同しない。
- シェアに添えるテキストは上記の合意を反映する。メンバー名・成績は本文に追加せず、画像で伝える。

## 実装・テスト方針

1. 共通のコーディング・CSS・モバイル規約と終了画面仕様を確認し、既存の描画・文字組み・アセットを調査する。
2. テキストの内容をオーナーと打ち合わせる。画像生成方式を検討し、表裏の縦結合と画面から独立した出力を実装する。
3. PCの画像コピー・確認画面・X投稿画面と、モバイルの画像共有を接続し、言語別の操作表示と失敗時の扱いを整える。
4. `tests/implementation/app/` を中心に、表裏の順序、同一結果の使用、共有可否による分岐、キャンセル、失敗、多重操作と既存操作への影響を必要な範囲で検証する。
5. 実際に生成した画像で、各終了結果、日本語・英語、長い文字列、成績表の全件表示、フォント・印影等のアセットを確認する。端末の縦横と表示中の面を変えても内容が欠けないことを確認する。
6. 変更に対応する対象テストを実行し、終了草案の提示前に `npm.cmd test` と `npm.cmd run build` を実行する。コマンドと結果を実装報告へ記録する。
7. 必要な仕様書とバックログを更新し、実装報告を作成する。

## オーナー検証

確認可能な実装ができた時点で、更新済みバージョンと操作手順・期待結果を付けて必要な項目を提示する。共有画像の見た目、実機での画像貼り付け・共有について、1項目ずつ判断できるようにする。

各項目の判断と対応を実装報告へ記録する。未回答を保留と解釈せず、「現時点で確認しない」と判断された項目だけをバックログのオーナー検証へ残す。既存の確認済み・却下済み項目を再依頼しない。

## 完了条件

- 各試験の終了結果について、表が上・裏が下の1枚の画像を生成できる。
- 画面サイズや現在の表示面によらず、両面の内容が欠けず、操作ボタンが含まれない。
- PCで画像コピー後の確認画面から本文入りのX投稿画面へ進み、画像を貼り付けられる。モバイルでは端末の画像共有ができる。
- シェアに添えるテキストについて、実装時の打ち合わせ結果が記録・反映されている。
- 裏返し・タイトル復帰、結果の集計・保存などの既存動作を維持する。
- 対象テスト・全テスト・本番ビルドの結果、および必要なオーナー検証の判断・対応が記録されている。
