# チップ数増加に伴う負荷調査の計画

## 開発内容

- 起点は全体レビューで挙がった性能問題の可能性。実ゲームで遅さを感じたというオーナー報告ではない。
- 対象バックログ: チップ数増加による描画・組合せ計算が操作性を損なうかを確認し、対策の要否を判断する。
- ブランチ: `chore/v0.68-chip-performance-investigation`
- 予定バージョン: `0.68.1`。初回調査版`0.68.0`の終了草案に対するオーナー指示により、必要な性能修正まで含める。
- チップ数を段階的に増やした再現可能な計測条件を整え、描画、物理・重なり計算、ドラッグ操作への影響を調査する。
- 最終合意では、描画品質と既存のメモリ予算を維持した計算負荷の削減で今回のスコープを満たす。調査・修正と同じ条件での効果・挙動確認まで行い、追加対策は実ゲームで遅さが問題となった際に再検討する。起動時JavaScriptの軽量化、ゲーム仕様の変更は対象外とする。

## 確認する実装

- `src/chips/ChipBoard.js`: 更新、地上の重なり解消、描画順、移動に伴う接触処理。
- `src/chips/ChipRenderer.js`: 本体・効果の描画。
- `src/game/HeroItemInteractionController.js`: アイテム収集、ドラッグ対象、実体の走査。
- `src/app/GameApp.js` と `src/app/TrialSession.js`: フレーム全体、シミュレーション更新、描画の呼出し。
- `src/game/WarehouseCapacity.js`: 実際の倉庫容量。容量超過の人工条件と通常プレイ条件を混同しない。

## 調査・計測方針

1. 既存の `scripts/measure-performance.js`、`scripts/lib/PerformanceBuild.js`、集計スクリプトを再利用し、必要な計測条件・指標だけを追加する。
2. 固定乱数、同じ課題・敵構成・速度・停止状態・カメラ・画像読込状態を揃える。倉庫アイテムの通常状態、容量の約25・50・75・100%を比較し、実数と総チップ数を記録する。元から存在するアイテムも含め、目標値へ追加できたことを確認する。
3. 主な比較はPCの通常CPUとCPU4倍負荷制限で行う。画面寸法・DPRを固定して個数の影響を比較し、PC画面条件も確認する。CPU制限や小画面条件はモバイル実機の再現とは扱わない。
4. 静止・物理更新中・ドラッグ中を区別する。初期落下が落ち着いた条件を基本とし、密集・移動時の負荷を別条件で確認する。ドラッグは同じ対象と経路を使い、入力イベントから描画反映までの観測範囲・測れない部分を明記する。
5. フレーム間隔のp50・p95・p99、長いフレームの割合、同期フレーム処理時間、描画・重なり処理時間、CDPのTaskDuration、経過tick/実秒を記録する。組合せ候補数などを追加計測する場合は、計測自体の負荷も比較する。
6. 予備測定と主要測定を分ける。主要測定は既存手順のウォームアップ5秒、30秒×3反復を基本とし、反復別の値とばらつきを示す。測定中は別のテストやビルドを並行実行しない。
7. 処理省略による切り分けは計測専用ビルドに限定する。同一シーンで処理あり→省略→ありの比較を優先し、関数内時間だけで原因や改善率を断定しない。詳細計測なしの条件とも照合する。

## 評価と完了条件

- 個数・配置・入力条件を再現でき、各反復のシーン整合性、実行時エラー、画像読込完了を確認できる。
- 通常状態から満杯までの負荷傾向を、描画と組合せ計算に分けて説明できる。
- 60Hzの1フレーム約16.7ms、複数フレームに及ぶ停止、入力反映の遅れ、ゲーム進行速度を評価の目安として使う。単一の分位点だけで操作性を断定せず、反復のばらつきとドラッグの観測結果を併記する。
- 結論を「対策が必要」「今回の測定範囲では不要」「判断に追加検証が必要」のいずれかとして、対象条件と根拠を示す。実機未測定などの制約を残したまま全環境へ一般化しない。
- 必要な場合は改善候補、期待する効果、影響する挙動を整理し、性能修正を実装する。修正前後を同じ条件で測定し、描画の品質、重なり順、接触・移動・収集の挙動を検証する。
- 計測条件・結果・判断・限界をフェーズ実装報告へ記録し、バックログの調査項目を結果に応じて整理する。生データ・CPUプロファイル・一時ビルドは `tmp_` 配下に置き、永続資料にしない。

## 実装・検証方針

- 計測用変換を通常ビルドへ読み込ませず、本番へ `__perf`・`__session` や処理省略機能が入らないことを確認する。
- 計測条件生成や集計に複雑なロジックを追加する場合は、対象の境界条件・集計の意味をテストで先に定義する。既存の `PerformanceBuild.test.js` など関連テストも実行する。
- 実装終了草案前に `npm.cmd test`、ブラウザー検証、`npm.cmd run build` を実行する。ブラウザー検証の実行・終了確認は `tests/README.md` に従い、コマンドと結果・失敗時の調査を実装報告へ記録する。
- オーナーによる操作感確認が必要になった場合は、一意ID、理由、手順、期待結果、設定と画面表示が一致する確認バージョンを提示し、判断と対応を記録する。未回答を保留として扱わない。
- GameWorksOAKは参照専用とする。共通基盤の修正が必要な場合はオーナーへ報告する。
