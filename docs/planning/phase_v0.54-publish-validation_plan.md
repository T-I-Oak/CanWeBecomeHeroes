# 公開ビルドの検証整備

## 開発単位

- ブランチ: `feature/v0.54-publish-validation`
- 予定バージョン: `0.54.0`。初回実装開始時に設定する。
- 対象: バックログ「共有と公開を整備する」の公開前検証と主要フローの受入テスト。

## 現状と目的

`.github/workflows/deploy.yml` は、ゲームと公開済みGameWorksOAKの`master`を取得し、隣接パスへリンクしてからビルド・配信する。共通ライブラリ参照の仕組みは既に存在するが、配信前にテストを実行しない。

`tests/spec/01.game_settings.test.js` は開始メンバー、合否判定、解放などを検証する。`TrialSession`、`TrialRunFlow`、`TrialResultEntrance`にも実装テストがある。既存の検証を利用し、開始からタイトル復帰までの接続で不足する部分を補う。

## 開発スコープ

1. 公開ワークフローで、依存関係のインストール後、ビルド・配信前に全テストを実行する。テスト失敗時は配信へ進めない。
2. タイトルから開始メンバー選択、開始劇、試験課題選択、戦闘、結果表示、タイトル復帰までの主要フローを検証する。合格と期限切れの両方を扱う。
3. 既存テストの責務と照合し、不足する接続の受入テストを追加する。テスト配置と要求文書の対応を`tests/README.md`に記録する。
4. 本番ベースパス`/CanWeBecomeHeroes/`で起動し、主要アセットと共通ライブラリを含むビルドを読み込めることを確認する。
5. 実装結果に応じて仕様・バックログを更新する。紹介データの整備は未完了として残す。

## 対象外

- 紹介文、タグ、コンセプト画像、公開予定バッジ・ボタンの変更。
- ゲームバランス、戦闘時間、試験難易度の変更。
- 固有スキル要件03と情報ウィンドウ要件05の独立した受入テスト整備。
- GameWorksOAK側の変更、共通ライブラリ参照方式の刷新。
- このフェーズでの実装・配信、正式公開への切り替え。

## 実装方針

- 公開済みGameWorksOAKの`master`を使う既存のcheckout・リンクを維持する。
- 主要フローは公開用の実装経路を対象にする。計算や内部処理の同じ検証を重複追加しない。
- DOM・Canvas描画の代替だけで画面全体の受入完了とは扱わない。既存のNodeテストで扱える接続と、ブラウザーで確認すべき起動・画面遷移を区別する。
- 時間・乱数・保存データを制御して、長時間の実プレイや偶然の勝利に依存しない検証にする。テストのために本番の合否条件を緩めない。
- 追加のブラウザーテスト基盤が必要な場合は、ゲーム内に閉じた最小限の構成とし、CI上での導入・実行手順も整備する。

## 検証方針と完了条件

- 開始操作で選択したメンバーがランに入り、開始劇から試験課題選択へ進むこと。
- 課題選択から戦闘へ進み、勝利後に次の課題へ進むこと。
- 最終課題の勝利で合格結果、期限切れで不合格結果が表示され、それぞれ閉じるとタイトルに戻ること。
- 結果確定が重複せず、タイトルから次のランを開始できること。
- 公開ワークフローが全テスト成功をビルド・配信の前提にすること。失敗を無視する設定を入れない。
- 本番ビルドのベースパスで起動・アセット読込を確認し、エラーがあれば調査する。
- 対象テスト、`npm.cmd test`、`npm.cmd run build`を実行し、結果を実装報告へ記録する。範囲内の失敗は修正する。
- 必要なオーナー検証が見つかった場合は、実装フェーズで理由・操作・期待結果と実際のバージョンを提示し、項目ごとの判断を記録する。既存の保留項目は再依頼しない。

- 必要に応じた仕様・バックログ更新。
- `phase_v0.54-publish-validation_implementation.md`への実装・検証結果。
