# アプリケーション構成

## 1. 方針

本番のゲーム実装と、開発中にだけ必要な画面確認用の入口は別の責務として扱う。

- `src/chips/`: ゲーム・デモの双方で使う共通チップライブラリ。物理、描画、衝突、移動を担当する。
- `src/game/`: Hero、Item、タグ、固定ワールド、ゲーム操作などのゲームルールと状態を担当する。
- `src/app/`: Canvas、カメラ、入力、描画ループを持つ本番アプリケーション基盤を担当する。
- `tests/manual/`: 開発用の画面確認と操作確認手順を置く。

## 2. 起動経路

`src/main.js` は `startGame()` を起動する。最初に `TitleMenu` を表示し、`StartPartySelectionModal` が解放済みHeroから2名を選ばせる。その直後に `VignetteModal` が開始劇を再生し、終わってから試験ランを始める。合格またはゲームオーバーの結果を閉じるとタイトルへ戻る。`GameApp` 自身はランダム生成やデモ専用の表示ガイドを持たない。

## 3. 本番アプリ基盤

`src/app/GameApp.js` は依存関係を組み立て、各責務モジュールを接続して更新ループを開始する。`TrialSession` は試験ランごとのシステム構築、入力対象の照会、更新と描画を接続する。

- `GameCanvasInput` は、Canvasのポインター、Chip選択ドラッグ、カメラ移動、ポインター中心ホイールズーム、2本指ピンチズームを扱う。
- `TimeSettingsController` は、時間設定UI、速度、自動停止、永続化、HUD状態表示を扱う。
- `VignetteModal` は、試験開始前の開始劇を画面固定モーダルで再生する。シナリオは `StartVignette` が選び、再生中は `GameClock` を理由 `vignette` で止める。
- `TrialRunFlow` は、加入処理、ランの終了判定、クリアー時の解放、次の試験課題表示を調停する。
- `WorldSurfaceRenderer` と `SelectionGuideRenderer` は、それぞれワールド面と選択ガイドのCanvas描画だけを扱う。
- `EquipmentSlotRenderer` と `HeroStatusPanelRenderer` は、装備スロットおよびHeroステータス・準備パネルのCanvas描画を扱う。準備パネルの装備配置は、入力判定と同じ `PreparationPanelHitTest` のレイアウト定義を使う。
- `RectHitTest` は矩形へのポインター判定、`EquipmentSlotHitTest` は装備スロット内のItem・タグ判定を扱う。`PreparationPanelHitTest` と `ShopPanelHitTest` は、それぞれのパネル固有の入力領域を組み立てる。

## 4. 試験ラン

`src/game/RunScenario.js` は選択した2名のHero、各Hero向けの開始装備、行き先Item、ショップ状態を初期化する。

### 4.1 Heroスロット管理

`src/game/HeroSlotManager.js` は、戦闘・ショップ・ギルド・訓練のHero用スロットを管理する。予約と占有を別状態として持ち、複数Heroが同時に移動しても同じスロットを選ばないようにする。戦闘スロットの予約優先順は `2 → 3 → 1 → 4` である。

`src/game/ItemPickupController.js` は、Heroごとの拾得状態を保持する。複数Heroの移動・吸収・行き先スロット移動を同時に更新し、目的Itemが盤面から消えた場合は次の装備可能Itemへ再ターゲットする。

`src/game/HeroItemInteractionController.js` は、全Chipを基点にできる共通のドラッグ選択状態と、Hero・Item・袋の組み合わせに応じたゲーム処理を接続する。Canvas上の点線・基点枠・有効／無効の終点枠は `TrialSession` が選択状態を描画する。Chipのタップは選択状態を変更せず、情報ウィンドウを開く。選択UI自体は処理の完了内容を持たず、袋格納・HeroのItem取得などの組み合わせ側へ委譲する。

### 4.2 ゲーム時計

`src/game/GameClock.js` は、一時停止とゲーム速度（x1／x2／x4）を管理する。描画・カメラ操作は常に継続し、ゲーム状態の更新だけを停止または加速する。加速時は最大1/60秒の内部更新へ分割し、チップの衝突・移動・吸収アニメーションを安定させる。

`src/game/StaminaRecoverySystem.js` は、ゲーム内1/60秒のtickを蓄積して準備エリア滞在Heroのスタミナ回復を処理する。

`src/game/ShopState.js` は今回・次回・次々回の販売タグ傾向を保持する。UIは今回と次回だけを表示する。試験課題選択で選んだ候補の傾向を反映し、ShopにHeroが滞在中なら今回販売を維持して次回・次々回へ反映する。

`src/game/ShopSystem.js` はショップ到着後の売買フェーズ、購入品の段階的な開示、購入品の倉庫への配送を担当する。`src/game/GuildSystem.js` はギルド到着後の申請と期限延長を担当する。`src/game/FacilityReturnSystem.js` はショップ・ギルド・訓練に共通の装備整理と準備エリアへの帰還を担当する。

`src/game/BattleSystem.js` は戦闘参加者の更新、勝利判定、帰還を調停する。`CombatStageLifecycle` は戦闘開始・勝利・勝利待機の状態遷移を、`CombatActionGaugeSystem` は行動ゲージを、`CombatActionResolutionSystem` は一回の行動における行動開始・属性・武器効果・命中／会心・ダメージ・行動後フックを担当する。`CombatDamageSystem` はダメージ・軽減・反射・撃破判定を、`CombatDamageReactionSystem` は被ダメージ後の固有スキル反応を、`CombatEnemyDefeatSystem` は敵撃破後の報酬、召喚、投影体後始末を担当する。`CombatAttributeSystem`、`CombatConditionSystem`、`CombatWeaponEffectSystem`、`CombatProjectionSystem`、`CombatActionLog` はそれぞれ属性状態、固有スキルによる戦闘中だけの状態、武器固有の補助効果、一時投影体、行動ごとの戦闘ログを担当する。

`src/game/UniqueSkillSystem.js` は中ボス・ボス固有スキルの保有状態とフックを解決し、`UniqueSkillEffectSystem` は該当フックにあるすべての効果結果を生成する。通常の固有スキルは常時保有し、加護による一時保有は戦闘開始・行動終了・被ダメージ後に再抽選する。実装済みの効果と発火条件は[固有スキル要件](../requirements/03.unique_skills.md)を参照する。「影の指先」のタグ候補抽選は`UniqueSkillEffectSystem`、選ばれたタグのItemへの適用と参加者の派生値・行動ゲージ更新は`CombatActionResolutionSystem`が担当する。「夜の使い魔」の数状態は`CombatConditionSystem`、その周回と飛行の描画は`CombatEffectSystem`が担当する。`Item`は自身のタグ由来の重量・価値・Chip表示値を更新し、Hero・Enemyは装備変更後の所持重量を更新する。`src/game/EntityRegistry.js` はHero・Enemy・Itemの論理的な生存状態をChipの盤面上の有無から分離して管理し、情報ウィンドウが対象の実際の破棄時だけ閉じるための唯一の照会先になる。`src/game/StageKindDistribution.js` はrouteごとのboss・elite確率を解決する。`src/game/EncounterDefinitions.js` はkind別のEnemy編成、難易度、スロット割り当てを解決する。`src/game/StageController.js` はそれらを使った試験課題候補の生成、選択後の敵出現、勝利待機後の次回選択を担当する。

`src/app/StageSelectionModal.js` は、カメラ拡大率に影響されない画面固定の試験課題選択モーダルを担当する。選択中は `GameClock` の理由付き停止によってゲーム内部時間を停止し、Canvasの背景描画は継続する。候補ごとに6敵スロットを表示し、Enemy Chipは通常戦闘と同じ `ChipRenderer` で描画する。ボスは横2スロットを占有し、雑魚・中ボス・ボスの表示サイズ比と必要な表示領域高を保つ。遭遇イベント・加入候補は現時点では表示しない。

`src/app/FacilityNameplateRenderer.js` と `src/app/AreaNameplateRenderer.js` は、Canvas上の施設名・エリア名を描画する。対応するレイアウトと説明データは、それぞれ `FacilityLayout`／`FacilityDetailCatalog` と `AreaNameplateLayout`／`AreaDetailCatalog` に置く。`GameApp` は看板のタップを情報ウィンドウとして開き、`InformationWindowManager` が対象ごとの重複表示を防ぐ。

### 4.3 ゲームログと通知

`src/game/GameLog.js` はゲーム起動中のユーザー向けログをメモリに保持する。ログは主体（`hero`、`enemy`、`system`）、結果レベル（`info`、`luck`、`unluck`、`warning`）、発生場所（`battle`、`shop`、`guild`、`training`、`preparing`、`event`）を別に持つ。`src/app/FlowLog.js` は通知対象のログを画面上で横断表示するUIであり、Canvas・カメラとは独立した画面固定レイヤーとして描画する。

## 5. 仕様書の区分

- `docs/specifications/`: 実装済みのエンティティ・チップモデル仕様
- `docs/requirements/`: ゲームルール、画面・操作要件、設定資料
- `docs/architecture/`: 実装の責務分割と起動構成
- `docs/demo/`: 検証専用の挙動
- `docs/planning/`: 未実装作業と優先順位

## 6. GitHub Pagesのビルド配置

`.github/workflows/deploy.yml` はゲームを `$GITHUB_WORKSPACE`、GameWorksOAKの公開済みmasterを `$GITHUB_WORKSPACE/.ci/GameWorksOAK` へcheckoutする。共通リポジトリへのシンボリックリンクを `$GITHUB_WORKSPACE/../GameWorksOAK` に作り、ローカルと同じ隣接参照で共通ライブラリへの相対importを解決する。npmコマンド、npmキャッシュ、デプロイのdistは従来のゲームルートを対象とする。
