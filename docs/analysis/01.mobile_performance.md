# モバイル性能の調査

## 目的と扱い

モバイルで非常に重くゲームとして操作できないという報告について、実装とPC実測から改善対象を絞る。
実機では開発者ツールを使えず、確認にpush・公開が必要なため、調査・比較はPCで行う。
実機確認は恒久修正のPC検証・公開後の最終確認とする。

本調査の比較実験は恒久修正ではない。通常ビルドに調査用フックや処理省略を含めない。
PCのCPU負荷制限、小画面、高画素密度は負荷条件の比較であり、実機のCPU/GPUの再現ではない。
報告された端末の機種・OS・ブラウザー・画面・表示版が不明なため、その端末固有の原因は未確定である。

## 実装から確認できること

| 対象 | 実装 | 性能上の確認対象 |
| --- | --- | --- |
| `GameApp.resizeCanvas` | メインと方向表示Canvasの内部寸法へ端末の画素密度を反映 | 高画素密度で処理する画素が増える |
| `TrialSession` | 一時停止中も背景、施設・準備表示、全チップを毎フレーム描画 | 進行を止めても描画負荷は残る |
| `ChipBoard` | 重なり順と接地衝突で全組合せを走査 | チップ数が多い場合に負荷が増える |
| `InformationWindowManager.refreshDynamicEntries` | 実体情報が開いていると更新ごとに表示層へ通知 | 変更のない内容も再描画される |
| `InformationWindowLayer.render` | ウィンドウDOMを再作成し、配置・見出し寸法を実測 | DOM更新とレイアウト計算が繰り返される |
| `TimeSettingsController.updateStatus` | 毎フレーム同じ文言・クラスでもDOMへ書く | 不要なスタイル・レイアウト更新の可能性 |
| `GameClock.advance` | 壁時計の差分を最大50msに制限し、倍率反映後に分割更新 | 重いフレームではゲーム時間が壁時計より遅れる |
| `AssetLoader` | パス単位で画像を保持 | 毎フレーム画像を再取得する構造ではない |

`TitleMenu.choose` はタイトル演出を停止し、`GameApp` は試験終了時にTutorial・ログ・通知を破棄する。
明らかな停止漏れをコードからは確認していないが、長時間の実機メモリー増加がないことを保証するものではない。

## 計測方法

- `scripts/measure-performance.js` でローカル専用の本番計測ビルドと必要に応じ通常ビルドを生成・配信する。
- 実行手順・環境変数・各条件の意味は[テストの構成と実行](../../tests/README.md#pcでの性能調査)を参照する。
- 通常ビルドとの比較、詳細計測を止めた比較を用いて計測の影響を確認する。
- 初期ロード後に画像が描画された状態で測り、初回ロード時間とは分ける。
- 通常のタイトル、編成、開始劇のスキップ、課題選択を操作する。
- 全チュートリアルを完了した保存状態、乱数seed 54、初期2名、画面390×844 CSS pxを基本とする。
- 標準速度1倍、情報表示時の停止・スタミナ満タン時停止・自動加速は無効にする。
- 各条件は新しいブラウザーコンテキストで開始し、主要比較は5秒のウォームアップ後30秒を3回測る。
- 初期候補の絞り込みには短い予備測定を使い、主要比較の結果と区別する。
- CPU制限のない標準条件と、ブラウザーのCPU制限4倍を比較する。
- 毎フレームのconsole出力をせず、採取データを最大20,000件に制限する。
- フレーム間隔、更新・描画の処理時間、各処理の呼出回数、チップ数、ゲーム時間を記録する。
- ブラウザーのTaskDuration、LayoutCount、LayoutDurationなども測定区間の差分で保存する。
- データは各反復の終了時にJSONへ保存し、追跡用の集計には毎フレームの生配列を含めない。

採用した条件別データは[計測集計JSON](mobile_performance_measurements.json)に保存する。
`confirmation` は主要4条件（30秒×3回）、`paired` は同一画面での切り替え（10秒×3区間×3回）、
`supplemental` は候補の補助確認（8秒×1回）。補助確認を主要比較と同じ精度とは扱わない。
JSONには環境、各反復の平均・p95、フレーム間隔のp50/p95/p99、エラー、ブラウザー指標を残す。
生データはPlaywrightの清掃対象外である `tmp_performance/` へ保存する。

主要比較の再実行例（PowerShell）:

```powershell
$env:PERF_SECONDS='30'
$env:PERF_REPEATS='3'
$env:PERF_WARMUP='5'
$env:PERF_OUTPUT='tmp_performance/confirmation.json'
node scripts/measure-performance.js idle-cpu4 idle-cpu4-dpr1 information-cpu4 information-no-refresh
$env:PERF_OUTPUT='tmp_performance/paired.json'
node scripts/measure-performance.js information-paired
```

関数の描画呼出時間は、以前に投入されたCanvas処理の待ちを含む可能性がある。
関数別時間の大きさだけで原因を決めず、処理省略前後の全体時間・フレーム間隔を照合する。
情報更新や物理を省く比較は、その処理を取り除いた場合の上限評価であり、完成した修正の性能ではない。
`main` はGameAppの1回のコールバックの壁時計時間で、GPU描画完了までの時間ではない。
タイトル演出には別のコールバックがあるため、タイトルの負荷を `main` だけで評価しない。
マウス操作中のフレーム間隔は測るが、タッチから描画完了までの入力遅延を直接測ったものではない。
小さな関数の測定値にはタイマー粒度の影響があり、0という値を処理時間ゼロとは解釈しない。
処理群とその中の関数は包含関係にあるため、各時間を単純合計しない。

## 測定環境と結果

Windows 10.0.26300、Core i7-12700H、32GiB RAM、Intel Iris Xe（ANGLE/D3D11）、
Chrome 155.0.8059.86のheadless実行で測定する。ページは前景扱い（visibility=visible）。
電源・温度・OSの他プロセスは固定しておらず、反復の範囲を併記する。
ゲームは0.61.0、基準HEADは `7a3f2a4`、共通ライブラリは `e4974f8`（未コミット差分なし）。
ゲームの変更は版設定と調査用ファイルであり、通常のゲーム実装は基準HEADと同じである。

画素密度3でメイン・方向表示Canvasはそれぞれ1170×2532、合計約592万画素となる。
同じCSS寸法で画素密度1なら合計約66万画素となる。処理する画素は9倍の差がある。
この比率だけで処理時間が9倍になるとは扱わない。

解像度・情報更新の主要比較は各30秒・3回。表の主処理とフレーム間隔p95は3回の最小〜最大、
50ms超率とゲーム時間の進みは3回の平均。時間の単位はms。
「進み」は壁時計1秒あたりのゲーム内秒数で、標準速度1倍なら1が期待値となる。

| 条件 | 主処理の平均時間の範囲 | フレーム間隔p95の範囲 | 50ms超率 | 進み |
| --- | --- | --- | --- | --- |
| CPU4倍・画素密度3 | 40.4〜47.6 | 66.7〜83.5 | 51.1% | 0.87 |
| CPU4倍・画素密度1 | 19.7〜20.5 | 33.5〜50.0 | 1.9% | 0.99 |
| CPU4倍・情報ウィンドウ表示 | 90.6〜153.8 | 150.0〜266.6 | 100% | 0.35 |
| 同条件・実体情報の更新省略 | 72.8〜83.4 | 133.3〜150.0 | 97.9% | 0.52 |

通常ビルドではゲーム側に計測フックを入れず、独立したフレーム間隔の採取だけを行う。
このため通常ビルドのサンプラー自身の時間を、ゲームの主処理時間として表へ載せない。
詳細計測の影響はゼロではないため、詳細計測なし・通常ビルドでもフレーム間隔を確認する。
情報表示の反復には大きなばらつきがある。条件をまとめて順に測る比較だけで割合を断定せず、
同一画面での更新あり→省略→ありの比較も照合する。

同一画面の比較はCPU4倍、各区間10秒、3反復。表は区間ごとの主処理の平均時間（ms）。

| 反復 | A1: 更新あり | B: 更新省略 | A2: 更新を戻す |
| --- | --- | --- | --- |
| 1 | 91.3 | 43.2 | 89.2 |
| 2 | 190.7 | 103.1 | 211.0 |
| 3 | 194.0 | 91.5 | 176.2 |

反復間で絶対値は大きく異なるが、各反復で更新省略時に減り、更新を戻すと負荷も戻る。
更新省略を実装した完成版の性能とは区別する。

### 実測で支持されたこと

- 同じCSS寸法・CPU条件で画素密度3→1にすると、主処理の3回平均が44.2→20.0ms（約55%減）。
  50ms超の割合とゲーム時間の遅れも改善する。Canvasの内部解像度は有力な改善対象である。
- 情報ウィンドウを開いて進行すると、実体情報の更新だけで1フレーム平均約64.4msを使う。
  分割更新に伴い約3回/フレーム呼ばれている。更新を省いた比較では、30秒のLayoutDurationが
  3回平均4.85→0.29秒となる。DOM再構築と寸法計算は有力な改善対象である。
  異なる条件の3回平均の主処理は126.7→77.4msだが、環境変動を含むため、その差を修正の効果保証とはしない。
- CPU4倍・画素密度3では、標準速度でもゲーム時間が平均0.87倍、情報表示中は0.35倍になる。
  単なる見た目のフレーム落ちに加え、50ms制限による進行の遅れが生じている。

### 補助比較と未確定事項

以下は各8秒・1回。主処理は区間平均、時間の単位はms。

| 条件 | 主処理 | フレーム間隔p95 |
| --- | --- | --- |
| タイトル | 別コールバックのため非掲載 | 16.8 |
| 課題選択・時間停止中 | 15.1 | 33.4 |
| 標準CPU・画素密度3 | 14.4 | 33.4 |
| PC画面1280×900・画素密度1 | 13.0 | 16.9 |
| CPU4倍・詳細計測なし | 91.1 | 133.4 |
| CPU4倍・通常ビルド | 未計測 | 133.4 |
| CPU4倍・タグ/ステータスを128pxへ縮小 | 66.5 | 133.3 |
| 標準CPU・速度4倍 | 12.9 | 33.3 |
| 標準CPU・戦闘フロー・速度4倍 | 16.9 | 33.4 |
| PCマウスのドラッグ・ホイール拡縮 | 14.2 | 33.4 |
| 標準CPU・倉庫満杯（295チップ） | 46.6 | 66.8 |
| 同条件・接地衝突の計算省略 | 51.9 | 83.2 |

課題選択中はゲーム時間が停止していても描画負荷が残る。
詳細計測なし・通常ビルドでも低フレームレートを再現しており、計測処理だけが原因ではない。
条件間で絶対時間が変動するため、詳細計測のオーバーヘッドをこの補助表だけから固定値へ換算しない。
PC画面の条件はタイトル演出の乱数消費により敵数も異なり、画面サイズだけの因果比較には使わない。
速度4倍・PCマウス操作だけで大きな追加停止は再現しなかったが、実機タッチの応答を保証しない。

倉庫満杯では接地衝突に約4.1ms、描画順に約1.9ms、チップ描画に約29.8msを使った。
接地衝突を省いた条件は単発・別時点の比較で、全体時間の改善は確認できなかった。
物理の省略で悪化したと断定せず、物理計算だけで重さを解消できる根拠がないと判断する。

倉庫満杯は初期位置を実際の倉庫内に置き、実容量289品まで同種の武器を追加する。
自然なプレイでの品種分布とは区別する。

### 画像保持量の目安

通常画面で読み込み済みの画像は62枚、未完了は0枚、寸法の32bit RGBA換算は約161.5MiB。
主な内訳はタグ60MiB、ステータス30MiB、敵28MiB、エリア24MiB、Hero12MiB。
タグ・ステータスを128px PNGへ置き換えた比較では概算約72.8MiBとなった。
これは実際のヒープ・GPUメモリー使用量ではなく、圧縮・共有・キャッシュ・描画バッファの状態を含まない。
画像縮小だけでの安定したフレーム改善は未確定だが、実占有と適正なサイズの調査候補となる。

## 改善の判断

### 優先する改善案

1. ネイティブ解像度・camera zoomを維持し、通常画面の描画負荷を絞る。
   - 解像度2・1の画質はオーナー判断で不採用。画素削減を改善案として採用しない。
   - 画像の事前縮小・再利用、輪郭線、クリップ、静的表示のキャッシュ、画面外描画を比較する。
   - PC測定だけでは実機の極端な遅さを説明できていないため、一度の実機採取を追加合意した。
2. 情報ウィンドウは今回の修正対象から外す。
   - 報告時は開く前だったため、上記の実測結果を通常画面の原因として扱わない。
   - DOM再作成の軽減は独立したバックログとして残す。
3. 多数チップの状態で必要なら物理・重なり順計算を減らす。
   - 近傍候補の絞り込みなどで全組合せ走査を減らし、物理と描画順のそれぞれを測る。
   - 接地、落下、衝突、押し出し、同位置の描画順、選択時の当たり判定を維持する。
   - 満杯状態は物理計算だけでなく描画も増えるため、組合せ計算の修正だけで解決したとは扱わない。

静的な表示のキャッシュ・画面外描画の省略も候補だが、本調査でその実装効果を確定していない。
実装前に変更対象と無効化条件を絞り、比較実験で効果を確認する。
ショップ描画の単体時間、ラベル描画、アイコン画像の大きさだけから修正対象を決めない。

### 修正後の比較条件

- 同じPC・GPU・ブラウザーで、今回の標準・CPU4倍・高画素密度・情報表示・倉庫満杯を再測定する。
- 1つの変更ごとの効果と組合せ後の効果を分け、各30秒・3回の範囲を報告する。
- 平均の処理時間だけでなくp95/p99のフレーム間隔、50ms超の割合、ゲーム時間の進みを比較する。
- 変更していない通常条件の悪化がないことと、全テスト・本番起動を確認する。
- 実機での目標FPSをPCの結果だけで保証せず、公開後の最終確認で操作感を判断する。

`GameClock` の50ms制限を単純に外すと、重いフレームで更新仕事が増える可能性がある。
制限解除を性能改善として扱わず、1フレームの仕事量を減らす。

## 残る確認範囲

- 報告端末の実際のCPU/GPU、ブラウザー、熱・省電力状態、タッチ入力の応答。
- ネットワーク越しの初期ロード、実機上の画像デコード・GPUメモリー圧迫。
- 最大人数、複数の固有スキル・ログが重なる戦闘、長時間プレイ・再開始での資源保持。
- 画像の事前縮小・キャッシュを変更した場合の文字・チップの見た目と、拡大時の鮮明さ。
- 情報表示の更新方式を変更した場合の数値、ピン、親子関係、位置、拡縮・スクロールの維持。

実機で繰り返し採取することは前提としない。追加合意に基づく一度の採取には、
通常URLで表示する計測画面を使う。手順・比較条件・限界は[テスト手順](../../tests/README.md)を参照する。
恒久修正は範囲合意後に同じブランチで実施し、PCで性能比較・機能回帰を確認してから実機で最終確認する。
