# PC・モバイルの実機採取結果

## 根拠

オーナー提供のv0.61.1の2ファイルを分析した。両方とも11区間を完了し、実行時例外は0。
各区間の平均値は生フレーム配列から再計算して一致を確認した。
元ファイルのSHA-256、環境、状態、区間別集計、縮小画像一覧を
[採取結果](mobile_performance_owner_measurements.json)へ保存した。
元ファイルは変更していない。

| 環境 | PC | モバイル |
| --- | --- | --- |
| ブラウザー | Windows / Edge 155 | Android / Chrome 152 |
| DPR | 1 | 2.8125 |
| 主Canvasの内部寸法 | 1912×948 | 1200×2015 |
| チップ数 | 26 | 25 |
| camera zoom | 0.4145 | 0.1332 |
| 通常動作区間 | 既に一時停止中 | 進行中 |

画面・zoom・編成等はPCとモバイルで異なるため、端末間の比率をハードウェア差だけに帰属しない。
一方、各端末内の停止比較区間はtick・camera・チップ数・Canvas寸法が変わっておらず、情報ウィンドウは0。

## 比較結果

時間はフレームごとの主処理平均。FPSは平均RAF間隔の逆数であり、描画完了の直接計測ではない。

| 停止画面の条件 | PC主処理 | モバイル主処理 | モバイル平均RAF間隔 |
| --- | ---: | ---: | ---: |
| 元画像・基準2 | 8.65ms | 2143.93ms | 2271.60ms（約0.44fps） |
| 事前縮小画像 | 1.52ms | 3.50ms | 24.46ms（約40.9fps） |
| 元画像・基準3 | 8.65ms | 2127.67ms | 2235.90ms（約0.45fps） |
| 画像描画を省略 | 1.62ms | 3.15ms | 22.57ms |
| 輪郭線を省略 | 8.67ms | 2145.47ms | 2266.67ms |
| クリップを省略 | 8.85ms | 2150.50ms | 2279.70ms |
| Canvas描画命令を省略 | 2.69ms | 1.94ms | 11.88ms |

元画像の大幅な縮小を含む描画経路が、この実機の極端な遅さの主因だと強く支持される。
画像を消さず事前縮小版に置き換えても改善し、元画像へ戻すと再び遅くなる。
Canvasの解像度・zoomは変えておらず、今回画素数削減を修正に使う根拠にはしない。
輪郭線・クリップそれぞれの省略だけでは改善しなかったため、今回の第一の修正対象としない。

モバイルの通常区間ではシミュレーション平均0.70msに対し、背景・パネル約1546ms、チップ約502ms。
進行を止めても約2.1秒の主処理が残る。シミュレーションの量だけではこの症状を説明できない。
ただし区間時間はGPU処理待ち等を含み得るため、背景パネルの特定関数や画像1枚の原因確定ではない。
GPUの有効・無効、ブラウザー内部の縮小・デコード・転送・キャッシュのどれが支配的かは、このJSONだけでは確定しない。

## 変動・測定の限界

- 基準1は平均52.22msだが、末尾の3フレームが約1200/1611/1916msへ悪化する。
  区間全体の平均だけで「元画像でも軽い」と解釈しない。基準2・3では約2.1秒へ戻っている。
  画像準備直後のキャッシュ状態等は候補だが、根拠なしに内部機構を確定しない。
- 遅い基準2・3は3〜4フレームしか採取できておらず、p95等の精密な比較には不十分。
  ただし異なる元画像区間で同じ秒単位の遅さが繰り返し現れ、縮小区間では246フレームすべて主処理7.2ms以下。
- 縮小区間のRAF間隔p95は44.2ms、50ms超は0。改善は大きいが、一定の60fpsや長時間の快適性を保証しない。
- モバイルの縮小画像準備区間は287268.6ms（約4分47秒）、PCは1342.8ms。
  その間も元画像による重いフレームを描いており、縮小計算だけの所要時間ではない。
  この診断用実装をそのまま製品へ入れる設計は採用しない。
- 元画像を保持したまま縮小画像を追加する条件なので、元画像を減らした場合のメモリ改善を測った結果ではない。
- 全体表示倍率での短時間比較であり、拡大時の画質は未確認。

## 修正方針の提案

1. 元画像を残し、複数段階の縮小画像を開発時またはビルド時に生成する。
   実機上で一括縮小する待ち時間を避ける。
2. 各描画先の物理画素数に足りる段階を選び、zoom変更時も大きい画像へ切り替える。
   足りない縮小画像の拡大使用を避け、Canvas寸法・camera zoom・ゲーム内座標を維持する。
3. キャッシュは画像・段階ごとに再利用し、必要なものだけ読み込む。
   段階数と保持上限は資産容量とPC実測を見て決める。元画像を一律縮小して置き換えない。
4. PCで全体表示から最大zoomまでの画質・描画速度・初期ロードを確認し、合意した範囲で恒久修正する。
   情報ウィンドウの最適化は対象に追加しない。実機での再採取を繰り返す前提にしない。

上記は採取直後に提示した修正方針である。その後「測定を維持したまま改善」の指示を受け、
v0.61.2で事前生成734画像と描画時の段階選択を実装した。
同一PC条件の各15秒×3反復では、主処理が元画像9.36〜11.60msから2.96〜3.06msとなった。
詳細は[改善比較の集計](image_level_comparison.json)を参照する。
測定機能を維持し、画像選択方式・キャッシュ量・読み込み失敗をJSONへ追加した。
実機の改善後の速度・画質は最終確認待ちであり、PC結果だけで保証しない。
