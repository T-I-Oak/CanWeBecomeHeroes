# 情報ウィンドウの更新負荷

この文書は0.63.0の調査結果を記録する。通知のフレーム集約による実装・効果検証は
[情報更新の性能改善](06.information_window_performance_improvement.md)を参照する。

## 調査の目的と条件

実体情報の表示中に繰り返される更新処理が、画面更新とゲーム進行に与える負荷を確認する。
調査対象は0.63.0。画像の段階選択が有効な現行版を測り、過去のモバイル計測値とは直接比較しない。
恒久的な性能修正は行わず、更新を完全に省略する実験は改善余地の上限評価として扱う。

主要比較の生データはtmp_information_settled_main/results.json、
生配列を除く保存用データは[information_window_performance_measurements.json](information_window_performance_measurements.json)。
各条件3反復を個別に保存し、表には反復平均と最小～最大を示す。統計的な信頼区間ではない。

| 項目 | 設定 |
| --- | --- |
| 表示 | 390×844 CSS px、DPR 3、既定の画質・画像段階・カメラ |
| 開始状態 | チュートリアル完了、最初の2名で開始、最初の課題候補を選択 |
| 乱数 | seed=54、ゲーム生成と課題候補生成の直前に再初期化 |
| 比較画面 | 全ての敵の出現待ちがなく、stage=battleになった後の画面 |
| 情報表示 | 最初のHero Avery、instanceId=entity-1の実体情報1枚 |
| 時間 | 速度1倍、情報表示・スタミナ満タンによる停止と自動加速を無効化 |
| 測定 | 5秒ウォームアップ後30秒×3反復、headless Chrome |
| CPU | 標準とCDPの4倍制限。モバイル実機を再現するものではない |
| 省略 | CPU4倍でrefreshDynamicEntries全体をローカル変換から省略 |
| 同一画面 | CPU4倍で更新ありA1→省略B→ありA2、各10秒×3反復 |
| 計測影響 | 情報表示の標準・CPU4倍で詳細計測なしを追加 |

再実行は[テスト手順](../../tests/README.md#pcでの性能調査)に従う。
他のテスト・ビルドは主要比較と並行実行しない。

```powershell
$env:PERF_SETTLED_INFORMATION = '1'
$env:PERF_OUTPUT = 'tmp_information_settled_main/results.json'
node scripts/measure-performance.js idle-dpr3 idle-cpu4 information information-cpu4 information-no-refresh information-paired information-no-probe information-cpu4-no-probe
node scripts/summarize-performance.js docs/analysis/information_window_performance_measurements.json tmp_information_settled_main/results.json
```

PERF_SECONDS・PERF_REPEATS・PERF_WARMUPの上書きがないことを確認する。
予備測定は3秒・1反復・ウォームアップ1秒で別保存し、主要比較に混ぜない。
初期の測定ではタイトル演出による乱数消費と敵の出現途中の状態差が見つかったため、
生成直前の再初期化と出現完了待ちを追加した。同じseedをページ初期化時だけに与えても、
画面遷移までのフレーム数が違えば同じ課題にはならない。

## 更新経路と指標の意味

TrialSession.updateはGameClock.advanceの分割処理内でrefreshDynamicEntriesを呼ぶ。
GameClockは壁時計の差を最大50msに制限し、最大1/60秒ずつに分割する。
遅いフレームでは速度1倍でも最大3回の動的更新が発生する。
一方、フレーム間隔が50msを超えても、その分を全てゲーム時間へ取り戻さないため、進行が遅くなる。

Managerは実体情報がありドラッグ・操作中でなければonChangeへ全entryを渡す。
Layer.renderは全entryのDOMを生成してreplaceChildrenし、ウィンドウの位置決め・タイトル調整を行う。
位置決めのgetBoundingClientRect、タイトルの寸法取得の前にDOMを書き換えるため、
分割更新ごとに同期的なレイアウト計算を発生させる経路がある。

- mainは1フレームのJavaScript主処理時間。ブラウザーの後続描画全体を含む指標ではない。
- informationはManager.refreshDynamicEntriesの累積時間/フレーム、renderはLayer.renderの累積時間/フレーム。renderはinformationに内包され、加算しない。
- 呼出回数は詳細計測有効時の実呼出を数える。情報非表示でもManagerは呼ばれるがLayerは呼ばれない。
- LayoutCount・LayoutDuration・RecalcStyleDuration・TaskDurationはCDPの区間差分。ウィンドウ以外も含む。
- ゲーム秒/実秒はtick差/60をCDP Timestamp差で割ったもの。通常比較は採取した先頭～末尾フレームのtick差で、端の約1フレームを含まない。
- p95/p99は各反復のフレーム間隔を昇順にし、floor((n-1)×分位)の値を採用する。
- 同一画面の区間はCDPとゲーム状態を逐次取得するため、境界の取得中にもフレームが進む。区間別フレーム集計とCDP差分の境界は厳密には同時でない。
- 詳細計測なしでもローカル変換・フレーム配列採取・skip判定は残る。通常ビルド全体との厳密なオーバーヘッド差ではない。

## 環境と主要比較

測定開始は2026-10-24 10:49:57（日本時間）。Windows 10.0.26300、
Intel Core i7-12700H（20論理CPU）、メモリー31.71GiB、Chrome 155.0.8059.86。
WebGLの申告値はANGLE / Intel Iris Xe / Direct3D11で、主要Canvasは1170×2532 px。

ゲームHEADはb2d8bc6952df240408237112b800daf3e085981b、
共通側HEADはe4974f86606374fb81dae4e57644f051085c2c45。共通側の差分はない。
ゲーム側は計測補助・テスト・版設定の未コミット差分を使い、環境情報に採取時のtracked diff統計を保存した。
通常アプリのsrc/は変更していない。

課題構成はregular・patternIndex=10・level=5、信用の小敵2体と火の小敵2体。
全24反復の開始時点で29チップ・Hero2名・敵4体・出現待ち0件・stage=battleが一致した。
各フレームも29チップ・速度1倍・停止なしを維持し、同一画面比較の情報対象と開始終了状態も一致した。
実行時・consoleエラーは全反復0件、採取開始時の未完了画像は0件。全24反復を完了し、スクリプトは終了コード0だった。
情報表示条件には396×396 pxのプレビューCanvasが1枚追加される。共通の主要Canvas寸法は同じである。

## 対策判断と後続候補

情報ウィンドウの更新経路には対策が必要と判断する。標準CPUでのフレーム間隔・進行への影響、
同一画面3反復での再構築・Layout時間・フレーム間隔の往復変化が根拠である。
対象は表示中の反復更新であり、実機タップ応答の悪化そのものを測定した結論ではない。
一方、CPU4倍では完全省略でも50ms超率がほぼ100%であり、情報更新の対策だけで快適になるとは判断しない。

後続実装の候補は次の順に評価する。いずれもこの調査で実装効果を確認したものではない。

1. 分割更新を終えた後に通知を集約する。フレーム内の中間状態を全て再描画する必要性を整理し、消滅時の閉鎖と表示値の鮮度を維持する。
2. 同じentryのDOMを保ち、変わった現在値・装備・タグなどの部分だけを更新する。変更検知には翻訳・定義文言・固有スキルの表示条件も含める。
3. サイズ・言語・内容・拡縮が変わったときにだけ位置・タイトルの寸法計算を行う。位置やscaleを変更した後の座標と表示の一致を保つ。

単なる一定間隔への更新制限は、表示の遅延を新たに生む可能性があるため、最初の候補とはしない。
実体情報のHP・スタミナ・属性・装備・タグ・現在の状態を更新し続け、
ピン・親子の置換・ドラッグ位置・拡縮・内部スクロール・実体消滅時の閉鎖を維持する必要がある。
実装後は要求05・関連実装テストと同じ性能条件を再実行し、表示の正しさと全体のフレーム間隔・進行を確認する。

## 解釈の限界

- PCのCPU制限である。実機のタッチ応答、GPU・熱・電力制限、ブラウザー差の再現保証はない。
- 情報1枚・29チップの画面が対象。多数のピン・親子ウィンドウ、異なる実体情報、スクロール操作中を網羅しない。
- 更新省略は値を古いまま固定する実験であり、採用可能な修正ではない。完成した修正の改善率として扱わない。
- 画面構成を揃えても実時間に対するゲーム進行は負荷で変わる。開始tick・スタミナ等の現在値まで完全一致する比較ではない。
- 条件はスクリプト内の順番で実行している。ランダム化・交差配置による環境変動の完全な排除はしていない。同一画面のA1/B/A2で往復の再現を確認する。
- TaskDurationやLayoutDurationはCPU4倍の影響を受けた壁時計時間であり、実CPU使用率そのものではない。
- 計測用wrapperの同期時間だけではCanvas・ブラウザー後続処理の全てを説明できない。情報更新以外に残る負荷の修正はこの調査の対象外。
