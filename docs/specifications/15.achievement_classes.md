# 集計・アチーブメントクラス設計

## 設計の目的（確定）

本書は[アチーブメント仕様](14.achievements.md)に基づく実装構成を示す。68種類の個別定義をグレード式と段階テーブルで評価する。通常58種類は15段階、タグ10種類は7段階で評価する。終了画面の表示対象選定・共通表示部品・取得トースト・レコード画面への接続は実装済み。

集計はゲーム内の事実を扱い、アチーブメントはその事実から達成グレードを求める。両クラスはUIと永続化を担当しない。個別のアチーブメントの追加に伴い、ゲーム処理へ個別の判定・カウンターを追加しない。

## 中間クラス：StatisticsCollectorの呼び出し構成（確定）

ゲーム処理のフックはStatisticsCollectorを呼ぶ。Collectorは今回のラン用・累積用の集計インスタンスを配列として持ち、受け取った情報を両方へ配信する。ゲーム処理は個々の集計インスタンスを直接呼ばない。

累積はゲーム中にも随時更新し、トーストのグレード上昇判定に使える状態を保つ。ラン終了時に今回のランの値を累積へ再加算しない。

### 変換処理の配置（確定）

Heroのタグ列からタグ数表への変換と、出発時の装備から武器種類の列への変換はCollectorで一度行う。同じ変換を2つの集計で繰り返さず、値だけの入力を両方へ配信する。他のイベントはフックから渡された数値・IDを使う。

### グレード表の保持と差分判定の進行（確定）

Collectorは初期化時に累積集計を受け取り、アチーブメントクラスで評価する。ラン開始イベントを集計する前のグレード表を`startGrades`として保持し、ラン中の比較用の`previousGrades`もその値で初期化する。この処理はグレード表の取得・保持だけを行い、更新時の差分通知処理は通らない。

各集計更新後、Collectorが累積集計と`previousGrades`をアチーブメントクラスへ渡して評価を呼ぶ。返されたグレード表で`previousGrades`を置き換え、`startGrades`は変更しない。グレードの計算と比較処理自体はアチーブメントクラスが担当する。

Collectorはランごとに初期化する。今回・累積の配信用配列とは別に、判定対象となる累積集計を識別できるようにする。

`new StatisticsCollector({ run, total, achievements, onGradeRaised })`で生成し、`record(event)`を呼ぶ。内部では`[run, total]`へ配信する。通知段階が上昇した結果を`onGradeRaised`コールバックへ渡す。`TrialSession`は`TrialStatisticsSession`生成前に`AchievementToast`を用意し、このコールバックを表示側へ接続する。ラン開始・初期Hero接続時の通知も受け取る。

## 集計クラス：GameStatistics（確定）

1インスタンスは1つの集計状態を持つ。今回のラン用と累積用に別のインスタンスを作り、同じ形式の集計情報をアチーブメントクラスへ渡す。

- ラン用は開始時に空の状態から作成する。
- 累積用は既存の保存状態から作成する。
- ゲーム処理から受け取った事実に従い、回数の加算・最高値の更新を行う。ラン結果のランキングは別の責務とする。
- Hero・Enemy・Itemなどの生きた実体、翻訳文、UI要素は保持しない。ID、数値、モード、日時、終了メンバーなどの値だけを保持する。
- アチーブメントの条件・グレード・通知済み状態は持たない。

### API

| API | 責務 |
| --- | --- |
| `new GameStatistics({ data, run })` | 保存済みまたは空の集計状態から構築する。ラン用は`run: true`とする |
| `record(input)` | Collectorから渡されたID・数値を集計する |
| `exportData()` | 保存・終了結果用に独立したデータを取得する |
| `getClearedStageCount()` | 集計した課題のクリアー回数の合計を返す |

達成の差分比較用に集計全体を複製するsnapshotは設けない。評価は現在の`data`を読み取り、保存・終了結果を作る時だけ`exportData()`で複製する。

`record`は次の事実を受け取る案とする。文字列ログの解析や、画面の表示からの収集は行わない。イベント履歴を全件保存する方式ではなく、受け取った時点で集約する。

| 事実 | 渡す情報の案 | 集約先 |
| --- | --- | --- |
| ラン開始 | モード、ランID、開始日時、初期Heroの組合せ分類 | モード・組合せごとの開始回数 |
| 課題挑戦 | 課題ID、課題レベル | 課題ごとの挑戦回数 |
| 課題クリアー | 課題ID、課題レベル | 課題ごとのクリアー回数・最高クリアーレベル |
| 施設への出発 | 施設ID、Hero ID | 施設・Heroごとの回数 |
| 敵討伐 | 敵種ID、今回獲得した貢献pt | 敵ごとの討伐回数・累積獲得pt |
| Heroのタグ状態 | Hero ID、タグごとの数 | Hero・タグごとの最高値 |
| ラン終了 | モード、ランID、結果、初期Heroの組合せ | 合格回数など。ランキングへの終了結果の登録は別途行う |

ゼロptの敵も討伐として記録できるよう、討伐成立と獲得ptの大小を区別する。最高値は加算せず最大値で更新する。タグ数は装備込み・上限適用なしとする。施設利用は出発確定時（行き先に応じてチップに色を着けるタイミング）に数える。課題は種類と構成indexの組で識別する案とする。

敵討伐イベントには、特定できる場合だけ最後のダメージを与えたHero IDも含める。討伐者と敵の情報は`isRun`が真のラン用で保持し、累積側では討伐者別カウントや履歴を作らない。終了画面が参照できる終了情報へ渡す。

ラン用ではHero・敵種ごとの討伐回数と討伐時の最高課題レベルとして集約する。Hero・武器種類ごとの装備回数は試験場への出発時に装備武器1個ごとに加算し、ラン・累積の両方へ保持する。

施設詳細はHero別のショップでの宝石スキルによる実際のタグ追加数、ギルドの延長時間、訓練の幸運によるスタミナ消費軽減成功回数とする。ラン・累積の両方へ保持する。宝石追加タグ数は配送処理時に集計し、倉庫の受入可否を条件にしない。購入品へ実際に追加されたタグは、倉庫満杯で入手できない場合も能力の成果として数える。

### 集計状態の構造案

| 領域 | 内容 |
| --- | --- |
| `runs` | モード・初期Hero組合せごとの開始回数・合格回数 |
| `stages` | 課題ごとの挑戦回数・クリアー回数・最高クリアーレベル |
| `facilities` | 施設・Heroごとの利用回数 |
| `combat` | 敵種ごとの討伐回数、獲得貢献ptの合計 |
| `heroes` | Heroごとの各タグ最高値 |

終了結果のランキングは集計情報から必要なラン内の値を受け取り、別の処理で管理する。複数の基準それぞれの上位N件の和集合を保持し、どの基準でも上位N件に含まれない結果は破棄する。Nは定数で10件とする。アチーブメントクラスはランキングを参照しない。

一般集計はモードを分けず共通に保持する。ラン開始・合格回数とラン結果では必要なモードを区別する。未クリアーの課題の最高レベルはnullとし、表示では未記録を示す。

## アチーブメントクラス：Achievements（確定）

現在の集計情報を読み、定義ごとに達成グレードを判定する。前回のグレード表を引数として受け取り、今回のグレード表と上昇した項目を返す。集計状態の変更、前回の入力の内部保持、保存、トースト表示は行わない。同じ定義と入力には同じ結果を返す。

### 定義と評価（確定）

JSモジュールで定義を管理する。各定義はID、計算値pの取得方法、グレード式G(p)、段階数s、表示用の評価項目、整数グレードごとの所見を持つ。集計項目の参照、合算、最大値は計算値の取得処理が担当する。

以前のcomparisonとグレードごとのvalueで達成を順次比較する方式は、read(data)による値取得とgradeFormula(p)による評価へ置き換えた。通常は `G(p) = sqrt(p/t) × s`、タグは `G(p) = (p-1)/2`。最高位の開始G値は通常s=15、タグs=3。段階数は通常15、タグ7とする。

整数達成グレードは開始G値を満たす最上位の段階テーブル行番号。通常はGの整数化と一致し、タグは半刻みのG値で7段階を選ぶ。未記録はG0とする。整数グレード表が差分判定用の状態であることは従来どおり。連続G値の増加だけでは上昇通知しない。

表示候補の選定に使えるよう、今回ランの整数化前・上限制限前のG値も評価結果として取得できる構成にする。具体的なプロパティ名・APIは実装時に決める。

### 結果画面用の評価（確定）

ラン開始前と終了後の累積整数グレードを比較して上昇を検出する。上昇した項目を優先し、それ以外は今回ランのG値順に上限まで採用する。G値が1以上という候補条件は設けない。同じIDを重複させない。

表示件数を制限する場合は、整数グレード上昇を優先し、次に今回ランの連続G値で採用対象を決める。上昇項目だけで上限を超える場合は、アチーブメントの定義順で上限まで採用する。採用後は上昇の有無にかかわらず全体を定義順へ並べる。G値による順序で表示しない。

表示する判定・所見は、上昇の有無にかかわらず終了後の累積整数グレードを使用する。累積整数グレード0は、終了画面ではEと未達成用の所見を表示する。これは新たな達成ではない。従来のexistingに今回ランのグレードを渡す方式は変更する。

判定処理はUI・翻訳・保存を担当しない。選定処理の配置と具体的な戻り値は実装時に定める。補充候補の今回ランG値が同じ場合は、アチーブメントの定義順で採用する。終了画面の表示上限は10件で確定している。

### 段階評価・定義生成・共通表示の責務（確定）

- JSの定義生成：敵・タグごとに展開し、各言語の名前を差し込んだ完成済みの評価項目・条件・所見を用意する。
- 判定クラス：G値を求め、参照する段階テーブルを高い段階から評価して判定・所見番号・通知段階を選ぶ。所見番号・通知段階は各アチーブメント内の番号。通知段階の上昇で通知対象を判定する。
- 共通DOM生成：表示モードと表示対象エントリ一覧を受け取り、完成済みリソースを配置する。toastモードは1回の生成につき1エントリで、AchievementToastが生成した行を共通テーブルへ追加して複数行を表示する。終了画面は選定済みの上限ありの複数、レコードは全エントリ。CSSは共通とする。
- カテゴリセルの結合：DOM生成時に表示対象の同一カテゴリの連続行数からrowspanを決める。カテゴリのないトーストでは行わない。

通常はFIFTEEN_LEVELS、タグはSEVEN_LEVELSを参照する。通常の所見はD/C→1、B/A→2、S→3、通知段階は細分段階を含む1〜15で、−／無印／＋もそれぞれ通知する。タグの判定はD・C・B・A・A＋・S・S＋、所見はタグ数1〜2・3〜4・5〜6・7以上の4区分、通知は7段階。未達成はE。一度の更新で複数段階を越えた場合は、最終到達判定を1件だけ通知する。表示仕様の正本は[アチーブメント仕様](14.achievements.md)の共通表示形式と段階テーブルの節、[取得トースト仕様](18.achievement_toast.md)を参照する。

### 既存コードとの差異

evaluateは { grades, gained, notices, entries } を返す。gradesは段階の番号（0は未達成）、gainedは表示段階の上昇、noticesは通知段階の上昇。entriesはID・カテゴリ・計算値p・連続G値・段階番号grade・判定label・所見番号comment・通知段階noticeを持つ。未記録pはnullとする。evaluateRunは { new, existing, entries } を返す。entriesには終了後累積の評価とupdated、runGを保持し、未達成候補も除外しない。既定では定義順を維持する。終了画面の上限選定はResultAchievementSelectionへ渡す。

## 呼び出しの流れ（確定）

`TrialStatisticsSession`がCollector、2つの集計インスタンス、アチーブメントクラスを組み合わせる。配信、初期グレード表の保持、ラン中の差分判定の呼び出しはCollectorが担当する。

1. Collectorの初期化時にラン開始前の累積を評価し、グレード表を結果画面用の`startGrades`として保持する。同じ値からトースト比較用の`previousGrades`を初期化する。更新時の差分通知処理は通らない。
2. フックがCollectorを呼び、Collectorがラン用と累積用へ配信して両方の集計を更新する。累積の随時更新と保存タイミングは分けて考える。
3. Collectorが更新後の累積と`previousGrades`を`evaluate`へ渡す。返された`grades`を次の比較用に保持し、`notices`があれば通知コールバックへ渡す。表示段階の差分gainedとは区別する。
4. ラン終了の事実を反映してから、Collectorの`getRunAchievements()`経由で開始前の`startGrades`、終了後の累積`total`、終了ランの`run`を`evaluateRun`へ渡す。
5. 集計・判定結果を保存側と結果画面へ渡す。トースト表示済みでも結果画面の新規達成から除外しない。

`startGrades`はラン中に変更せず、`previousGrades`だけを各評価結果で置き換える。同じ事実をラン・累積へ反映するのは意図した処理だが、ラン終了時にラン全体を再加算して二重集計しない。

## フック（確定）

| 情報 | 接続先 |
| --- | --- |
| ラン開始・終了 | `TrialSession`のセッション開始、`TrialRunFlow`の終了遷移 |
| 課題挑戦 | `StageController.selectStage`で選択が確定した時点。選択肢の生成では数えない |
| 課題クリアー | 勝利確定の遷移。最終課題は`victory`でもラン終了するため、`complete`だけを条件にしない |
| 敵討伐・獲得pt | `CombatEnemyDefeatSystem.resolve`で盤面上の敵の討伐が成立した時点。対象不在では通知せず、ゼロptの討伐は通知する |
| 施設利用 | 行き先に応じたチップの着色が始まる出発確定処理。描画フレームごとには数えない |
| タグ最高値 | 初期Hero・加入Heroの生成と、装備・解除など実際のタグ数が変わる処理。装備込み・上限適用なしの数を収集する |

フックはゲーム内の事実だけを通知し、個別のアチーブメントIDや条件を持たない。状態更新の繰り返し呼び出しで同じ事実を再通知しないよう、成立・遷移を通知する。

討伐者は`CombatDamageSystem.applyEnemyDamage`の`actor`から取得し、`onEnemyDefeated(target, actor)`経由で討伐成立の処理へ受け渡す。ゲームログ文字列から復元しない。

## 永続保存の時点（確定）

累積集計は課題決定時とゲーム終了時に保存する。課題決定時は挑戦の集計後、ゲーム終了時は終了の集計後とする。各イベントでのメモリ更新・グレード評価とは独立した保存時点である。

途中離脱では最後に成功した保存時点までの集計が残る。未保存分は残らず、途中ランの終了記録や再開可能な状態は生成しない。保存の実処理はRepositoryへ委ねる。

## 後続の検討事項（検討中）

- 将来追加する条件が既存の集計情報では判定できない場合は、必要な集計項目を追加する。複合条件のための追加集計は現時点では実装しない。
- 取得トーストの表示と演出は[取得トースト仕様](18.achievement_toast.md)、レコードのUI接続は[ラン記録仕様](16.run_records.md)を参照する。

## 設計を検証する観点（検討中）

- 連続G値から整数達成グレードを求め、終了画面の候補選定と定義順表示を分ける。
- 同じ事実でラン・累積が更新され、獲得ptが消費で減らない。
- 課題の最高レベルは最大値で更新され、イベント履歴は増えない。
- トースト用の直前比較と、結果画面用の開始前比較が独立する。
- ラン・累積の集計が独立し、グレード評価が前回表とラン開始前の表を変更しない。
- グレード判定だけを追加する場合、既存の収集情報で足りる限りゲーム処理の変更が不要。

### 実装済みの共通表示境界

- src/app/AchievementTable.jsのcreateAchievementTableが mode・entries・headings を受け取りtable要素を返す。modeはresult／record／toast。
- entriesは選定・整列・翻訳済みで、categoryId・category・label・condition・gradeLabel・comment・updatedを持つ。headingsはcategory・item・grade・commentの見出し文字列。
- 終了画面が既存リソースを表示エントリへ変換し、共通部品のresultモードを使う。共通部品は評価・選定・翻訳・保存・画面遷移を担当しない。
- resultはカテゴリー・項目・判定・所見、recordはカテゴリー・項目・判定・判定基準・達成度、toastは1項目の項目名・判定のみ。recordのentriesはprogress（現在値・次評価目標・比率）とprogressLabelを持ち、headingsはcondition・progressを追加する。カテゴリー結合は表示一覧の連続するcategoryIdで判定する。
- 表の共通スタイルはsrc/styles/achievement_table.cssに集約する。画面固有の幅・配置は呼び出し側が担当する。取得トーストはAchievementToastが行ごとの演出・寿命・待機列を管理し、TrialSessionから接続する。表示詳細は[取得トースト仕様](18.achievement_toast.md)を参照する。RecordScreenはrecordモードを使用する。
