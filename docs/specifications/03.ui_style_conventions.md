# UIスタイル設計規約

## 1. 目的

本規約は、UIの見た目をその場の都合で追加するのではなく、ゲーム内で何を表す表示なのかを将来も一貫して選べるようにするための共通契約である。

CSSクラスは、コンポーネントの文脈、表示内容の意味、UI状態を分けて表す。意味だけを示すクラスが、コンポーネント外で見た目を持ってはならない。

## 2. クラスの役割

### 2.1 コンポーネントクラス

画面上のUI部品とその構造を表す。PascalCaseを使う。

- `.Toast`: 通知1件を表示するコンポーネント
- `.Toast__Message`: `.Toast` 内のメッセージ要素
- `.NotificationCenter`: 複数の通知を画面固定位置へ積むコンテナ

要素クラスは `Component__Element` の形式とする。コンポーネントクラスは配置、寸法、共通レイアウト、出入りアニメーションなど、その部品の構造だけを担う。

### 2.2 意味クラス

表示内容が誰・何に関するものかと、結果の性質を表す。小文字の単語を使う。

#### 主体

- `.hero`: 名前を持つ味方キャラクターが主語の出来事
- `.enemy`: 名前を持つ敵キャラクターが主語の出来事
- `.system`: ゲーム全体、共有資源、期限、進行状態が主語の出来事

効果の対象が味方全体でも、行動者を示せる場合は `.hero` または `.enemy` とする。例: 「○○は味方全体の士気を上げた」は `.hero.info` である。

#### 結果レベル

- `.info`: 通常の情報・状態変化
- `.luck`: ランダム判定などにより主体にとって有利な結果
- `.unluck`: ランダム判定などにより主体にとって不利な結果

`luck` と `unluck` は単なる重要度ではない。原則としてランダム判定の上振れ・下振れを表し、期限延長のような個別の計算結果では各仕様が定める基準値で分類する。

### 2.3 状態クラス

UIの操作可能性・表示中・選択中など、意味分類とは独立した一時状態を表す。`state-` 接頭辞を使う。

- `.state-clickable`: クリックまたはタップできる
- `.state-disabled`: 操作できない
- `.state-selected`: 選択中
- `.state-visible`: 表示中
- `.state-leaving`: 退場アニメーション中

状態クラスは、意味クラスを置き換えない。たとえば、Heroにとって幸運な通知が操作不能になっても、`.hero.luck.state-disabled` のように三者を併記する。

## 3. スタイルを定義する場所

意味クラス・状態クラスだけに、グローバルな見た目を定義してはならない。

```css
/* 禁止: どのコンポーネントに属するか分からない。 */
.hero { color: blue; }
.luck { background: gold; }

/* 正式: Toast内のHeroにとって幸運な表示として定義する。 */
.Toast .hero.luck { /* Toast用のHero幸運スタイル */ }
.Toast .enemy.unluck { /* Toast用のEnemy不運スタイル */ }
.Toast .system.info { /* Toast用のシステム情報スタイル */ }
```

同じ意味クラスでも、詳細ログ、モーダル、ステータス表示では異なるスタイルを持てる。その場合も、それぞれのコンポーネント文脈を先頭にしたセレクタを使う。

```css
.BattleLog .hero.luck { /* 戦闘ログ用 */ }
.Toast .hero.luck { /* トースト用 */ }
```

状態スタイルもコンポーネントに限定する。

```css
.Toast .state-clickable { cursor: pointer; }
.Toast .state-disabled { pointer-events: none; }
.Toast .hero.luck.state-clickable { /* 必要な組合せだけ追加の強調 */ }
```

## 4. ToastのHTML契約

通知は、外側にコンポーネント、内側に意味・状態を持つ要素を置ける。これにより、外側は通知の配置と出入りを、内側はメッセージの意味に応じた見た目を担当できる。

```html
<div class="Toast">
  <div class="hero luck">剣士・アヴェリーは敵に会心ダメージ120を与えた。</div>
</div>
```

状態が必要なら内側へ追加する。

```html
<div class="Toast">
  <div class="system info state-clickable">期限の残りは6日です。</div>
</div>
```

コンポーネントの構造上必要なら、意味・状態クラスをコンポーネント要素と同じ要素へ置いてよい。

```html
<article class="Toast__Message hero luck state-visible">…</article>
```

どちらの構造でも、見た目は `.Toast .hero.luck` のようにコンポーネント文脈で定義する。

## 5. テーマと色

ゲームは現在テーマ切替を要件としないため、テーマ用クラスは必須ではない。将来テーマを導入する場合だけ、最上位のテーマコンテナを追加し、テーマ固有の上書きをその配下に限定する。

```css
.ThemeNight .Toast .hero.luck { /* 将来のテーマ差分 */ }
```

テーマを持たない現在は、`.Toast .hero.luck` などの組合せセレクタを正式なスタイルの単位とする。

## 6. JavaScriptとの境界

- JSは、コンポーネント・意味・状態に対応するクラスを付け外しする。
- スタイルに無関係な識別子やゲームデータは `data-*` 属性またはJSの状態として持ち、CSSクラスをデータ格納先にしない。
- 表示内容の意味は、`subject`（`hero` / `enemy` / `system`）と`level`（`info` / `luck` / `unluck`）を別パラメータとして渡す。描画側はそれぞれを独立したクラスとして出力する。

## 7. 既存実装の扱い

現在の通知実装は `fortune`、`misfortune`、`hero`、`enemy`、`system` の単一分類と、`is-visible`、`is-leaving` の旧状態クラスを使用している。

通知ログを主体・レベルの2軸へ更新する実装単位で、以下へ移行する。

- `subject`: `hero` / `enemy` / `system`
- `level`: `info` / `luck` / `unluck`
- 状態: `state-visible` / `state-leaving` など

移行完了までは、既存クラスを互換目的で維持する。新規UIは本規約へ従い、単一分類の新規追加は行わない。
